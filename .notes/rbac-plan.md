# Разделение прав по ролям и вход по ролям

Задача Отабека от 06.10 в группе. Запрет «роли не трогать» (25.09) снят тем же
сообщением. План составлен 06.10, ведёт dev2, ветка `feature/frontend-import`.

## Что просил заказчик

1. У каждой роли свой вход: логин = роль, пароль `<логин>123` — **дефолтный**.
2. После первого входа человек обязан сменить пароль; пока не сменил — не пускать.
3. Забывшему пароль сбрасывает руководитель.
4. Нынешний демо-список людей заменить списком по ролям.

## Решения, названные заказчику

| Логин | Роль (код) | Компании |
|---|---|---|
| `admin` | Администратор (`admin`) | обе |
| `owner1` | Собственник (`owner`, новая) | Торговый дом (`trade`) |
| `owner2` | Собственник (`owner`) | Завод (`plant`) |
| `director` | Директор (`director`) | обе |
| `finance` | Бухгалтер (`accountant`) | обе |
| `sales` | Менеджер продаж (`sales_manager`) | обе |
| `warehouse` | Кладовщик (`warehouse_keeper`) | обе |
| `master` | Начальник производства (`production_master`) | Завод |
| `worker` | Сотрудник производства (`production_worker`) | Завод |

- Коды существующих ролей **не переименовываются**: на них висят сид, назначения
  и тесты (правило 1 в шапке `roles.service.ts`).
- «Руководитель», который сбрасывает пароль, — это право `admin.users`:
  администратор и директор. Собственнику сброс чужих паролей не даём.
- Права `owner`: всё на просмотр по своей компании, включая финансы и отчёты;
  ни одного `admin.*`; ничего не проводит и не правит. Набор вычисляется
  правилом «все права с суффиксом `.view`», а не списком, — новое право на
  просмотр попадёт собственнику само.
- Учётка `user` с правами администратора (решение 25.09) убирается.

## Что делаю

1. `must_change_password` в `user_account` + миграция (прогон под owner-URL).
2. `POST /auth/me/password` — текущий пароль + новый, не короче 8, новый не
   равен дефолтному `<логин>123` и не равен текущему.
3. Пока признак стоит: вход проходит, `GET /auth/me` и смена пароля работают,
   остальные маршруты — 403 с кодом `PASSWORD_CHANGE_REQUIRED` и текстом на
   ru/uz. Разрешение помечается декоратором `@AllowTempPassword()`.
4. Сброс руководителем — на существующей заявке: `action: 'done'` выдаёт
   временный пароль, возвращает его один раз в ответе и поднимает признак.
   Там же снимается блокировка и обнуляется счётчик неудачных входов.
5. Сид профиля `demo` — девять учёток выше, пароль `<логин>123`, признак
   поднят у всех. Старые демо-люди и `user` убраны. Профиль `dev` не тронут.
6. Фронт: окно «Измените пароль» сразу после входа без возможности обойти;
   отбор разделов сайдбара по правам; показ временного пароля один раз в
   заявках.
7. Для стенда — одноразовый скрипт `scripts/rbac-stand-accounts.ts`: приводит
   учётки к новой схеме без пересева. Пересев стенда не делаю: он сотрёт
   демо-данные.

## Красный → зелёный

На каждую возможность: падающая проверка → починка → зелёный прогон → слом
обратно. Сторожа:

- `test/stand-logins.spec.ts` — перевести на девять учёток и признак.
- `test/rbac-roles.spec.ts` — новый: состав прав каждой роли, `owner` без
  `admin.*`, у каждой роли есть демо-учётка.
- `test/password-change.e2e.spec.ts` — новый: временный пароль, отказы, смена.
- `test/role-access.e2e.spec.ts` — новый: каждая роль получает 403 на чужом
  маршруте, а не только не видит пункта меню.
- `qa/roles-live` — новый прогон: вход ролью, окно смены пароля, состав меню.

## Открытые вопросы (вынести заказчику)

- Признак «пароль временный» на стенде **не поднят у `admin`**: это наш рабочий
  вход и вход десятка прогонов QA (`STAND_ADMIN_PASSWORD`, плюс жёстко
  прописанный `admin`/`admin123` в прогонах). Подняв его там, мы заперли бы
  автоматические проверки за паролем, которого никто не записывает. В сиде
  признак поднят у всех девяти — свежая установка ведёт себя ровно так, как
  просил заказчик.
- `sales` получил обе компании: демо-данные завода и торгового дома держат
  ответственного менеджера, и на одну учётку `sales` их больше не разложить.
  Разрез по компаниям показывают `owner1`/`owner2`, `master`, `worker`.

## Состояние на 06.10, вечер

Сделано и проверено:

- бэкенд: признак `must_change_password`, роль `owner`, `POST /auth/me/password`,
  сторож `@AllowTempPassword()`, выдача временного пароля при сбросе,
  демо-профиль из девяти учёток;
- фронт: экран `ChangePasswordScreen` вместо интерфейса, отбор разделов меню
  по правам (`lib/modules.ts` — одна таблица на сайдбар и `App.tsx`), показ
  выданного пароля один раз в очереди заявок;
- тесты: 1333 зелёных на 91 файле (было 1273/88), `npm run lint` чист в
  бэкенде и во фронте;
- прогон `qa/roles-live`: 100 проверок на четырёх проходах (1440 и 360,
  светлая и тёмная). Красный показан дважды: с выключенным экраном смены
  пароля прогон падает на ожидании `[data-screen="change-password"]`, с
  невыключенным отбором разделов — четырьмя «в меню чужие разделы».

Скрипт для стенда — `backend/scripts/rbac-stand-accounts.ts`. По умолчанию
только показывает план; пишет по `--apply`. `admin` не трогает без
`--admin-too`. Остальные учётки выключает, а не удаляет: на них висят журнал,
документы и ответственность в заказах.
