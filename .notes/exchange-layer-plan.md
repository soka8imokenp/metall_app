# Обменный слой для интеграций (ТЗ 12) — план и решения

Задача Отабека 06.10. Ветка `feature/frontend-import`, от `6a9afc9`.
Делается **универсальный каркас**. Конкретные коннекторы (1С, REGOS, банк,
телефония) не пишутся: ни доступов, ни документации — ТЗ 12 прямо говорит, что
состав каждой интеграции уточняется после их предоставления.

## Что уже есть в системе и что из этого годится

| Что | Где | Годится ли |
|---|---|---|
| Ключ внешней системы, вкл/выкл, список разрешённых адресов, счётчик обращений | `backend/src/crm/site-keys.service.ts` + `site_key` | **Да**, образец переиспользован целиком: тот же набор полей, тот же `withTenant` + сырой SQL, тот же `keyView` |
| Открытый маршрут приёма, частота, проверка Origin | `backend/src/public/public-leads.service.ts` | **Да** по форме: счётчик частоты в памяти процесса, `@Public()`, ответ без данных |
| Сырое тело запроса с пределом размера | `backend/src/main.ts` (`raw({limit:'21mb'})` на вложениях) | **Да**, тот же приём для вебхука и для загружаемого файла |
| Выгрузка таблицы в CSV/XLSX/PDF | `backend/src/common/{csv.ts,xlsx.ts,report-file.ts}` + `ReportTable` | **Да**, выгрузка номенклатуры собирает `ReportTable` и отдаёт через `sendReportFile` |
| Журнал действий как каталог событий системы | `backend/src/common/audit.ts` (`writeAudit`), `ACTIONS` в `src/admin/journal.service.ts` | **Да**, см. решение про события |
| Очередь уведомлений | `backend/src/notifications/` + `notification_outbox` | **Частично**, см. ниже |

### Почему `NotificationOutbox` переиспользуется только механикой доставки

Смотрел до того, как писать своё (`notifications.service.ts:175` `scan()`,
`:786` `pending()`, `:828` `markSent`, `:836` `markFailed`).

Годится — **форма доставки**: колонки `attempts`, `last_error`, `sent_at`,
предел `MAX_ATTEMPTS = 5`, пара `markSent`/`markFailed`, выборка «не отправлено
и попыток меньше предела». Повторено один в один, включая имена.

Не годится — **сама таблица и способ сбора**:

1. `notification_outbox.user_id NOT NULL` и уникальность
   `(user_id, kind, dedupe_key)`. Получатель уведомления — человек с Telegram,
   получатель вебхука — URL внешней системы. Человека там нет.
2. Это **не транзакционный outbox**, хотя `02-ARCHITECTURE.md` §8.1 его так
   называет. `scan()` — опрос базы по условиям (`financePending`,
   `stockCritical`, `stageOverdue`…), а не запись события доменным кодом.
   Подписки на события системы на этом не построить: условия зашиты в код.
3. Нарастающей задержки в ней нет вовсе: `pending()` отбирает по
   `attempts < MAX_ATTEMPTS`, и неудачная строка берётся снова на следующем же
   проходе. ТЗ по этой задаче требует нарастающую — добавлена колонка
   `next_attempt_at`, которой у уведомлений нет.

Вывод: доливать вебхуки в `notification_outbox` значило бы сломать её
уникальность и смысл колонки `user_id`. Таблица своя, механика — её.

### Спящая таблица `outbox_event` — не трогается, и это надо знать

В схеме с самого начала лежит `outbox_event` (`schema.prisma:2075`): `company_id`,
`event_type`, `payload`, `status`, `attempts`, `last_error`, `next_attempt_at`.
Это и есть транзакционный outbox из `02-ARCHITECTURE.md` §8.1. **В неё никто
никогда не писал и из неё никто не читает** — проверено: по всему `src/`,
`prisma/` и `test/` ни одного обращения, кроме сгенерированного клиента Prisma.
Рядом так же спит `idempotency_key`.

Очередь доставки на ней не строится: в ней нет **адресата**. Событие «заказ
отгружен» случилось один раз, а уйти должно трём подписчикам, каждому по своему
URL, со своим счётом попыток и своей последней ошибкой. Доливать в неё
`system_id`, `url`, `http_status` и тела запроса с ответом значит переписать её
целиком — то есть сделать `exchange_message`, только сломав по дороге то, что
описано в архитектуре.

Поэтому веер по подпискам идёт **той же транзакцией**, что и событие: на каждую
активную подписку своя строка `exchange_message`. Промежуточного шага нет —
он добавил бы второй счёт попыток на том же пути.

`outbox_event` и `idempotency_key` оставлены как есть: удалять таблицы из схемы
без спроса не моё решение. **Вопрос заказчику/на ревью:** либо их выпиливать,
либо писать в них — сейчас это мёртвый вес, который при чтении схемы выглядит
работающим механизмом.

## Решение: событие системы = запись журнала действий

Исходящий вебхук подписывается на событие вида `<сущность>.<действие>`
(`sales_order.ship`, `item.create`, `finance_operation.post`). Публикация
сделана **одним крючком в `writeAudit`**, а не вызовами из доменного кода.

Почему так:

- журнал действий уже есть везде, где меняется что-то значимое, и уже отобран
  по смыслу («журнал значимых действий», ТЗ 13.3). Второй список точек
  публикации разошёлся бы с ним на первой же правке;
- у каждого события уже есть название на двух языках (`ACTIONS`, `ENTITIES` в
  `journal.service.ts` и `AdminJournals.tsx`) — экран подписки не выдумывает
  подписи;
- запись идёт **той же транзакцией**, что и само изменение: откатилось — вебхук
  не уйдёт. Это и есть то свойство, ради которого в архитектуре заведён outbox;
- доменный код не тронут вовсе, значит и ломать в нём нечего.

Цена: один индексный `SELECT` по `webhook_subscription` на каждую запись
журнала. Кеша нет сознательно — кеш пришлось бы греть вне RLS, а
`webhook_subscription` закрыт политикой по компании.

Тело вебхука — `{event, entityType, entityId, action, changes, occurredAt}`.
Детали объект отдаёт по своему API, свой идентификатор внешняя система находит
в карте соответствий. Выгружать всю карточку в вебхук не нужно и вредно:
получатель должен спросить актуальное, а не поверить снимку.

## Таблицы (миграция `20261006160000_exchange_layer`)

Все четыре — под RLS `company_isolation` по образцу
`20261004210000_production_calendar`. Миграция под owner-URL.

1. **`external_system`** — справочник подключений.
   `code` (машинный, уникален в компании), `name`, `is_active`,
   `key_hash` + `key_tail`, `signing_secret`, `allowed_ips text[]`,
   `last_used_at`, `used_count`.
   - Ключ хранится как `sha256`, а не bcrypt: по нему нужен **поиск** на
     входящем запросе. Ключ — 24 знака из `randomBytes(18)`, перебирать там
     нечего, а bcrypt не даёт найти строку по значению.
   - `key_tail` — последние 6 знаков, только для узнавания на экране.
   - `signing_secret` лежит восстановимым: HMAC без него не посчитать.
     Наружу не отдаётся никогда, API возвращает только `hasSecret`.
     Шифрование на хранении не делается — ключа для ключа в проекте нет,
     это был бы перевод секрета из базы в тот же диск.
   - «Разрешённые адреса» здесь — **IP**, а не `Origin`: обмен серверный,
     браузера в нём нет.

2. **`exchange_message`** — одна таблица на три дела: очередь исходящих,
   защита от повтора входящих и журнал обменов.
   `direction` (`in`/`out`), `event`, `external_id`, `status`
   (`pending`/`done`/`failed`/`dead`), `attempts`, `next_attempt_at`,
   `last_error`, `request_body`, `response_body`, `http_status`,
   `created_at`, `processed_at`.
   - `UNIQUE (system_id, direction, external_id)` при непустом `external_id` —
     это и есть идемпотентность: повтор сообщения с тем же внешним
     идентификатором не создаёт второй записи.
   - Тела усечены до 4000 знаков на записи, а не на показе: иначе журнал за
     месяц съедает базу.
   - Отдельного журнала не делается: очередь и журнал — одно и то же, и
     вторая таблица рассходилась бы с первой.

3. **`external_ref`** — карта соответствий.
   `system_id`, `entity_type`, `external_id`, `internal_uid`.
   Два уникальных индекса, в обе стороны: `(system, type, external_id)` и
   `(system, type, internal_uid)`. Только первый — и наш объект мог бы получить
   два внешних кода, то есть ровно тот дубль, от которого карта и заводится.

4. **`webhook_subscription`** — подписка.
   `system_id`, `event`, `url`, `is_active`. `UNIQUE (system_id, event)`.
   Индекс `(company_id, event)` — под крючок в `writeAudit`.

## Маршруты

Административные — под `admin.users`, **новых прав не заводится**. Раздел
«Администрирование» целиком закрыт этим правом (`AdminView.tsx`: без
`admin.users` раздел не показывает ничего), и вкладка обменов стоит рядом с
журналами, за тем же замком. Своё право (`admin.integrations`) напрашивается
по смыслу, но заказчик отложил разделение ролей на конец проекта — завести его
сейчас значит раскроить права дважды. **На этап ролей вынесено как вопрос.**

| Маршрут | Что |
|---|---|
| `GET/POST/PATCH /exchange/systems` | справочник подключений; ключ показывается один раз в ответе на создание и на `POST .../key` |
| `GET/PUT/DELETE /exchange/systems/:uid/subscriptions` | подписки на события |
| `GET /exchange/events` | каталог событий с названиями ru/uz — для выпадающего списка |
| `GET /exchange/messages`, `POST /exchange/messages/:uid/retry` | журнал обменов и повтор кнопкой |
| `GET /exchange/refs` | карта соответствий |
| `GET /exchange/items/file?format=xlsx\|csv` | выгрузка номенклатуры |
| `POST /exchange/items/import?dryRun=` | загрузка файла, протокол по строкам |
| `POST /hooks/:code` | **входящий вебхук**, `@Public()`, ключ в `X-Exchange-Key` |

Предел тела: `raw({limit:'1mb'})` на `/api/v1/hooks` и `raw({limit:'6mb'})` на
`/api/v1/exchange/items/import` в `main.ts`. Сырое тело, а не JSON, по двум
причинам сразу: HMAC считается по тем самым байтам, которые пришли, а предел
должен объяснить себя ошибкой, а не обрывом соединения.

## Импорт номенклатуры: что именно проверяется по строке

Круг на номенклатуре — выгрузка и загрузка одним и тем же набором колонок.
Разбор CSV — зеркало `buildCsv` (`;`, BOM, десятичная запятая); XLSX читается
через `jszip` (уже в зависимостях, `buildXlsx` им же пишет).

Строка не применяется, если: нет кода или названия; неизвестная единица;
неизвестный вид позиции; минимальный уровень выше критического; код уже есть
в другой компании выборки; дубль кода внутри самого файла. Причина называется
по-человечески и с номером строки. Остальные строки при этом применяются —
файл не отвергается целиком из-за одной опечатки.
Существующая позиция обновляется, **но код при наличии движений не меняется** —
это правило уже стоит в `refs.service.ts` и обходить его импортом нельзя.
`dryRun=true` считает тот же протокол и ничего не пишет.

## Что сознательно не делается

- коннекторы 1С / REGOS / банк / телефония — нет доступов и документации (ТЗ 12);
- приём файлов обменом через S3/FTP-папку: способ обмена ни по одной системе не
  согласован, а каталог на диске — это уже решение за заказчика;
- шифрование `signing_secret` на хранении (см. выше);
- отдельное право на обмен (см. выше), решается на этапе разделения ролей.
