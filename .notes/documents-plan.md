# Документы (конструктор и реестр) — план до конца модуля

Правило заказчика (Отабек, 26.09, группа #318): **страница делается до конца** —
фронтенд, бэкенд, логика, и если для проверки нужны данные, они создаются
и проверяются в БД.

Источник требований — `docs/01-TZ.md` §7 (7.1–7.5), метка `[С]` — есть в
Спецификации договора. Вопросы к заказчику по модулю — `docs/09-CLIENT-INPUTS.md`.

В ТЗ модуль называется «Конструктор документов», в интерфейсе — пункт меню
«Документы». Это одно и то же и делается вместе: конструктор собирает документ
из шаблона, реестр его хранит, ищет, согласует и отдаёт файлом.

## Что уже есть в основании

- `document_type` — код, названия, **маска нумерации** (`{TYPE}-{YY}/{SEQ}`),
  область счётчика (`company` или `company_period`), выключение.
- `document` — номер, дата, контрагент, ссылка на источник
  (`source_doc_type` + `source_doc_id`), валюта, сумма, язык, статус
  (`draft`, `pending_approval`, `approved`, `signed`, `returned`, `cancelled`),
  `version`, автор. Уникальность номера — по компании и типу.
- `document_counter` — последний номер по компании, типу и периоду.
- `attachment.document_id` заведён ещё в складском Э7: API вложений к документу
  готов и проверен, на экране кнопки нет — потому что экрана нет.
- В посеве 240 документов (счёт и ТТН на последние 120 заказов продажи).

То есть хранилище номеров и статусов уже спроектировано. Нет кода, нет экрана
и нет того, из чего документ собирается.

## Чего нет и придётся завести

- **Шаблоны.** Таблицы нет вовсе. Нужен файл DOCX с плейсхолдерами, привязка к
  типу документа, компании и языку, версия и признак «опубликован».
- **Строки документа.** `document` держит только итоговую сумму. Табличной
  части нет, а она есть в каждой печатной форме.
- **Согласование и версии.** Статусы в перечислении есть, переходов между ними
  и журнала — нет. Версия документа как отдельная запись с файлами — нет.
- **Генерация файлов.** Ни DOCX, ни PDF в проекте не собирается: есть только
  `common/xlsx.ts` и `common/csv.ts` для отчётов.
- Модуля `backend/src/documents` нет; экран `DocumentsView.tsx` (149 строк) —
  на фикстуре `MOCK_DOCUMENTS`, таблица без единого живого запроса.

## Решения, принятые до кода

**1. Документ хранит снимок, а не ссылку на живой заказ.** Строки и реквизиты
копируются в документ в момент создания. Счёт, выставленный в марте, обязан
печататься мартовскими ценами и мартовским адресом, даже если в заказе потом
поменяли цену, а у клиента — банк. Ссылка на источник остаётся, но она для
перехода, а не для расчёта.

**2. PDF получается из того же DOCX, а не собирается отдельно.** Иначе
«скачал Word» и «распечатал PDF» рано или поздно покажут разные числа.
Преобразование — LibreOffice в headless-режиме (`soffice --convert-to pdf`),
он уже стоит на стенде (26.2.5.2). Это зависимость окружения: на боевом
сервере её надо будет поставить, и это инфраструктура, а не мой код.

**3. Шаблонизатор — `easy-template-x`** (MIT, 8.0.0 от 24.09.2026,
https://github.com/alonrbar/easy-template-x). Причины: лицензия без платных
модулей (у `docxtemplater` ядро MIT, а часть возможностей — платные
расширения), циклы и условия из коробки — это ровно табличная часть и строка
НДС из ТЗ 7.2, и есть перечисление плейсхолдеров прямо из файла. Последнее
нужно для требования «администратор сопоставляет плейсхолдеры с полями
системы»: без чтения тегов из файла сопоставлять было бы не с чем.

**4. Тип документа остаётся настраиваемым, а печатная форма — файлом.**
Заказчик меняет свои бумаги, не трогая код: загрузил новый шаблон — со
следующего документа печатается он, у прошлых остаётся тот, которым они
напечатаны.

## Этапы

### Э1. Реестр документов на живом API [закрыт 29.09]
- `GET /documents` — список с фильтрами: тип, статус, контрагент, период,
  поиск по номеру; серверная пагинация; счётчики по статусам над списком.
- `GET /documents/{uid}` — карточка: реквизиты, источник, вложения, автор.
- Экран «Документы» уходит с фикстур на живой API.
- Вложения на карточке — закрывает хвост складского Э7 («API готов, кнопку
  ставить некуда»).

Почему первым: экран перестаёт показывать выдуманные счета сразу, а всё
дальнейшее наращивается на уже работающем списке.

**Сделано.** `backend/src/documents/` (сервис, контроллер, модуль),
`backend/test/documents.e2e.spec.ts` — 13 проверок,
`frontend/src/components/modules/DocumentsView.tsx` переписан с нуля,
прогон `qa/documents-live/registry.mjs` на 1440 и 360 в двух темах.
Контракт — `docs/04-API-CONTRACT.md` §9.1.

Решения по ходу:

1. **Счётчики статусов считаются без выбранного статуса.** Они же вкладки-фильтр:
   разводить «сколько их» и «покажи их» на два элемента — это два действия вместо
   одного, а счётчик, пропадающий от нажатия на себя, просто врёт.
2. **Фильтр по типу — по коду, а не по uid.** Тип принадлежит компании, и в
   холдинге «Счёт» приходит дважды. Свели по коду; `typeUid` остался в API.
3. **Источник — ссылка, а не пересчёт.** Сумма и контрагент берутся из самого
   документа: счёт за март печатается мартовскими числами, что бы потом ни
   поменяли в заказе. В SQL это четыре явных `LEFT JOIN`, а не подстановка имени
   таблицы из `source_doc_type` — подставлять имя таблицы из данных нельзя.
4. **Кнопок под то, чего нет, не ставим.** Создания, согласования и печати на
   экране нет — они идут этапами Э2–Э6.
5. **Имя компании отдаёт сервер.** На карточке стояло «Компания plant»; словарь
   кодов на фронте не завели — компании в системе добавляет заказчик.

Грабли:

- **`document_type` был без `uid`** — третий раз тот же пробел после
  `lead_source`/`price_type` и `deal_stage`. Миграция
  `20260929210000_document_type_uid`. Заводя таблицу-справочник, сразу клади
  `uid`: наружу id не отдаём.
- **Экран не перечитывался при смене компании.** Переключатель меняет заголовок
  `X-Company-Id`, но перезапрос не вызывает: в холдинге оставался список
  торгового дома. `company` в зависимостях обоих `useEffect`. Сторож — круг
  «в холдинге документов больше, чем в торговом доме» в прогоне.
- **Одинаковые номера в холдинге.** Нумерация у каждой компании своя, и в списке
  подряд стояли два «ТТН-26/00003» с разными контрагентами. В режиме холдинга
  в строке стоит код компании.
- **На 360 фильтры сжались в огрызки**: поиск до «Ном», даты — до двух стрелок
  без подписи. До 640 точек каждый фильтр занимает строку целиком.
  Мерить это обрезкой текста бесполезно: у элемента с многоточием `scrollWidth`
  равен `clientWidth`, а замер ширины надписи по шрифту расходится на единицы
  точек. Проверяем правило вёрстки: фильтр не делит строку с соседом.
- **`CustomSelect` объявлял `role="listbox"`, а строки были без `role="option"`** —
  для скринридера список пуст. Починено в самом компоненте; остальные десять
  живых прогонов после этого зелёные.
- **Сид стенда идёт не от `.env`.** В `~/.config/systemd/user/metall-asia-stand.env`
  только `APP_DATABASE_URL`; миграция и сид стенда требуют `DATABASE_URL` ролью
  владельца на базу `metall_asia_stand`. Запущенный без него `npm run seed`
  пересевает базу разработки — что и произошло 29.09, вернул профилем `dev`.

### Э2. Типы документов и нумерация на запись [закрыт 29.09]
- `GET/POST/PATCH/DELETE /documents/types` по правилам складских и CRM
  справочников: использованный тип выключается, а не удаляется; правка,
  меняющая смысл записанного, отклоняется с объяснением.
- Маска нумерации с проверкой: без `{SEQ}` номер не уникален, такую маску не
  принимаем. Смена маски действует вперёд — уже выданные номера не
  переписываются, они напечатаны на бумаге.
- Выдача номера атомарна: `UPDATE ... RETURNING` под блокировкой строки
  счётчика внутри транзакции создания. Проверка — два одновременных создания
  не получают один номер (ТЗ 7.3).

**Сделано.** `backend/src/documents/numbering.ts` (разбор маски),
`numbering.service.ts` (выдача номера), `types.service.ts` (справочник),
`backend/test/documents-types.e2e.spec.ts` — 15 проверок,
`frontend/src/components/modules/DocumentTypes.tsx` — вкладка «Типы документов»
на экране «Документы», прогон `qa/documents-live/types.mjs`.
Контракт — `docs/04-API-CONTRACT.md` §9.2.

Решения по ходу:

1. **Периодический счётчик без года в маске отклоняется.** Он обнулится в
   январе, а в номере этого не видно — повторится номер прошлого года. Это
   единственное правило, связывающее маску и область счётчика; остальные
   сочетания разрешены.
2. **Ключ периода считается по маске, а не отдельной настройкой.** Есть `{MM}` —
   счётчик помесячный, иначе годовой. Две настройки рядом рано или поздно
   разошлись бы: месяц в номере, а счётчик годовой — и в феврале номер
   повторится.
3. **Пример номера считает сервер, а не форма.** Разбирать маску в двух местах
   значит однажды показать в подсказке одно, а напечатать другое.
4. **Заморожены код и область счётчика, маска — нет.** Код уходит в номер через
   `{TYPE}`, область счётчика задаёт, с какого числа начнётся период. Маска
   действует вперёд: выданные номера напечатаны на бумаге и названы в договорах.
5. **Правила «нельзя выключить последний тип» не завожу.** У складских и CRM
   справочников она есть потому, что форма не примет запись без источника,
   причины, типа задачи. Здесь такой формы нет: выключив все типы, заказчик
   просто не сможет создать документ, и это обратимо одним нажатием.

Грабли:

- **`uid` у `document_type` без умолчания в базе.** Миграция Э1 добавила
  колонку с разовым заполнением, а `DEFAULT` не поставила, и сырая вставка
  падала на `NOT NULL`. Соседние справочники CRM пишут `gen_random_uuid()`
  прямо во вставке — сделал так же, это уже принятый в проекте способ.
- **Заведённый тип не появлялся в фильтре реестра.** Справочник правят на
  соседней вкладке того же экрана, а список типов читался один раз при
  монтировании. Выглядело так, будто тип не сохранился. `tab` в зависимостях.
- **Форма правки обещала «СЧ-26/00001»**, когда следующий номер — 00072:
  пример считался от единицы, без счётчика типа. Теперь `sample` принимает
  `typeUid` и считает от счётчика, ничего не занимая.
- **Проверил и снимаю своё же предположение:** посев счётчики пишет
  (`document_counter`, ключ периода `2026`), и они сходятся с выданными
  номерами. Сторож на это есть отдельной проверкой.

### Э3. Создание документа из источника [закрыт 30.09]
- `POST /documents` из заказа продажи, сделки, клиента, платежа,
  производственного задания или складской операции.
- Новая таблица строк документа: позиция, количество, единица, цена, сумма,
  НДС — снимком на момент создания (решение 1).
- Автоподстановка реквизитов компании и контрагента, суммы прописью,
  сроков и условий оплаты (ТЗ 7.1).
- Связь в обе стороны: документ виден в карточке источника, из документа —
  переход к источнику в один клик. Вкладка «Документы» в карточке клиента
  (CRM Э5) сейчас только читает готовое — наполняется здесь.

**Сделано.** Миграция `20260930090000_document_lines` (таблица `document_line`
с RLS, `document.amount_net/amount_vat/requisites`),
`backend/src/documents/{from-source.service.ts,amount-words.ts}`,
`POST /documents/from-source`, `GET /documents/sources`,
`backend/test/documents-from-source.e2e.spec.ts` — 16 проверок,
`backend/test/amount-words.spec.ts` — 13, форма «Выписать документ» и
табличная часть с реквизитами на карточке, прогон `qa/documents-live/issue.mjs`.
Контракт — `docs/04-API-CONTRACT.md` §9.3.

Решения по ходу:

1. **Строки — снимок текстом, а не ссылки.** Название и единица лежат в самой
   строке документа: переименовали позицию — в выписанном счёте остаётся то
   название, по которому её приняли. `item_id` оставлен для перехода к
   карточке, печать на него не смотрит.
2. **Реквизиты — JSON.** Состав у договора, счёта и накладной разный и будет
   дополняться под образцы заказчика. Колонка на каждый реквизит означала бы
   миграцию на каждую новую печатную форму.
3. **Суммы заказа не пересчитываются**, суммы отгрузки и производства —
   считаются. У заказа они уже посчитаны и проверены, и свой пересчёт однажды
   напечатал бы в счёте не то, что стоит в заказе. У отгрузки есть только
   количество и цена строки заказа — итог складывается здесь.
4. **Шесть источников написаны шестью запросами.** `source_doc_type` хранит имя
   таблицы, и собрать `FROM ${kind}` из данных было бы дырой.
5. **Удаления документа нет и не будет.** Номер выдан; такой документ отменяют
   статусом — это Э6.

Грабли:

- **«Тийин» склоняется**: род. мн. — «тийинов» (Викисловарь). Первая версия
  проверки ждала несклоняемое «тийин» — ошибка была в проверке, не в коде.
- **Шапка карточки округляла сумму до целых**, а рядом стояла та же сумма
  прописью с копейками: 179 256 090 против «…089,59». В списке округление
  уместно, в документе — это расхождение в реквизите. В карточке показываем
  две цифры после запятой.
- **Модальные окна не были объявлены диалогом** — для скринридера список под
  окном оставался частью той же страницы. `role="dialog"` и `aria-modal`
  добавлены обоим окнам модуля.
- **Проверка «неудачное создание не тратит номер» была тривиальной**: источник
  читается раньше выдачи номера, и счётчика она не касалась вовсе. Переписана
  честно (сторожит порядок действий), а откат транзакции проверяется отдельно —
  номер, взятый в упавшей транзакции, возвращается счётчику.
- **Прогон оставляет на стенде четыре черновика за запуск** — удалять их
  нечем и не нужно: выданный номер не исчезает. Убирает пересев.

### Э4. Шаблоны и сборка DOCX [закрыт 30.09]
- Таблица шаблонов: тип документа, компания, язык, файл, версия, опубликован.
  Русская и узбекская версии — два файла, как требует ТЗ 7.2.
- Загрузка шаблона, чтение списка плейсхолдеров из файла, сопоставление с
  полями системы, проверка на тестовой записи **до** публикации.
- `GET /documents/{uid}/file?format=docx` — сборка по опубликованному шаблону.
- Наши черновые шаблоны на четыре формы: счёт, накладная, КП, акт. Когда
  придут образцы заказчика — загружаются как файлы, код не меняется.

**Сделано.** Сборка — `easy-template-x` 8.0.0 (MIT, ESM, node ≥ 20). Контракт
и правила — `docs/04-API-CONTRACT.md` §9.4. Экран — вкладка «Шаблоны» в
разделе «Документы», кнопка «Скачать DOCX» в карточке.

Три вещи, которые стоит помнить дальше:

1. **Имена полей плоские, хотя и с точкой.** `{doc.number}` движок ищет как
   ключ `doc.number`, а не как путь в объекте — проверено на живом файле, не
   по документации. Данные собираются плоскими (`render.service.ts`).
2. **Публикация проверяет сборку на настоящем документе.** Не на выдуманном:
   шаблон, проверенный на пустых значениях, скроет ровно ту ошибку, ради
   которой проверка и нужна. Нет ни одного документа этого типа — проверять
   не на чем, и об этом говорится прямо.
3. **`document.template_id` пришивает документ к форме после первой печати.**
   Без этого «перепечатай мартовский счёт» давало бы сентябрьскую бумагу.

Черновиков четыре, но не тех, что в плане: КП в справочнике типов нет, вместо
него спецификация к договору (SPEC) — те же позиции с ценами. Заведут тип КП —
загрузят в него файл, код не изменится.

Не закрыто здесь и ждёт заказчика: сами формы до образцов МЕТАЛЛ АЗИЯ,
ЭЦП, отправка документа почтой и в Telegram.

### Э5. PDF и печатные формы [закрыт 30.09]
- `GET /documents/{uid}/file?format=pdf` — преобразование собранного DOCX
  (решение 2). Файл кладётся в хранилище вложений и привязывается к документу,
  повторное скачивание не пересобирает его заново.
- Здесь же закрывается хвост складского Э6б: печатная форма PDF для отчётов
  идёт тем же трактом.
- Проверять придётся не «файл скачался», а что в нём: кириллица и узбекская
  латиница, разряды в суммах, табличная часть целиком.

**Сделано.** LibreOffice 26.2 в безголовом режиме, `SOFFICE_BIN` и
`SOFFICE_TIMEOUT_MS`. Контракт — `docs/04-API-CONTRACT.md` §9.5. На экране:
в карточке документа кнопки DOCX и PDF, в отчётах склада и CRM — третья
кнопка «PDF».

Что стоит помнить дальше:

1. **Таблица в собранном DOCX разъезжалась в PDF.** От табличной части счёта
   оставались «№» и «Наименование», остальные шесть колонок LibreOffice терял.
   В XML все ячейки были на месте — дефект видно только на бумаге. Чинит пара:
   кегль под содержимое и заданные ширины колонок. Обе половины проверены
   ломкой по отдельности.
2. **Проверка сначала была пустой.** Она брала документ на одну строку, а у
   такого итог по строке совпадает с итогом документа и печатается под
   таблицей — «последняя колонка на месте» проходило на пустой таблице.
   Теперь источник обязательно на несколько строк, и сверяется шапка таблицы:
   эти слова встречаются только в ней.
3. **`pdftotext -layout` читает страницу построчно.** Перенос внутри ячейки
   раскидывает её содержимое между числами соседних колонок, поэтому сверять
   нужно по словам, а не целой строкой.
4. **Знак `to‘lov` в системе — U+2018, а узбекский стандарт требует U+02BB.**
   До бумаги знак доходит, и проверка это держит. Менять его надо во всех
   тридцати файлах разом и по решению заказчика, а не молча в одном.

### Э6. Согласование, версии, журнал [закрыт 30.09]
- Маршрут ТЗ 7.4: черновик → на согласовании → утверждён → подписан, с
  возвратом и отменой. Возврат и отмена требуют причины — как отказ по
  обращению и проигрыш сделки в CRM. Причина стоит рядом со статусом на
  карточке: её читает тот, кто переделывает, и в журнал он не пойдёт.
- Правка утверждённого заводит новую редакцию: прежняя уходит в
  `document_version` целиком (строки, реквизиты, суммы, шаблон, готовый PDF),
  документ получает версию +1 и возвращается в черновик. Согласующий смотрел
  не эти цифры.
- Журнал — тот же `audit_log`, что история карточки клиента, в одной
  транзакции с изменением и защищён триггером от правки.
- Право на согласование отдельно от права на создание: у «Менеджера по
  продажам» его нет, кнопок утверждения он не видит. Своё отменить может.
- Какие действия доступны, решает сервер (`actions` в карточке). Второй
  перечень правил на фронте однажды разошёлся бы с серверным.

Что нашлось и починено по ходу:

1. **Суммы документа считались с долями тийина.** 3 × 0,3333 давало в цифрах
   1,00, а прописью «99 тийинов»: цифры округляются, а сумма прописью берёт
   два знака как есть. Теперь округление стоит до записи, в `replaceLines`.
2. **Список редакций предлагал скачать то, чего нет.** Шаблон закрепляется на
   документе первой удачной печатью; у редакции, которую не печатали, его нет,
   и кнопка возвращала бы `409`. Сервер отдаёт `hasTemplate`, экран показывает
   кнопку только там, где файл есть чем собрать.
3. **Форма правки на 360 уезжала вбок** строкой итогов с `whitespace-nowrap`,
   а числа приходили в поля сырыми из базы («12.0000»). Итоги переносятся по
   частям, хвост нулей снимается, запятая принимается наравне с точкой.
4. **Подписи статусов лежали в двух местах** — в реестре и в блоке
   согласования. Сведены в `document-status.ts`: один экран называл бы
   документ утверждённым, другой подписанным.

Грабли прогона (`qa/documents-live/workflow.mjs`):

1. **Имя роли в Playwright ищется подстрокой.** `{ name: 'Вернуть' }` ловит
   ещё и «Свернуть или развернуть боковую панель». Кнопки маршрута — только
   `exact: true`.
2. **Сырой `fetch` из прогона идёт без `X-Company-Id`,** то есть по всему
   холдингу, а номера у компаний свои. Прогон брал «ТТН-26/00007» завода и
   открывал в реестре торгового дома другой документ с тем же номером.
   Документ выбирается на самом экране.
3. **`\w` в JS не матчит кириллицу.** `/нов\w+ редакци/` не находило
   «новую редакцию», и проверка предупреждения молча проходила.
4. **Падение внутри хода уносило уже найденное.** Ход обёрнут в перехват:
   один таймаут прятал весь список расхождений.

## Что в модуле не закрывается моим кодом

- **Сами формы.** «Точный перечень форм и обязательных полей определяется
  после получения образцов действующих документов заказчика» — это записано в
  Спецификации. До образцов формы наши, черновые.
- **LibreOffice на боевом сервере** — инфраструктура.
- **Электронная подпись.** В ТЗ есть статус «подписан», но чем подписывают, не
  сказано. Если нужна ЭЦП — нужен провайдер и его документация.
- **Отправка документа клиенту** (почта, Telegram) — общий тракт уведомлений.
