## 1. Приёмка архива с фронтендом

Первое, что делаю после получения zip — не пишу код, а проверяю, с чем имею дело:

1. Запускаю проект на моках: собирается ли, работает ли.
2. Снимаю фактический перечень запросов, которые делает фронт: пути, методы,
   тела, заголовки. Сверяю с `04-API-CONTRACT.md`.
3. Составляю таблицу расхождений: что фронт ждёт иначе, чего в контракте нет,
   что в контракте есть, а фронт не использует.
4. Решаю по каждому расхождению: подстроить бэкенд или править фронт.
   Правка фронта — отдельная договорённость с Тагиром, не молча.
5. Проверяю, что слой доступа к данным изолирован: замена моков на реальный
   адрес не требует правок в компонентах. Если требует — это первая задача.

Результат приёмки — документ `07-FRONTEND-HANDOVER.md` со списком расхождений
и решением по каждому. Без него начинать бэкенд бессмысленно: половина работы
уйдёт на подгонку вслепую.

## 3. Сквозные механизмы

Делаются первыми, до бизнес-модулей — потому что каждый модуль на них опирается.

### 3.1. Контекст запроса

Перехватчик достаёт пользователя из токена, компанию из `X-Company-Id`,
проверяет доступ пользователя к этой компании и открывает транзакцию с
установкой переменных сессии PostgreSQL:

```sql
SET LOCAL app.user_id = ...;
SET LOCAL app.company_ids = ...;
```

Без этого RLS не работает. Поэтому установка контекста — не в сервисах,
а в одном месте на входе, и её отсутствие должно ронять запрос, а не молча
отдавать пустой список.

### 3.2. Права

Декоратор `@RequirePermission('sales.order.create')` на методе контроллера плюс
проверка области видимости в репозитории. Матрица прав — в БД, кэш в Redis
с инвалидацией при изменении роли.

Ответы объектов дополняются полем `permissions` — что доступно по этой записи.
Считается одним проходом, не запросом на каждую строку списка.

### 3.3. Идемпотентность

Перехватчик на изменяющих методах: по `Idempotency-Key` + хэш тела ищет
сохранённый ответ. Найден — возвращает его. Не найден — выполняет, сохраняет
ответ, отдаёт. Другое тело с тем же ключом — `409`.

### 3.4. Оптимистическая блокировка

Поле `version` на изменяемых сущностях, `UPDATE ... WHERE version = $1`.
Ноль затронутых строк → `409` с текущим состоянием.

### 3.5. Обработка ошибок

Единый фильтр: доменные исключения → коды из `04-API-CONTRACT.md`, тексты
на языке из `Accept-Language`, `requestId` в каждом ответе. Технические
подробности — только в лог, не пользователю.

### 3.6. Outbox

Событие пишется в таблицу в одной транзакции с изменением. Обработчик BullMQ
читает и доставляет: Telegram, push, вебхуки, пересчёты. Повтор с нарастающей
задержкой, после N неудач — «мёртвая» очередь и сигнал администратору.

## 5. Бизнес-логика, требующая точности

Места, где ошибка стоит дороже всего. Каждое покрывается тестами до реализации.

### 5.1. Списание партий (FIFO)

```
подобрать партии по дате прихода
  → заблокировать строки партий (SELECT ... FOR UPDATE)
  → проверить достаточность доступного
  → списать, посчитав стоимость по каждой партии
  → записать движения и обновить агрегат остатков
всё в одной транзакции
```

Блокировка обязательна: без неё две параллельные отгрузки заберут одну партию
дважды и остаток уйдёт в минус.

### 5.2. Резервирование

Резерв проверяет `qty_available`, а не `qty_on_hand`. Ограничение в БД
`qty_reserved <= qty_on_hand` — последняя линия защиты, на которую нельзя
полагаться как на основную, но без которой нельзя.

### 5.3. Себестоимость производственного заказа

```
материалы (фактический расход × стоимость партий)
+ полуфабрикаты (по их себестоимости)
+ прямые затраты заказа
+ затраты дочерних заказов на переделку
= себестоимость заказа
себестоимость единицы = себестоимость заказа / количество годного выпуска
```

Брак не уменьшает базу: его стоимость остаётся в заказе и удорожает годную
продукцию. Расчёт сохраняется снимком; пересчёт создаёт новую запись, не
затирая прежнюю.

### 5.4. Маржа заказа продажи

Выручка и себестоимость фиксируются в момент отгрузки. Последующие приходы
по другим ценам не меняют уже посчитанную маржу — иначе отчёт за закрытый
месяц перестаёт быть воспроизводимым.

### 5.5. Двойная запись

Каждая финансовая операция порождает сбалансированный набор проводок.
Отложенное ограничение в БД проверяет `SUM(debit) = SUM(credit)` на момент
фиксации транзакции. Проведённая операция не редактируется — только сторно.

### 5.6. Пересчёт единиц измерения

Металлопрокат учитывается в тоннах, метрах и штуках одновременно. Коэффициент
хранится у позиции (вес метра зависит от типоразмера). Движения пишутся в
базовой единице; ввод и отображение — в выбранной. Округление — только при
отображении, никогда при хранении.

### 5.7. Нумерация документов

`UPDATE document_counter SET last_number = last_number + 1 ... RETURNING` под
блокировкой строки, в транзакции создания документа. Два одновременных
создания не получат один номер.

### 5.8. Потребность в закупке

```
дефицит = минимальный уровень
        + активные резервы
        + плановый расход по запущенным производственным заказам
        − доступный остаток
```

Без учёта резервов и планового расхода цифра врёт в меньшую сторону, и закупка
приходит позже, чем нужна.

## 6. Telegram-бот

Один бот, меню собирается по правам пользователя (решение принято в
`01-TZ.md` §11 на основании формулировки Спецификации).

- Привязка аккаунта одноразовым кодом из веб-интерфейса; номер телефона как
  идентификатор не используется.
- Перед каждой командой — проверка права и области видимости, как в API.
- Сценарии: задания производства и смена статуса, запрос остатков,
  подтверждение складских операций, приём фото чека с созданием черновика
  расхода, согласование документов и платежей, сводка руководителя.
- Все действия пишутся в общий `audit_log` с источником `bot`.
- Уведомления идут через тот же outbox, что и остальные каналы.

## 7. Мобильное приложение

ОТКРЫТО: Expo или PWA — решение Артёма.

Требования к бэкенду независимо от выбора:

- компактные ответы для мобильных списков (курсорная пагинация);
- эндпоинты «мои задания», «мои заказы», «мои задачи» — без клиентской фильтрации;
- приём операций из offline-очереди с `Idempotency-Key` — повтор не создаёт
  вторую операцию;
- загрузка фото по частям с докачкой;
- push-уведомления через тот же outbox;
- `GET /warehouse/scan?code=` как единая точка разбора отсканированного кода.

## 8. Интеграции

Обменный слой делается один раз, коннекторы подключаются по мере появления
доступа. Ни одна интеграция не находится на критическом пути пользовательской
операции.

| Система | Что нужно от заказчика | Статус |
|---|---|---|
| 1С | версия, конфигурация, способ обмена (HTTP-сервисы, файлы, COM), перечень объектов | ОТКРЫТО |
| REGOS | документация API или формат выгрузки, доступ | ОТКРЫТО |
| Банк | банк, формат выписки, способ получения | ОТКРЫТО |
| Телефония | провайдер, API, вебхуки, доступ к записям | ОТКРЫТО |
| Сайт и реклама | формы, источники, способ передачи заявок | ОТКРЫТО |

Обязательная часть каждого коннектора: сопоставление идентификаторов
(`external_id_map`), журнал обменов с возможностью повтора, идемпотентность
по внешнему id.

## 9. Тестирование

| Уровень | Что |
|---|---|
| Юниты | FIFO, себестоимость, маржа, НДС, пересчёт единиц, KPI, нумерация |
| Интеграционные | сквозной сценарий на реальной БД: заказ → резерв → производство → выпуск → отгрузка → оплата → маржа |
| Контрактные | ответы против схем `packages/contracts` |
| Параллельность | одновременные отгрузки одной партии, двойное проведение платежа, гонка за номером |
| Права | каждая роль против каждого эндпоинта + попытки доступа к чужой компании |
| Нагрузка | 1 млн движений, 100 тыс. позиций остатков: списки и отчёты в заявленных рамках |
| Приёмочные | контрольные примеры заказчика — ОТКРЫТО, ждём |

Порядок по каждому расчёту: сначала падающая проверка, потом реализация,
потом подтверждение, что проверка проходит, и обратная проверка, что сломанная
реализация снова её роняет.

- Миграции накатываются при старте, откат предусмотрен.
