# 08. Внешний стенд

Как поднять стенд, который смотрит наружу, и чем он отличается от стенда
разработки. Решение о самом стенде и домене — за владельцем флота; здесь только
техническая часть.

## Что стенд — не прод

По договору сервер и домен под рабочую систему — за счёт заказчика, физически
в Узбекистане: это требование по персональным данным. Стенд на нашем домене
служит одному: показать ход работ. Отсюда два правила, которые нельзя обойти
удобством.

1. **Данных заказчика на стенде нет.** Ни названий контрагентов, ни ИНН,
   ни ФИО, ни телефонов, ни банковских реквизитов. Стенд наполняется профилем
   `demo` (см. ниже), и это проверяется тестом, а не обещанием.
2. **Ссылка должна быть закрыта.** Cloudflare Access или basic-auth: даже
   демонстрационные данные показывают структуру бизнеса.

   **Сейчас это не выполнено.** Стенд `https://metall-asia.cloudplus.uz`
   поднят и открыт по адресу: закрывает только вход в приложение. У нашего
   токена Cloudflare нет области Zero Trust, поэтому Access включить нечем;
   basic-auth поверх nginx ставится за минуты, но тогда показывающему нужно
   называть два пароля. Вопрос у Артёма, решение его. До решения: стенд
   открыт по адресу и закрыт по данным — клиентских данных там нет, всё демо.

## Профили сида

`backend/prisma/seed-profiles.ts` держит два набора опознавательных данных.
Структура — номенклатура, склады, движения, заказы, суммы — у них общая, разница
только в том, по чему можно узнать живую фирму и живого человека.

| | `dev` | `demo` |
|---|---|---|
| Где | локальная разработка | внешний стенд |
| Компании | настоящие названия и ИНН | те же бренды с пометкой «(демо)», ИНН с ведущим нулём |
| Контрагенты | правдоподобные названия | «Демо Строй Альфа» и подобные |
| Пользователи | ФИО | должности: «Директор (демо)» |
| Почта | `@metall-asia.uz` | `@demo.invalid` (RFC 2606, не делегируется) |
| Телефоны | `+9989…` | `+99800…`, кода оператора `00` не существует |
| Пароль | общий, из `SEED_PASSWORD` | случайный на каждый прогон, печатается один раз |

Выбор — переменной `SEED_PROFILE`, по умолчанию `dev`. Незнакомое значение
останавливает сид, а не откатывается к `dev` молча.

Правило держит `backend/test/seed-profiles.spec.ts`: он сверяет профили между
собой и падает, если в `demo` появится хоть один идентификатор из `dev`.

## Порядок развёртывания

### 1. База

```bash
cd backend
docker compose up -d                 # postgres:18, том metall-asia-pgdata
./scripts/db-bootstrap.sh            # роли metall_owner и metall_app
```

Пароли ролей — файлы `600` в `~/.local/state/openclaw/secrets/`, в compose и в
git их нет. Порт публикуется только на петлевой интерфейс.

### 2. Схема и данные

```bash
npm run prisma:deploy                          # миграции ролью владельца
SEED_PROFILE=demo npx tsx prisma/seed.ts       # демонстрационные данные
```

Сид напечатает пароль и список логинов **один раз**. Сохраните сразу: второй
раз его не покажет никто, потерялся — прогоняйте сид заново.

### 3. Бэкенд

```bash
npm run build      # tsc -p tsconfig.json; nest build с TypeScript 7 не работает
npm run start      # node dist/main.js
```

Переменные:

| | |
|---|---|
| `DATABASE_URL` | роль владельца, **только** миграции и сид |
| `APP_DATABASE_URL` | рабочая роль `metall_app`, без BYPASSRLS — ею ходит сервис |
| `JWT_SECRET_FILE` | путь к файлу с секретом, права 600 |
| `PORT` | по умолчанию 4000 |
| `CORS_ORIGINS` | **не нужен**, если фронт и API на одном адресе |
| `PUSH_SCHEDULER` | `off` — не рассылать push на телефоны. По умолчанию включено: раз в минуту процесс API собирает уведомления и шлёт их через службу Expo (контракт §14.30). Бот push не шлёт — только API |

### 4. Фронт

```bash
cd frontend
bun install --frozen-lockfile
bun run build:stand                  # VITE_USE_MOCKS=false, VITE_API_URL=/api/v1
```

Статика — `frontend/dist`, отдаётся как SPA: любой неизвестный путь возвращает
`index.html`.

### 5. Внешний вход

Один хост, `/api/v1` проксируется на бэкенд. Так фронт и API оказываются на
одном источнике, и CORS не участвует вовсе — одной поверхностью меньше.

```
https://<хост>/            → frontend/dist (SPA)
https://<хост>/api/v1/...  → http://127.0.0.1:4000/api/v1/...
```

Прокси обязан сохранять путь и переносить заголовки: авторизация ходит в
`Authorization`, а видимость компаний — в `X-Company-Id`.

## Проверка

```bash
cd qa && node stand-smoke/run.mjs
```

Тот же прогон против поднятого стенда — ничего не поднимает, только проверяет:

```bash
STAND_URL=https://metall-asia.cloudplus.uz \
STAND_LOGIN=director \
STAND_PASSWORD_FILE=~/.local/state/openclaw/secrets/metall-asia-stand-demo-password \
STAND_ALLOWED_ORIGINS=https://static.cloudflareinsights.com \
node stand-smoke/run.mjs
```

Пароль читается из файла `600` и в вывод не попадает; в файле должно лежать
одно значение, иначе прогон скажет об этом прямо. Чужие адреса в запросах —
ошибка по умолчанию: `STAND_ALLOWED_ORIGINS` разрешает их поимённо. Сейчас там
нужен beacon аналитики, который Cloudflare вставляет в страницу сам.

Прогон повторяет топологию стенда: поднимает бэкенд, ставит перед ним прокси на
одном порту, открывает собранный фронт на 1440 и 360, входит, открывает дашборд
и продажи, переключает компанию на завод и открывает производство,
перезагружает страницу. Падает, если хоть один запрос ушёл мимо адреса стенда,
если на экране входа осталось предупреждение о моках, если список продаж или
цеховых заказов пуст, если в журнале этапов нет событий или если перезагрузка
выбрасывает на вход.

Компанию прогон переключает тем же переключателем, что и человек: цех есть
только у завода, и под торговым домом производство пусто по праву.

Прогон проверен обратно: собранный обычным `bun run build` фронт его валит с
сообщением `запросы мимо стенда: http://127.0.0.1:4000`.

## Чего на стенде пока нет

- На фикстурах не осталось ни одного экрана из меню: «Дашборд», «Продажи»,
  «Склад», «Производство», «Финансы», «Документы» и CRM ходят в API.
- Записи нет в «Документах»: реестр читает, создание и согласование идут
  этапами Э2–Э6 (`.notes/documents-plan.md`). Кнопок под них на экране нет —
  экран не обещает того, чего не делает.

## Грабля: пересев меняет uid компаний

Пересев данных пересоздаёт компании, и их `uid` становятся другими. Открытая
с прошлого раза вкладка держит прежние в `sessionStorage`: токен ещё годен,
а заголовок `X-Company-Id` указывает на компанию, которой больше нет, — сервер
отвечает 403 «Нет доступа к указанной компании».

Снаружи это выглядит обманчиво: при выборе одной компании экран пишет
«Показатели не загрузились», а при «всех» работает — в режиме холдинга
заголовок не отправляется вовсе.

Лечится не перелогином руками: при восстановлении сессии фронт перечитывает
состав компаний и права через `GET /auth/me`
(`frontend/src/context/AuthContext.tsx`), а сохранённой сессии верит только
в части токена. Сторож — круг «старые uid компаний» в `qa/login-live`.

## Грабля: сборка стенда только `build:stand`

29.09 стенд отвечал «Сервер недоступен. Проверьте, что бэкенд запущен.» —
в `frontend/dist` лежала сборка, сделанная обычным `bun run build`. Он берёт
`frontend/.env.local`, где для разработки стоит
`VITE_API_URL=http://127.0.0.1:4000/api/v1`, и адрес попадает в бандл: браузер
посетителя стучится в свой же localhost, запрос гибнет на CORS
(«loopback address space»), фронт показывает «Сервер недоступен».

Для стенда собирать только `bun run build:stand` — он передаёт `VITE_API_URL=/api/v1`
переменной окружения, а она у Vite старше `.env`-файлов. Проверка: в
`dist/assets/*.js` не должно встречаться `127.0.0.1:4000`.

Второе на том же разборе: в файле
`~/.local/state/openclaw/secrets/metall-asia-stand-demo-login` лежал весь вывод
сида (21 строка) вместо одного логина — прогон подставлял его в поле входа и
получал 401. В файле должен быть один логин, `director`.

## Грабля: сид стенда идёт не от `.env`

В `~/.config/systemd/user/metall-asia-stand.env` лежит только
`APP_DATABASE_URL` — рабочая роль. Миграции и сид ходят ролью владельца
переменной `DATABASE_URL`, а её там нет: `npm run seed` без явного указания
возьмёт `backend/.env`, то есть **базу разработки**. 29.09 так и вышло — база
разработки уехала на профиль `demo`, вернул повторным сидом.

Стенд мигрируется и сеется так (база `metall_asia_stand`, роль владельца та же,
что и в разработке):

```bash
cd backend
OWNER=$(node -e '…подставить имя базы metall_asia_stand в DATABASE_URL из .env…')
DATABASE_URL="$OWNER" npx prisma migrate deploy
DATABASE_URL="$OWNER" SEED_PROFILE=demo npx tsx prisma/seed.ts
```

## Пароли демо-учёток: «название роли + 123»

Все девять учёток профиля `demo` входят по правилу **название роли + 123**, без
исключений — включая `admin` (`admin123`). Хвостовой номер в логине на пароль не
влияет: `owner1` и `owner2` — два человека на одной роли, у обоих `owner123`.
У логинов без номера правило совпадает с «логин + 123»: `director123`,
`sales123`, `warehouse123`.

Правило задано в одном месте — `backend/src/common/default-password.ts`, функция
`defaultPasswordFor`. Оттуда его берут сид (`prisma/seed-profiles.ts`), сервер
(`auth.service.ts` — чтобы такой пароль нельзя было поставить себе «новым»),
разовый скрипт учёток стенда (`scripts/rbac-stand-accounts.ts`) и прогон
`qa/roles-live`. Руками правило нигде не переписываем: 06.10 оно уже разъехалось
(сид выдавал `owner1123`, заказчик просил `owner123`), и прогон этого не замечал,
потому что проверял свою копию.

Каждая из девяти учёток заведена с признаком `must_change_password`: первым входом
человек обязан сменить пароль, до этого сервер отвечает `PASSWORD_CHANGE_REQUIRED`
на все маршруты, кроме смены пароля. Значит и прогоны, которые ходят на стенд
учёткой из этого списка, после первого живого входа работать перестанут — им
нужна своя учётка.

Случайный пароль профиля сид всё ещё печатает строкой «пароль у всех, кроме
названных ниже», но **не подходит ни к одной учётке**: своё значение есть у
каждой. 02.10 на этом потерян час — пароль из той строки сохранили в файл и
получили 401 на стенде. Ловить это нужно сверкой с хешем в базе, а не глазами:

```bash
node -e 'const b=require("bcryptjs"),{Client}=require("pg"),fs=require("fs");
const p=fs.readFileSync(process.env.HOME+"/.local/state/openclaw/secrets/metall-asia-stand-demo-password","utf8");
(async()=>{const c=new Client({connectionString:process.argv[1]});await c.connect();
const r=await c.query("SELECT password_hash FROM user_account WHERE login=\x27director\x27");
console.log("подходит:", await b.compare(p, r.rows[0].password_hash)); await c.end();})()' "$OWNER"
```

В файле `600`
`~/.local/state/openclaw/secrets/metall-asia-stand-demo-password` — одно
значение, пароль `director`: прогон `stand-smoke` подставляет его в поле входа
целиком. В чат и в вывод пароль не копируем.

## LibreOffice для PDF

Печатная форма PDF и выгрузка отчётов в PDF собираются внешней программой:
DOCX отдаётся LibreOffice в безголовом режиме. Без неё эти маршруты отвечают
`503` со словами, что поставить, — остальная система работает.

```bash
soffice --version          # на cloudplus-an стоит 26.2.5.2
which pdftotext            # нужен прогону qa/documents-live/pdf.mjs
```

| Переменная | Зачем |
|---|---|
| `SOFFICE_BIN` | путь к программе, по умолчанию `soffice` из `PATH` |
| `SOFFICE_TIMEOUT_MS` | срок на один файл, по умолчанию 60 000 |

Шрифты должны знать кириллицу и узбекскую латиницу (`oʻ`, `gʻ`). На
cloudplus-an это Liberation и DejaVu — они есть в базовой установке. На
сервере без них PDF соберётся, но буквы станут квадратами, и заметить это по
коду ответа нельзя: проверка `qa/documents-live/pdf.mjs` разбирает готовый PDF
обратно в текст именно поэтому.

Преобразования идут по одному и каждое со своим профилем LibreOffice во
временном каталоге. Второй одновременный запуск с общим профилем молча
присоединяется к первому и не преобразует ничего, возвращая при этом ноль.

## Вложения на стенде

Файлы вложений лежат вне репозитория, каталог задаётся `ATTACHMENTS_DIR`
(по умолчанию `backend/var/attachments`, он в `.gitignore`). На стенде
переменная стоит в `~/.config/systemd/user/metall-asia-stand.env` и указывает
на `/home/an/clients/metall-asia/sistema-upravleniya/dev/backend/var/attachments-stand`
— отдельный каталог от каталога разработки, как и база.

Демонстрационный сид кладёт 13 вложений: сертификаты качества к партиям
с номером сертификата, фото к приходам и списаниям, сканы накладных к первым
финансовым операциям. Файлы собираются в коде (`prisma/demo-files.ts`),
двоичных заготовок в репозитории нет.
