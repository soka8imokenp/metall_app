# 11. Мобильное приложение — устройство, что сделано, что осталось

Документ для того, кто разворачивает платформу на сервере. Здесь — как
устроено мобильное приложение, какие части сервера написаны под него, что
работает, и **что нужно сделать на стороне сервера/инфраструктуры**, чтобы
приложение заработало в бою. Функционал приложения закончен (версия 0.9.x);
всё, что ниже в разделе «Осталось», — настройка окружения, а не код экранов.

Код: `mobile/` (приложение), серверные части — в `backend/` (перечислены в §4).
Контракт API для мобильного клиента — `04-API-CONTRACT.md` §14.30.

---

## 1. Стек

| Что | Чем |
|---|---|
| Платформа | Expo SDK 57, React Native 0.86 (новая архитектура), TypeScript |
| Навигация | expo-router, маршруты — файлы в `mobile/src/app/` |
| Данные | TanStack Query + кэш в AsyncStorage (офлайн-просмотр) |
| Анимации | Reanimated 4, Gesture Handler |
| Прочее | expo-camera (сканер, фото), expo-local-authentication (отпечаток/Face ID), expo-secure-store (токены, PIN), expo-notifications (push), expo-blur, expo-linear-gradient, lucide-иконки, шрифт Inter |
| Сборка APK | локально в Docker (`mobile/scripts/release.sh`), без EAS |

Нативные папки `android/`, `ios/` **не хранятся** — их генерирует
`expo prebuild` при сборке (в `.gitignore`). Настройки нативной части — только
в `mobile/app.json` и `mobile/app.config.js`.

## 2. Режим работы: «только онлайн»

- Все изменения — только при связи с сервером. Без сети кнопки записи
  заблокированы, сверху плашка «Нет связи — данные могут быть устаревшими».
- Последние загруженные данные хранятся на телефоне (24 ч) и показываются
  офлайн. Справочники и файлы не кэшируются.
- Каждая запись идёт с заголовком `Idempotency-Key`: повтор запроса при
  обрыве связи не создаёт дубль (сервер требует ключ от мобильного клиента).

## 3. Структура `mobile/src`

```

  _layout.tsx           провайдеры: тема, язык, сеть, кэш, вход, обновления, блокировка, меню
  login.tsx             вход (+ настройка адреса сервера)
  change-password.tsx   обязательная смена пароля
  (tabs)/               нижняя панель: index (главная), warehouse, production, finance, sales, documents
  inventory/[uid]       пересчёт инвентаризации
  production/[uid]      заказ цеха: этапы, выпуск, материалы, фото
  finance/[uid]         операция: согласование, проведение, чек
  finance/reports       отчёты (Excel/PDF)
  sales/[uid]           заказ клиента: позиции, оплаты, резерв партий, отгрузки
  documents/[uid]       документ: маршрут согласования, PDF/Word, сканы, история, версии
  admin/                администрирование: пользователи, сессии, устройства, мин. версия
  scan.tsx              сканер QR/штрихкодов (партии, товары)
  settings.tsx          язык, тема, уведомления, PIN/отпечаток, обновления, выход
api/                    client.ts (запросы, refresh-токен), query.ts (useApi), action.ts (записи)
auth/AuthProvider.tsx   вход/выход, права (can('perm')), компания
components/             листы форм по модулям (warehouse, production, finance, sales, documents, admin), Photos
lib/                    format, status, modules, network, storage, device, updates, push, files
ui/                     дизайн-система: components, Band, TabBar, Sheet, Drawer, AppLock, UpdatePrompt, PushBridge…

```

Права: экраны и кнопки показываются по тем же кодам прав, что в вебе
(`warehouse.view`, `finance.post`, `admin.users`…), их отдаёт `/auth/me`.

## 4. Что написано на сервере под приложение (`backend/`)

Всё уже в коде и покрыто тестами (`test/mobile-sessions.e2e.spec.ts`,
`test/mobile-updates.spec.ts`). Миграция:
`prisma/migrations/20261009120000_mobile_sessions_devices`.

| Часть | Где | Суть |
|---|---|---|
| Сессии и refresh-токены | `src/auth/sessions.service.ts`, `auth.controller.ts` | Для `X-Client: mobile`: токен доступа 15 мин + refresh 30 дней, `POST /auth/refresh`, `POST /auth/logout` |
| Устройства | `src/auth/devices.service.ts`, `devices.controller.ts` | `POST /devices/register` (модель, версия, push-адрес); админ: `GET /admin/devices`, `POST /admin/devices/:uid/revoke` / `restore`, `GET/DELETE /admin/sessions` |
| Настройки приложения | там же | `GET /mobile/config` (открытый), `GET/PUT /admin/mobile-config` — минимальная версия, сообщение |
| Ключ повтора | `src/common/idempotency.interceptor.ts` | Обязательный `Idempotency-Key` для записей мобильного клиента |
| Журнал | `request-context.ts` | Действия из приложения пишутся в аудит с источником `mobile` |
| Push | `src/push/*` | Раз в минуту берёт строки `notification_outbox` (те же, что идут в Telegram) и шлёт на телефоны. Только на устройства с живой сессией и не отозванные |
| Обновления APK | `src/updates/*` | `GET /mobile/update` — есть ли новая версия; `GET /mobile/update/apk` — сам APK (сервер кэширует его в `backend/var/updates`) |

### Переменные окружения сервера, относящиеся к приложению

| Переменная | Значение |
|---|---|
| `GITHUB_RELEASES_REPO` | Репозиторий с выпусками APK, сейчас `soka8imokenp/metall_app` (ветка `releases`, файл `latest.json` + APK) |
| `GITHUB_TOKEN_FILE` | Не нужен, пока репозиторий публичный. Для приватного — путь к файлу с токеном (только чтение) |
| `UPDATES_DIR` | Куда кэшировать APK (по умолчанию `backend/var/updates`) — должен быть доступен на запись |
| `PUSH_SCHEDULER` | `off` — выключить рассылку push. По умолчанию включено |

## 5. Обновление приложения «по воздуху» (без магазина)

1. Разработчик запускает `mobile/scripts/release.sh 0.9.3 "что нового"`:
   ставит версию, собирает APK в Docker, публикует `latest.json` + APK в ветку
   `releases` GitHub-репозитория.
2. Сервер (`UpdatesService`) видит новую версию, скачивает APK к себе.
3. Телефон при запуске спрашивает `GET /mobile/update`, показывает лист
   «Вышло обновление» → «Скачать» (полоса загрузки) → «Установить».
4. Если в админке задана минимальная версия выше установленной — обновление
   обязательное, лист не закрывается.

Только Android. На iPhone ставить приложения можно лишь через App Store /
TestFlight.

## 6. Функционал (что сделано)

- **Общее:** вход, смена пароля, роли и права, две компании, RU/UZ, светлая/тёмная тема,
  PIN-код и отпечаток/Face ID, офлайн-просмотр, обновление из приложения, сканер, камера.
- **Склад:** остатки, партии, перемещения/приход/списание, деталь движения и сторно,
  инвентаризации (новая, пересчёт), сканирование партии.
- **Цех (производство):** заказы, этапы (старт/пауза/завершение с причиной и комментарием),
  выпуск продукции, расход материалов, фото.
- **Финансы:** операции, создание, согласование/проведение, фото чека, отчёты с выгрузкой в Excel/PDF.
- **Продажи:** заказы, создание, оплаты, резерв конкретных партий и снятие резерва, отгрузки.
- **Документы:** список, маршрут согласования (отправить/согласовать/вернуть/подписать/отменить),
  PDF/Word, прикрепление скана, история, прежние версии.
- **Администрирование:** пользователи (вкл/выкл доступ, снять блокировку), их сессии
  (завершить) и устройства (отозвать/восстановить), минимальная версия приложения.
- **Push (код готов):** запрос разрешения, регистрация адреса, переключатель в настройках,
  переход в нужный раздел по нажатию. Не работает до шага 7.3.

## 7. Осталось — на стороне сервера / инфраструктуры

### 7.1. Боевой адрес API (обязательно)
Сейчас адрес вшит в сборку: `EXPO_PUBLIC_API_URL`, по умолчанию
`http://192.168.1.165:4001/api/v1` (ПК разработчика в локальной сети через
`mobile/scripts/dev-proxy.mjs`). Нужно:
- поднять API на сервере с доменом и **HTTPS** (например `https://erp.metall-asia.uz/api/v1`);
- сообщить адрес разработчику приложения — он пересоберёт APK с
  `RELEASE_API_URL=https://… ./scripts/release.sh …`.

Пользователь может и сам сменить адрес на экране входа (кнопка «Сервер»),
но правильнее вшить боевой.

После перехода на HTTPS в `mobile/app.json` можно убрать
`usesCleartextTraffic: true` (это разрешение на http — нужно только для стенда).

### 7.2. Сервер обновлений
На боевом сервере задать `GITHUB_RELEASES_REPO` (и `GITHUB_TOKEN_FILE`, если
репозиторий станет приватным) и дать запись в `UPDATES_DIR`. Серверу нужен
исходящий доступ к `api.github.com` и `raw.githubusercontent.com`.

### 7.3. Push-уведомления
Код сервера и приложения готов; не хватает учётных записей служб доставки.
Без них уведомления продолжают идти в Telegram-бот, приложение работает.

Почему нужны внешние службы: закрытое приложение на Android можно «разбудить»
только через Google (Firebase Cloud Messaging), на iPhone — только через Apple
(APNs). Свой сервер этого не заменяет.

Сейчас сервер шлёт через службу Expo (`exp.host`), поэтому нужно:
1. Аккаунт на **expo.dev**, проект `metall-asia` → его **Project ID** вписать
   в `mobile/app.json` → `expo.extra.eas.projectId` (не секрет).
2. Проект **Firebase**, Android-приложение с пакетом `uz.metallasia.app` →
   файл `google-services.json` положить в `mobile/` (в git не попадает,
   `app.config.js` подключит его сам при сборке).
3. В Firebase: Service accounts → Generate new private key → загрузить этот
   JSON в expo.dev → проект → Credentials → Android → FCM V1 (секрет, в репозиторий не класть).
4. Пересобрать APK. На сервере ничего менять не нужно, кроме исходящего доступа к `exp.host`.

Вариант без Expo: в `src/push/push.service.ts` заменить отправку (провайдер
`PUSH_SEND`) на прямой FCM HTTP v1 с ключом сервисного аккаунта в `.env`
сервера; в приложении — `getDevicePushTokenAsync` вместо Expo-токена и
`pushProvider: 'fcm'` (поле уже есть в `POST /devices/register`). Firebase
нужен в обоих вариантах.

### 7.4. Ключ подписи APK (обязательно до раздачи сотрудникам)
Сейчас APK подписан отладочным ключом. Нужен постоянный ключ (keystore);
**сменить его потом нельзя** — обновления перестанут ставиться поверх, придётся
удалять приложение. Ключ хранить вне репозитория, передать разработчику
приложения путь/пароли через защищённый канал; в `release.sh` добавить подпись.

### 7.5. iPhone
Нужен аккаунт Apple Developer (99 $/год), сборка через EAS или Xcode,
раздача через TestFlight/App Store. Самообновление из приложения на iPhone
невозможно (ограничение Apple) — лист обновления там только сообщает о версии.

### 7.6. Безопасность перед боем
- Репозиторий публичный; в документах стенда видны адрес и правило тестовых
  паролей (`логин123`). На боевом сервере — свои пароли, стендовые учётки удалить.
- `PUSH_SCHEDULER`, `GITHUB_*` — проверить в `.env` боевого сервера.

## 8. Локальная разработка (для справки)

```bash
# сервер
cd backend && docker compose up -d && npm run build && node dist/main.js   # 127.0.0.1:4000
# мост для телефона в локальной сети (CORS, 0.0.0.0:4001)
cd mobile && node scripts/dev-proxy.mjs
# веб-просмотр приложения
cd mobile && npx expo start --web --port 8081
# проверка типов
cd mobile && npx tsc --noEmit
# выпуск APK (тяжело: не запускать параллельно с другими сборками)
cd mobile && ./scripts/release.sh 0.9.3 "что нового"
```
