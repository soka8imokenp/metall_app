# Контракт API

Это шов между фронтендом (делает сторонний исполнитель) и бэкендом (собираю я
вторым этапом). Фронтенд разрабатывается на моках, повторяющих этот контракт.
Любое изменение контракта — только письменно, с отметкой в этом файле.

Базовый префикс: `/api/v1`. Формат — JSON, UTF-8.

---

## 1. Общие соглашения

### 1.1. Заголовки запроса

| Заголовок | Обязателен | Назначение |
|---|---|---|
| `Authorization: Bearer <access_token>` | да, кроме `/auth/*` | аутентификация |
| `X-Company-Id` | да | в какой компании работает пользователь |
| `Accept-Language: ru \| uz` | нет (по умолчанию `ru`) | язык текстов и ошибок |
| `Idempotency-Key` | да для POST/PUT/PATCH/DELETE | защита от двойного проведения |
| `X-Request-Id` | нет | сквозная трассировка |

`X-Company-Id` — не косметика. Пользователь с доступом к двум компаниям
переключается в интерфейсе, и сервер обязан знать контекст. Компания, к которой
у пользователя нет доступа, даёт `403`.

### 1.2. Ответ-конверт

Успех:

```json
{ "data": { ... }, "meta": { ... } }
```

Список:

```json
{
  "data": [ ... ],
  "meta": { "page": 1, "pageSize": 50, "total": 1234, "totalPages": 25 }
}
```

Ошибка:

```json
{
  "error": {
    "code": "INSUFFICIENT_STOCK",
    "message": "Недостаточно доступного остатка",
    "details": [
      { "field": "lines[0].qty", "message": "Доступно 12.5 т, запрошено 20 т",
        "meta": { "available": "12.5", "requested": "20" } }
    ],
    "requestId": "01J8..."
  }
}
```

Фронт показывает `message` пользователю и подсвечивает поля из `details[].field`.
Тексты приходят уже на языке из `Accept-Language`.

### 1.3. Коды ответов

| Код | Когда |
|---|---|
| 200 | успешное чтение или изменение |
| 201 | создан ресурс |
| 204 | удаление/отмена без тела |
| 400 | ошибка валидации формы |
| 401 | нет или истёк токен |
| 403 | нет права на действие или на компанию |
| 404 | ресурс не найден **или недоступен по области видимости** |
| 409 | конфликт состояния: неверный переход статуса, устаревшая версия записи |
| 422 | форма верна, но бизнес-правило нарушено (нет остатка, превышен лимит долга) |
| 429 | превышен лимит запросов |
| 500 | ошибка сервера |

Различение 400 и 422 важно фронту: 400 — поправь форму, 422 — покажи
пользователю осмысленное объяснение, форма при этом валидна.

### 1.4. Типы значений

- Числа с точностью (деньги, количества) — **строки**: `"12.500000"`.
  JSON-число потеряет точность, а в учётной системе это недопустимо.
- Даты — `2026-09-23`, моменты времени — ISO 8601 с зоной:
  `2026-09-23T10:15:00+05:00`.
- Идентификаторы в API — `uid` (uuid), а не внутренние `id`.
- Перечисления — строковые коды в нижнем регистре (`in_progress`).

### 1.5. Списки: пагинация, сортировка, фильтры

```
GET /api/v1/sales/orders?page=1&pageSize=50&sort=-orderDate&status=confirmed
    &search=труба&dateFrom=2026-09-01&dateTo=2026-09-30
```

- `page` с 1, `pageSize` по умолчанию 50, максимум 200.
- `sort` — поле, `-` в начале для убывания; несколько через запятую.
- Фильтры — отдельные query-параметры, множественные значения через запятую.
- `search` — сквозной поиск по значимым полям сущности.

Для бесконечных списков (мобильное, журнал движений) дополнительно курсор:
`?cursor=<opaque>&limit=50`, в `meta.nextCursor`.

### 1.6. Идемпотентность

Любой POST/PATCH/DELETE несёт `Idempotency-Key` (uuid, генерирует клиент).
Повтор с тем же ключом и тем же телом возвращает **сохранённый ответ**, а не
создаёт второй документ. Тот же ключ с другим телом — `409`.

Это не опция: мобильное приложение работает в цеху с обрывами связи и повторяет
отправку.

### 1.7. Оптимистическая блокировка

Ответы объектов несут `version` (integer). При изменении клиент присылает
`If-Match: <version>` или поле `version` в теле. Несовпадение — `409` с текущей
версией в `error.details`, фронт предлагает перезагрузить запись.

### 1.8. Права в ответе

Каждый объект списка и карточки несёт `permissions` — что доступно
текущему пользователю именно по этой записи:

```json
"permissions": { "canEdit": true, "canDelete": false, "canApprove": false, "canShip": true }
```

Фронт строит кнопки по этому полю и не хранит матрицу прав у себя.
Сервер проверяет права повторно при самом действии — клиентское поле только
для интерфейса.

### 2.1 Забыли пароль — заявка, а не сброс

| Метод | Путь | Кто | Назначение |
|---|---|---|---|
| POST | `/auth/password-reset-request` | без входа | `{login, contact, note?}` → `{accepted: true}` |
| GET | `/auth/password-reset-requests?status=new\|done\|rejected\|all` | `admin.users` | очередь заявок |
| POST | `/auth/password-reset-requests/{uid}` | `admin.users` | `{action: done\|rejected, note?}` |

Пароль система не меняет и не рассылает: тракта рассылки нет ни в одном
модуле, а выдать новый по одному знанию логина — отдать учётку тому, кто
логин угадал. Заявка кладётся в очередь, администратор узнаёт человека и
выдаёт пароль тем способом, которым у них принято.

Три правила, каждое проверяется в `test/password-reset.e2e.spec.ts`:

- **ответ не различает логины.** На выдуманный логин ответ тот же, что на
  настоящий, — иначе форма становится справочником действующих учёток;
- **открытая заявка на логин одна.** Повторное нажатие обновляет свою же
  (частичный уникальный индекс), список администратора не тонет;
- **очередь закрыта правом `admin.users`.** Признак «такая учётка есть»
  виден только в ней и наружу не уходит.

### 5.12. Настройки учёта компании (ТЗ 5.7)

| Метод | Путь | Право |
|---|---|---|
| GET | `/refs/settings?companyUid=` | `warehouse.view` |
| PATCH | `/refs/settings` | `settings.edit` |

```json
{ "data": { "rows": [ { "companyUid": "...", "companyCode": "trade",
                        "companyName": "…", "costingMethod": "fifo" } ] } }
```

Чтение отвечает списком по каждой видимой компании: компаний две, и учёт у них
разный — завод и торговля считают себестоимость по-своему. Требовать выбор
компании на чтение значило бы, что человек с доступом к обеим не увидит
настройку вовсе. `PATCH` компанию требует, если видимых больше одной.

`costingMethod` — `fifo` или `weighted_average`. Чтение открыто каждому, кто
видит склад: цифра себестоимости без метода не читается. Правка — отдельным
правом: это не справочник, а правило, по которому считаются деньги.

Метод действует с момента смены и вперёд. Проведённые движения не
пересчитываются: их себестоимость уже вошла в маржу закрытых заказов, и
переписать её задним числом значит переписать прибыль по сделкам, которые
давно закрыты.

Считается так: **FIFO** — цена той строки остатка, откуда товар уходит
(партию называет документ); **средневзвешенная** — среднее по всей позиции на
складе, взвешенное по количеству, на момент расхода. Партия в движении
остаётся в обоих случаях: прослеживаемость от метода оценки не зависит.
Серийный номер метод обходит — уезжает конкретная труба со своей ценой.

### 6.1. Отгрузка штучной позиции (ТЗ 5.6)

У строки с признаком `trackSerials` ответ `availability` несёт не только
количество, но и `serials` — свободные номера труб на складе строки
(до 50). `availableQty` у такой строки равно числу номеров: доступное
штучной позиции меряется штуками, которые можно назвать.

`POST /sales/orders/{uid}/shipments` принимает номера в строке:

```json
{ "lines": [ { "lineUid": "...", "qty": "2",
               "serialNumbers": ["PPU-2026-0007", "PPU-2026-0011"] } ] }
```

Правила, и все — ответ 422 с объяснением:

- номеров ровно столько, сколько штук в строке, количество — целое;
- номер существует в компании, закреплён за этой же номенклатурой и лежит
  на складе строки;
- один номер не называется в накладной дважды;
- позиции без штучного учёта номера не передаются.

Каждая труба уезжает своей строкой ТТН и своим движением склада на одну
штуку: строка журнала несёт один `serial_id`, и «две штуки этим номером»
было бы неправдой про одну из них. Состояние номера в той же транзакции
становится `shipped`, и по `GET /warehouse/serials/{number}` видно, кому
труба ушла.

### 9.1. Сделано: реестр (Э1, 29.09)

Из таблицы выше сделано только чтение: `GET /documents`, `GET /documents/{uid}`,
`GET /documents/types`. Остальное — следующие этапы `.notes/documents-plan.md`.

```
GET /documents?search=&typeUid=&typeCode=&status=&partnerUid=&from=&to=&limit=&offset=
```

| Параметр | |
|---|---|
| `search` | подстрока номера, регистр не важен |
| `typeUid` | тип одной компании |
| `typeCode` | тип по коду (`INV`, `TTN`, `ACT`, `SPEC`, `CONTRACT`) — во всех компаниях сразу |
| `status` | один из `draft pending_approval approved signed returned cancelled` |
| `partnerUid`, `from`, `to` | контрагент и период по дате документа |

Ответ:

```json
{ "rows": [ … ], "total": 240, "byStatus": { "signed": 76, "pending_approval": 83 },
  "limit": 100, "offset": 0 }
```

**`byStatus` считается по всем фильтрам, кроме статуса.** Экран показывает его
вкладками-счётчиками, и они же — фильтр: иначе «на согласовании 83» исчезало бы
ровно в тот момент, когда по нему нажали. `total` при выбранном статусе — число
по этому статусу.

**Два фильтра по типу, потому что тип принадлежит компании.** У торгового дома
и у завода свой «Счёт» со своей нумерацией. В режиме холдинга выпадающий список
показывал бы «Счёт» дважды, и любой выбор прятал бы половину счетов, — экран
сводит типы по коду и фильтрует по `typeCode`. `typeUid` остаётся для запроса по
типу конкретной компании.

Строка документа:

```json
{ "uid": "…", "number": "ТТН-26/00003", "documentDate": "2026-09-24",
  "type": { "uid": "…", "code": "TTN", "nameRu": "…", "nameUz": "…" },
  "company": { "uid": "…", "code": "plant", "nameRu": "…", "nameUz": "…" },
  "partner": { "uid": "…", "name": "…", "inn": "000000201" },
  "source": { "kind": "sales_order", "uid": "…", "number": "ЗВ-00254" },
  "amountTotal": "269811704.9034", "currency": "UZS", "locale": "ru",
  "status": "approved", "version": 1,
  "author": { "uid": "…", "name": "…" }, "files": 0, "createdAt": "…" }
```

**Сумма и контрагент берутся из документа, а не из источника.** `source` — это
ссылка для перехода: счёт, выставленный в марте, печатается мартовскими числами,
даже если в заказе потом всё поменяли. `kind` — одно из `sales_order`, `deal`,
`finance_operation`, `production_order`; источник неизвестного вида
возвращается как есть, с `uid: null`.

`files` — число вложений; сами файлы к документу отдаёт раздел 10 с
`entityType=document` (заведено ещё в складском Э7).

`GET /documents/types?all=true` — типы с маской нумерации, областью счётчика и
числом документов по типу (`usage.documents`); без `all` — только включённые.

Права: всё чтение — `documents.view`. `documents.edit` и `documents.approve`
заведены и понадобятся на следующих этапах.

### 9.2. Сделано: типы и нумерация (Э2, 29.09)

```
GET    /documents/types?all=true
GET    /documents/types/sample?mask=&counterScope=&code=&typeUid=
POST   /documents/types
PATCH  /documents/types/{uid}
DELETE /documents/types/{uid}
```

Чтение — `documents.view`, запись — `refs.edit` (то же право, что у складских
и CRM-справочников: справочники ведёт тот, кто отвечает за названия и счёт, а
не тот, кто выписывает документы).

Строка типа:

```json
{ "uid": "…", "code": "INV", "nameRu": "Счёт на оплату", "nameUz": "…",
  "numberingMask": "СЧ-{YY}/{SEQ}", "counterScope": "company_period",
  "isActive": true,
  "company": { "uid": "…", "code": "trade", "nameRu": "…", "nameUz": "…" },
  "usage": { "documents": 71, "issued": 71 },
  "nextNumber": "СЧ-26/00072" }
```

`nextNumber` показывает следующий номер, **не занимая его**: справочник
открывают чаще, чем выписывают документ, и дырки в нумерации от просмотра
потом не объяснить.

#### Маска номера

Всё вне фигурных скобок попадает в номер как есть. Подстановки:

| | |
|---|---|
| `{SEQ}` | счётчик, пять знаков |
| `{SEQ:N}` | счётчик шириной N знаков (1–9) |
| `{YY}` / `{YYYY}` | год документа |
| `{MM}` | месяц |
| `{TYPE}` | код типа |
| `{COMPANY}` | код компании |

Отклоняется с 422: маска без `{SEQ}` (у всех документов был бы один номер),
два `{SEQ}`, незнакомая подстановка (ответ называет её и перечисляет
доступные), и **периодический счётчик без года в маске** — счётчик обнулится
в январе, а в номере этого не видно, и номер прошлого года повторится.

`counterScope`: `company_period` — счётчик с начала периода (года, а с `{MM}`
в маске — месяца), `company` — сквозной.

`GET /documents/types/sample` считает пример, ничего не занимая. С `typeUid`
считает от счётчика этого типа: форма правки обязана показывать тот номер,
который напечатается, а не единицу.

#### Что заморожено

| Поле | Когда нельзя менять | Почему |
|---|---|---|
| `code` | есть документы или выданные номера | код уходит в номер через `{TYPE}` и остаётся в напечатанном |
| `counterScope` | выданы номера | переключив сквозной на периодический, начнём период заново и повторим выданный номер |
| `numberingMask` | — | менять можно, действует вперёд: выданные номера не переписываются |

Отказ — 409, в `error.details` идут `{documents, issued}`.
`DELETE` на тип с документами или выданными номерами — тоже 409: такой тип
выключают (`PATCH {isActive:false}`), а не удаляют, иначе из истории пропадёт,
чем эти документы были.

#### Выдача номера

Номер выдаётся одним запросом:

```sql
INSERT INTO document_counter (company_id, document_type_id, period_key, last_number)
     VALUES ($1, $2, $3, 1)
ON CONFLICT (company_id, document_type_id, period_key)
DO UPDATE SET last_number = document_counter.last_number + 1
  RETURNING last_number
```

Читать счётчик и писать обратно тремя действиями значит выдать двум
одновременным созданиям один номер. `ON CONFLICT DO UPDATE` берёт блокировку
строки счётчика, второй запрос ждёт первого. Проверено: пять одновременных
выдач дают пять разных номеров, сломанная на «прочитать и записать» версия
даёт четыре одинаковых.

Вызывается только внутри транзакции создания документа: откатилась вставка —
откатился и счётчик. Если собранный номер всё же занят (так бывает после
правки маски), счётчик двигается дальше — до двадцати попыток, дальше 409 с
объяснением.

### 9.3. Сделано: выписка из источника (Э3, 30.09)

```
GET  /documents/sources?kind=&search=      — поиск основания по номеру
POST /documents/from-source                — выписать документ
```

Право на оба — `documents.edit`.

```json
{ "documentTypeUid": "…", "sourceType": "sales_order", "sourceUid": "…",
  "locale": "ru", "documentDate": "2026-09-30" }
```

Ответ — `{uid, number}`. Документ создаётся в статусе `draft`.

`sourceType` — одно из `sales_order`, `shipment`, `deal`, `finance_operation`,
`production_order`, `partner`. Список закрытый, и имя таблицы в запрос не
подставляется: `source_doc_type` хранит строку, и собрать по ней `FROM ${kind}`
было бы дырой. Запрос под каждый вид написан отдельно.

Откуда что берётся:

| Источник | Строки | Суммы |
|---|---|---|
| `sales_order` | строки заказа как есть | суммы заказа, не пересчитываются |
| `shipment` | что реально уехало | количество отгрузки × цена строки заказа |
| `production_order` | одна строка: выпущенное, а пока не выпущено — плановое | без цены |
| `deal`, `finance_operation`, `partner` | нет | сумма источника |

**Документ — снимок, а не вид на источник.** Строки (`document_line`),
реквизиты (`document.requisites`) и суммы записываются в сам документ.
Правка заказа после выписки счёт не меняет: он ушёл клиенту, и по нему платят.
В строке лежат название и единица **текстом**, а не только ссылка на
номенклатуру: переименовали позицию — в выписанном счёте остаётся то
название, по которому её приняли.

**Номер выдаётся в той же транзакции.** Оборвалось создание — откатился и
счётчик; проверено прямо: номер, взятый в транзакции, которая потом упала,
возвращается счётчику.

Отказы: 422 — сделка без контрагента (выписывать некому), тип и источник из
разных компаний; 409 — тип выключен; 404 — источника нет.

`GET /documents/{uid}` теперь отдаёт ещё два поля:

```json
{ "…": "…",
  "amountNet": "160050079.9900", "amountVat": "19206009.6000",
  "lines": [ { "seq": 1, "itemCode": "SHVELLER-16P", "name": "Швеллер 16П ГОСТ 8240-97",
               "qty": "18.694000", "unitCode": "t", "unitName": "тонна",
               "price": "8561543.2400", "discountPercent": "0.0000",
               "vatRate": "12.0000", "amountNet": "…", "amountVat": "…",
               "amountTotal": "…" } ],
  "requisites": { "company": {"name","inn","legalAddress","bank"},
                  "partner": {"name","inn","legalAddress","actualAddress","bank"},
                  "basis": "Заказ ТД-00368", "paymentDueDate": "2026-09-24",
                  "paymentDelayDays": 14, "deliveryDate": null,
                  "vehicle": null, "driver": null,
                  "netWeightT": null, "grossWeightT": null,
                  "currency": "UZS", "amountInWords": "Сто семьдесят девять …" } }
```

В списке `lines` и `requisites` не приходят намеренно: на 240 документов это
240 лишних запросов ради данных, которых на экране списка не видно.

`requisites` — JSON, а не колонки: состав реквизитов у договора, счёта и
накладной разный и будет дополняться под образцы заказчика. Колонка на каждый
реквизит означала бы миграцию на каждую новую печатную форму.

**Сумма прописью** считается на сервере (`documents/amount-words.ts`), по-русски
и по-узбекски. По-русски согласуется род («одна тысяча», «один миллион») и
склоняется разряд с отдельным правилом для 11–14. Копейки идут цифрами — так
пишут в счетах. Незнакомая валюта пишется своим кодом, а не выдуманным словом.

### 9.4. Сделано: шаблоны печатных форм и сборка DOCX (Э4, 30.09)

```
GET    /documents/templates/fields          — поля системы (refs.edit)
GET    /documents/templates?typeUid=        — список шаблонов (refs.edit)
POST   /documents/templates/upload?documentTypeUid=&locale=&name=   — файл телом
PATCH  /documents/templates/{uid}/field-map — тег файла → поле системы
POST   /documents/templates/{uid}/check     — проверка на настоящем документе
POST   /documents/templates/{uid}/publish   — вывести в печать
POST   /documents/templates/{uid}/unpublish — снять
GET    /documents/templates/{uid}/file      — исходный файл шаблона
DELETE /documents/templates/{uid}
GET    /documents/{uid}/file?format=docx    — печатная форма (documents.edit)
```

Право на весь шаблонный блок — `refs.edit`, как у справочников: менеджер
выписывает документы, но бумагу, по которой печатает вся компания, меняет не
он. Право на печать — `documents.edit`, а не `documents.view`: выпуск бумаги
наружу, а не просмотр карточки.

**Загрузка — байты телом запроса**, как у вложений (§14.10): описание в строке
запроса, файл телом. Предел 5 МБ, принимается только DOCX (проверяется по
сигнатуре zip, а не по расширению). Сырой разбор тела включён в `main.ts`
ровно на `/api/v1/documents/templates/upload` — на префиксе
`/documents/templates` он съел бы JSON у сопоставления полей.

**Публикация — отдельное действие, и это главное правило этапа.** Загруженный
файл не печатается сам собой: шаблон с опечаткой в теге даёт не ошибку, а
пустое место в счёте, который уже ушёл клиенту. `POST …/publish` сначала
собирает шаблон на последнем документе этого типа и отказывает `422`, если
собраться не удалось или остались теги, которым нечем заполниться, — отказ
называет теги поимённо. Документов этого типа ещё нет — `check` честно говорит,
что проверять не на чем, и публикация не проходит.

**Опубликованный на тип и язык ровно один.** Держит частичный уникальный
индекс `document_template_published_key`, публикация нового снимает прежний.
«Какой из двух печатается» — вопрос, которого не должно возникать.

**Теги читаются из самого файла** (`parseTags`) и возвращаются списком
`{name, kind, known, mappedTo}`. Неизвестный тег — не ошибка загрузки, а работа
администратора: в бумаге заказчика стоит `{НомерСчета}`, переписывать его файл
мы не вправе, поэтому сопоставление живёт у шаблона (`field_map`). Цикл строк
приходит одной записью, а не парой открывающего и закрывающего тега.

**Имена полей плоские, хотя и с точкой.** `{company.inn}` — это ключ
`company.inn`, а не путь в объекте: `easy-template-x` разбирает `{doc.number}`
как тег с таким именем и по вложенному объекту его не ищет (проверено на живом
файле). Точка здесь для человека, не для движка.

Поля: `doc.*` (number, date, type, basis), `company.*` и `partner.*` (name,
inn, address, bank), `payment.dueDate`, `payment.delayDays`, `delivery.date`,
`transport.*`, `amount.*` (net, vat, total, words), `currency`, `linesCount`;
цикл `{#lines}…{/lines}` с полями `seq, code, name, qty, unit, price, vatRate,
net, vat, total`; условия `hasVat`, `noVat`, `hasPartner`, `hasLines`,
`hasTransport`.

**Документ печатается тем шаблоном, которым напечатан впервые.**
`document.template_id` проставляется после первой успешной сборки и дальше не
меняется. Заказчик обновил бумагу — новые документы идут по новой, а
«перепечатай мартовский счёт» даёт мартовскую форму, ту самую, что ушла
клиенту. Упавшая печать ссылку не проставляет. По той же причине шаблон,
которым что-то напечатано, не удаляется: `DELETE` отвечает `409` и кладёт
число в `error.details.printed`.

**Подставляются только данные самого документа** — строки, реквизиты и суммы,
записанные при выписке. Ни одного обращения к заказу: документ снимок, и печать
не повод его пересчитать.

Отказ печати без опубликованного шаблона — `409` со словами, что делать, а не
пустой файл.

**Черновые формы кладёт посев**: счёт, накладная, акт и спецификация, на
русском и узбекском, по обеим компаниям. Это наши заготовки без оформления —
без них кнопка «Скачать DOCX» не работала бы, пока не приехали образцы
заказчика. Придут — загружаются файлами поверх, код не меняется. Для договора
черновика нет: его набирают прозой, подставлять в него таблицу позиций незачем.
КП в справочнике типов пока не заведено — заведут тип, загрузят в него файл.

### 9.5. Сделано: PDF печатной формы (Э5, 30.09)

```
GET /documents/{uid}/file?format=pdf     — печатная форма PDF (documents.edit)
GET /warehouse/reports/{kind}/file?format=pdf   — отчёт склада на бумаге
GET /crm/reports/{kind}/file?format=pdf         — отчёт CRM на бумаге
```

**Преобразует LibreOffice в безголовом режиме.** Своего рисовальщика PDF мы
не пишем: у документа шаблон заказчика со своей вёрсткой, и «почти как в
Word» здесь означает поехавшую таблицу в счёте, который уже ушёл клиенту.
Путь к программе — `SOFFICE_BIN` (по умолчанию `soffice`), срок на один файл —
`SOFFICE_TIMEOUT_MS` (по умолчанию 60 с). Программы нет — ответ `503` со
словами, что поставить; файл не собрался — `422` с советом открыть DOCX.

Три вещи, без которых это не работает под нагрузкой, и все три в `pdf.ts`:

1. **Свой профиль на каждый запуск.** LibreOffice держит настройки в каталоге
   пользователя и при втором одновременном запуске присоединяется к первому
   процессу — преобразование тогда не происходит вовсе, а команда возвращает
   ноль.
2. **Очередь.** Преобразования идут по одному: пять одновременных LibreOffice
   — это пять процессов по паре сотен мегабайт.
3. **Срок.** Процесс, севший на сломанном файле, висит вечно и держит очередь.

**Готовый PDF не пересобирается.** Байты ложатся в хранилище вложений, в
`document` остаются `pdf_key`, `pdf_size`, `pdf_built_at` и `pdf_version`.
Счёт скачивают, отправляют, печатают и скачивают снова — четыре запуска на
один и тот же неизменившийся файл. Годным он считается, пока не изменилась
версия документа; изменилась — собирается заново, а прежний файл удаляется из
хранилища: два PDF одного счёта это шанс отправить клиенту устаревший.

**Отчёты идут тем же трактом** (`common/report-file.ts`): отчёт собирается в
DOCX и отдаётся LibreOffice. Второй способ делать PDF означал бы две разные
бумаги из одной системы. Лист альбомный от семи колонок, кегль — по их числу,
ширина колонки — по самому длинному, что в ней стоит. Это не украшение:
тринадцать колонок в равной ширине рвут «283 309 339,12» посередине разряда,
и на бумаге это читается как другое число. В PDF уходит первая тысяча строк, и
об этом написано на самой бумаге; Excel и CSV отдают отчёт целиком.

**Табличная часть в собранном DOCX требует заданных ширин и кегля под
содержимое.** Без них LibreOffice при выгрузке в PDF оставлял от таблицы счёта
«№» и «Наименование», а остальные шесть колонок терял, обрезая название на
полуслове. В XML файла при этом все ячейки на месте — видно это только на
бумаге, поэтому проверка разбирает готовый PDF обратно в текст
(`pdftotext -layout`), а не сверяет заголовки ответа.

### 9.6. Сделано: согласование, редакции и журнал (Э6, 30.09)

```
POST  /documents/{uid}/actions            — движение по маршруту (documents.view + право действия)
PATCH /documents/{uid}                    — правка документа (documents.edit)
GET   /documents/{uid}/versions           — прежние редакции
GET   /documents/{uid}/history            — журнал изменений
GET   /documents/{uid}/versions/{n}/file  — печатная форма прежней редакции
```

**Маршрут ТЗ 7.4 один и живёт на сервере** (`documents/workflow.ts`):
черновик → на согласовании → утверждён → подписан, с возвратом на доработку и
отменой. Карточка не считает доступные действия сама — `GET /documents/{uid}`
отдаёт их полем `actions`. Второй перечень правил на фронте однажды разошёлся
бы с серверным, и экран предлагал бы действие, на которое придёт отказ.

**Право на согласование отдельно от права на создание.** `submit` и `cancel`
требуют `documents.edit`, `approve`, `return` и `sign` — `documents.approve`.
Счёт выписывает менеджер, утверждает не он: у роли «Менеджер по продажам»
второго права нет, и кнопок утверждения на карточке он не видит. Своё
отменить он может — это отказ от собственного документа, а не согласование.

**Возврат и отмена требуют слов.** Без причины `POST /actions` отвечает `422`:
в журнале осталось бы действие без объяснения, а тот, кто переделывает, не
узнал бы, что именно. Причина ложится в `status_comment` и показывается на
карточке рядом со статусом, а не прячется в журнале.

**Правка зависит от статуса** (`editMode`). Черновик и возвращённый правятся
на месте, версия не растёт. Утверждённый и подписанный — только новой
редакцией: прежняя уходит в `document_version` целиком (строки, реквизиты,
суммы, шаблон, готовый PDF), документ получает версию +1 и **возвращается в
черновик**. Согласующий смотрел не эти цифры, и оставить документ утверждённым
значило бы подписать чужими руками то, чего никто не видел. На согласовании и
после отмены документ не правят вовсе — ответ `409` словами, что с ним делать.

**`version` в теле PATCH обязательна.** Разошлась с текущей — `409` и текущая
в `error.details.version`. Двое открыли документ, один сохранил: второй не
должен затереть чужое молча.

**Суммы документа считаются в тийинах.** Колонка держит четыре знака, потому
что цена за тонну бывает с четырьмя (0,3333), но сумма к оплате — нет:
3 × 0,3333 давало в цифрах 1,00, а прописью «99 тийинов». Счёт, который спорит
сам с собой, клиент вправе не принять. Округление стоит до записи, поэтому
итог, строки, сумма прописью и бумага считают одно и то же.

**Прежняя редакция печатается своим файлом.** PDF отдаётся тот самый, что
лежал в архиве, — пересобрать его нельзя, это был бы другой файл, а спорят с
клиентом о той бумаге, которую он получил. DOCX собирается из снимка тем
шаблоном, которым редакцию печатали (`template_id` закрепляется на документе
первой удачной печатью). Не печатали — `409`, и список редакций говорит об
этом полем `hasTemplate` **до** нажатия: кнопка, которая заведомо вернёт
отказ, — обещание, которого экран не выполнит.

**Журнал — тот же `audit_log`, что история карточки клиента.** Пишется в одной
транзакции с изменением и защищён триггером от правки: строка только
добавляется. `GET /history` отдаёт до 200 записей с тем, кто и когда действовал
и что изменилось.

Миграция этапа: `20260930140000_document_workflow` (`status_comment`,
`status_at`, `status_by` у документа; таблица `document_version` с RLS).

## 12. Реальное время

WebSocket `/ws` с авторизацией по access-токену. Каналы:
`notifications`, `production.orders`, `warehouse.balances`, `sales.orders`.

Событие несёт тип, сущность и `uid`, но не полные данные: клиент перезапрашивает
изменившуюся запись. Так не возникает расхождения между пришедшим событием
и реальным состоянием.

Деградация обязательна: если сокет недоступен, фронт работает на периодическом
обновлении. Реальное время — удобство, не требование Спецификации.

## 13. Моки для фронтенда

До готовности бэкенда фронт работает на моках. Требования к ним:

1. Формат ответов — ровно как здесь: конверт `data`/`meta`/`error`,
   числа строками, uid вместо id.
2. Обязательно смоделировать: `422` с бизнес-ошибкой (нет остатка), `409`
   (конфликт версий), `403` (нет права), пустой список, список на 10 000 строк,
   долгий ответ (3–5 с) для проверки состояний загрузки.
3. `permissions` в каждом объекте — с разными значениями, чтобы проверить
   скрытие кнопок.
4. Двуязычные поля заполнены обоими языками — иначе переключение языка
   проверить нечем.

Фронт, который падает на 422 или рисует кнопки без оглядки на `permissions`,
приёмку не проходит.

Пояснения, которые важнее самой формы:

- `scope` — `holding`, `trade` или `plant`; вычисляется из компаний, видимых

- Ряд `chart` содержит ровно `period` точек, включая дни без отгрузок — нулями.

  должна называть его средним, а не планом. Появится планирование продаж —
  поле меняет источник, имя остаётся.
- Сумма ряда сходится с карточкой: проверяется тестами отдельно по выручке и по
  тоннам, через два независимых SQL-запроса.

### 14.2. Дашборд: `deltaPercent` стал nullable, подписи — с запятой

Дата: 24.09.2026. Основание — прогон интерфейса на живых данных
(`dev/qa/dashboard-live/`), две находки.

**`kpis[].deltaPercent: string | null`.** Было `string`, у складского остатка
подставлялось `"0.0"` с `isPositive: true`. На экране это выглядело как
«↗ 0,0 %», то есть «динамика посчитана и она нулевая». Считать её не с чем:
остаток — срез на сегодня, прошлого периода у него нет. Теперь приходит `null`,
и фронт не рисует бейдж вовсе. У остальных трёх карточек прирост обязателен.

**Подписи `sub1Ru/sub1Uz/sub2Ru/sub2Uz` — готовый текст, дробная часть через
запятую.** Было «Закрыто или отгружено 77.9% заказов» и «46.7 млрд UZS
в наличии» — точка как десятичный разделитель не годится ни для русского,
ни для узбекского. Машинные поля `value` и `deltaPercent` остаются строками
с точкой: их разбирает фронт (`src/lib/formatters.ts`), и менять их формат
нельзя.

Проверено тестами `test/dashboard.e2e.spec.ts`, блок «честность карточек»
(3 проверки, обе правки ломаются обратно и тесты краснеют).

### 14.3. Замечание по стеку: pg 8.19+ и вложенные связи Prisma

`pg` начиная с 8.19 ругается `DeprecationWarning: Calling client.query() when
the client is already executing a query` и обещает убрать такое поведение в
9.0 (node-postgres, issue #3612). В нашем коде параллельный запуск запросов
внутри одной транзакции убран (`dashboard.service.ts`, было `Promise.all` на
четырёх выборках по одному соединению).

Оставшееся предупреждение приходит из самого Prisma: при выборке с вложенными
`select` по связям (`plan.service.ts`) интерпретатор Prisma 7 шлёт запросы
связей конвейером на тот же client транзакции. Это внутри библиотеки, обойти
из прикладного кода нельзя. На pg 9.0 это сломается — следить за версиями
`@prisma/adapter-pg` и `pg` при обновлении.

### 14.4. Склад: инвентаризация — пути `/warehouse/inventory/*`, а не `inventory-checks`

В §4 стояли `GET/POST /warehouse/inventory-checks`,
`POST /warehouse/inventory-checks/{uid}/lines` и `.../approve`. Сделано короче
и по состояниям листа, потому что подсчёт идёт построчно, а не пачкой: строку
считают у полки по одной, и адрес строки удобнее адреса листа.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/warehouse/inventory?warehouse=&status=&limit=` | листы пересчёта |
| GET | `/warehouse/inventory/{uid}` | лист со строками |
| POST | `/warehouse/inventory` | завести лист (снимок остатка) |
| POST | `/warehouse/inventory/lines/{uid}/count` | записать факт по строке |
| POST | `/warehouse/inventory/{uid}/finish` | закрыть подсчёт, на утверждение |
| POST | `/warehouse/inventory/{uid}/approve` | утвердить: расхождения → движения |
| DELETE | `/warehouse/inventory/{uid}` | отменить лист |

Тело создания: `warehouseCode` обязателен, `zoneCode` сужает лист до одной зоны,
`blockMode` — `block` (операции по месту закрыты) или `mark` (проходят с
пометкой), `companyUid` — при двух компаниях. Тело подсчёта: `qty` **строкой**
(столбец `decimal(20,6)`), ноль законен — «на полке пусто» тоже результат.

Правила, которых в §4 не было:

- **Лист — снимок.** Учётное количество записывается в строки при создании, и
  расхождение считается от него. Иначе оно ехало бы вместе с остатком, пока
  идут подсчёт и утверждение.
- **Второй открытый лист по тому же складу не заводится** (422): два пересчёта
  одного места дают два разных «учётного» и два набора движений.
- **Права разведены.** Считать — `warehouse.inventory`, утверждать —
  `warehouse.inventory.approve` (admin, director). Утверждение списывает
  недостачу на компанию, и это решение не того, кто стоит у полки.
- **Непосчитанные строки не пускают лист на утверждение** (422): «не считали»
  и «посчитали ноль» — разные вещи.
- **Утверждение пишет движения** `write_off` на недостачу и `surplus` на
  излишек, `sourceDocType = 'inventory_sheet'`, причина из справочника не
  нужна — объяснение сам лист, его номер виден в журнале. Себестоимость
  излишка берётся из снимка: товар тот же, придумывать ему закупку нечего.
  Лист без расхождений движений не пишет.
- **Операции во время пересчёта.** Общая проверка в
  `src/warehouse/inventory.ts` зовётся и складом, и продажами: в режиме `block`
  движение по месту отбивается 422 с номером листа, в режиме `mark` проходит и
  ложится в журнал с `during_inventory = true`. Лист без зоны накрывает склад
  целиком, лист с зоной — только свои ячейки; соседняя зона работает как обычно.

### 14.5. Склад: прослеживаемость партии — в ответе `GET /warehouse/batches/{uid}`

Отдельного пути `.../trace` нет. Цепочка в обе стороны (ТЗ 5.6) приехала в тот
же ответ, что и карточка партии: вопрос «откуда это и куда ушло» задают там же,
где смотрят остаток, и второй запрос за тем же экраном не нужен.

К прежним `batch`, `balances`, `moves` добавлены два списка одинаковой формы:

| Поле | Кто заполняет |
|---|---|
| `uid` | движение журнала, которым звено записано; у выпуска цеха своего нет — `null` |
| `kind` | `receipt`, `output`, `material` (вверх); `issue_to_production`, `output`, `shipment`, `write_off` (вниз) |
| `at`, `qty` | дата и количество в базовой единице, количество строкой |
| `partner` | поставщик у прихода, покупатель у отгрузки |
| `docNumber` | номер документа: партия, заказ цеха, ТТН, лист пересчёта |
| `productionOrder` | заказ цеха, если звено про него |
| `item`, `batch` | позиция и партия у материала и у выпуска: `batch.uid` — адрес следующего шага |
| `salesOrder`, `payment` | только у отгрузки: номер заказа продажи и `{status, paid, total}` |

- **`upstream`** — приход от поставщика **или** выпуск цехом, а за выпуском
  материалы того же заказа, каждый своей партией.
- **`downstream`** — выдача в цех, продукция того заказа, отгрузка с ТТН,
  покупателем и состоянием оплаты, списание.
- **Оплата не пересчитывается**: берётся `sales_order.payment_status` и
  `paid_amount`. Второй ответ на тот же вопрос расходился бы с первым.
- **Сторно в цепочку не попадает** — ни сама отмена, ни отменённое ею движение:
  товар никуда не ушёл. В журнале движений обе записи по-прежнему видны.
- **Партия выпуска** ищется и по `production_output.batch_id`, и по заказу
  партии продукции: в первом поле данные есть не всегда, а без номера цепочка
  обрывается на «труба вообще».

### 14.6. Склад: серийные номера — `GET /warehouse/serials` и `/warehouse/serials/{number}`

Штучный учёт (ТЗ 5.6) заводится у позиции флагом `track_serials`. Партия и
номер — разные ответы на один вопрос «какая именно труба», поэтому у одной
позиции стоит что-то одно: `track_batches` или `track_serials`.

Правила записи движения (`POST /warehouse/moves`):

- `serialNumber` **обязателен** у позиции со штучным учётом и **не принимается**
  у остальных — оба случая отвечают 422.
- Количество ровно `1`: одно движение — одна штука. Иначе 422.
- Новый номер заводится **только приходом**. На расходе неизвестный номер — 422:
  выдумывать штуку, которой не приходило, нельзя.
- Приход номера, который уже лежит на складе, — 422: вторая штука с тем же
  номером сделала бы неразличимыми две разные трубы.
- Номер уникален по компании, а не по позиции: закреплённый за другой
  номенклатурой — 422.
- `serial_number.current_state` — производная от движения: приход и возвраты
  дают `in_stock`, выдача в цех `in_production`, списание `written_off`.
  Сторно пересчитывает состояние по остатку, а не возвращает предыдущее.

| Путь | Что отдаёт |
|---|---|
| `GET /warehouse/serials?itemCode=&warehouseCode=&limit=` | номера, лежащие на складе: `{number, state, warehouseCode, location}`. Для подбора в форме операции; номеров, которых на складе нет, в ответе не бывает |
| `GET /warehouse/serials/{number}` | путь одной штуки: `serial` (номер, состояние, позиция, партия выпуска), `place` (склад, ячейка, количество — `null`, если штуки на складе нет), `moves` той же формы, что и у партии |

Номер виден и там, где раньше стояла только партия: в строке остатка
(`GET /warehouse/stock` — поле `serial`, поиск по номеру работает), в журнале
движений (`GET /warehouse/moves` — поле `serial`, поиск тоже) и в строке листа
пересчёта (`serial`): у штучной позиции лист заводится на каждую штуку.

**Продажа и отгрузка по номерам не сделаны.** Позиция со штучным учётом в заказ
продажи и в ТТН не принимается — явный 422 с этим текстом. Молчаливый пропуск
довёл бы заказ до склада и встал бы там.

### 14.7. Склад: штрихкоды, QR и сканер — `/warehouse/scan` и `/warehouse/labels`

Печатается **свой** код, а не человеческий номер. Номера партий в системе
кириллические (`П-00012`, `СР-00001`), а Code 128 кодирует только печатный
ASCII, и партию своим же номером не закодировать.

Код вычисляемый, не хранимый: `MA` + буква вида + девять цифр идентификатора
строки + контрольная цифра Луна, всего 13 знаков.

| Вид | Буква | Разряд в контрольной цифре |
|---|---|---|
| позиция | `I` | 1 |
| партия | `B` | 2 |
| серийный номер | `S` | 3 |
| ячейка | `L` | 4 |

Вид входит в контрольную цифру отдельным разрядом: неверно прочитанная буква
даёт отказ, а не другой объект. Хранимый код пришлось бы стеречь на
уникальность и сверять с объектом; вычисляемый сверять не с чем.

| Путь | Что делает |
|---|---|
| `GET /warehouse/scan?code=` | разбирает то, что принёс сканер, и отдаёт объект |
| `GET /warehouse/labels/templates` | шаблоны этикеток компании |
| `POST /warehouse/labels` | лист этикеток к печати: текст и готовый рисунок кода |

Порядок разбора при скане важен: сначала наш код — у него контрольная цифра,
и совпадение в нём случайным не бывает; потом штрихкод позиции `item.barcode`,
штрихкод ячейки `storage_location.barcode`, серийный номер и код
номенклатуры. Разбирать чужие штрихкоды первыми значит иногда находить не то,
что наклеено. Ответ называет, чем нашлось: `matchedBy` —
`labelCode | itemBarcode | locationBarcode | serialNumber | itemCode`.
Не найдено — 404 с текстом; для сканера это обычный ответ, а не поломка.

Код этикетки приходит вместе с объектом везде, где его печатают: `labelCodes`
(позиция, партия, номер, ячейка) в строке `GET /warehouse/stock`, `labelCode`
в голове партии, в строках `GET /warehouse/serials`, в пути номера и в
справочниках `GET /warehouse/refs` (позиции и ячейки).

Тело `POST /warehouse/labels`: `{templateUid, codes[], copies}`. Копий 1..50,
этикеток за раз не больше 500 — иначе 400 с числом и пределом. Каждый код
разбирается тем же разбором, что и на скане: напечатать этикетку на объект,
которого нет, нельзя.

В ответе `{template, symbology, labels[]}`, в этикетке `{labelCode, kind,
title, subtitle, lines[], symbol}`. **Рисунок кода считает сервер**, а не
экран: Code 128 отдаётся как `{widths[], modules}` — ширины чередующихся полос
и пробелов, начиная с полосы; QR как `{size, rows[]}` — строки из «1» и «0»,
уровень коррекции M. Разойдись кодирование печати и разбора хоть на символ,
напечаталось бы одно, а искалось бы другое.

Шаблон — настройка, а не константа (ТЗ 5.9): размер листа и этикетки, сетка,
поля, зазоры и симвология. `label_template`, уникальный код в компании, один
шаблон по умолчанию на компанию (частичный уникальный индекс), RLS
`company_isolation`. То, что сетка помещается на лист, стережёт CHECK в базе,
а не только форма.

### 14.8. Склад: потребность в закупке — `GET /warehouse/purchase-needs`

Отчёт отвечает на один вопрос: что дозаказать и сколько (ТЗ 5.10).

**Уровень задают на компанию или на склад, и это перекрытие, а не сумма.**
Компанийский уровень живёт в карточке позиции (`item.min_qty`,
`item.critical_qty`), складской — в новой таблице `item_stock_level`
(уникальная пара «позиция + склад», RLS `company_isolation`, CHECK «критический
не выше минимального» и «пустых строк уровня не бывает»). Заведён складской
уровень хотя бы по одному складу — компанийский по этой позиции выключен
целиком. Складывать их значило бы посчитать одну нехватку дважды: один раз по
складу, другой по компании, и закупка заказала бы вдвое.

**Тревога идёт по доступному, дозаказ — по доступному с планом.** Это не
разнобой, а две вещи из одного абзаца ТЗ: «при падении доступного ниже уровня»
позиция попадает в отчёт, «в потребности учитываются открытые резервы и
плановый расход». Доступное = наличие − активные резервы; берутся они из
`stock_reservation`, а не из `stock_balance.qty_reserved`: остаток обрезан
наличием, и резерв сверх наличия (право `sales.order.oversell`) в нём выглядел
бы как его отсутствие. Дозаказ считается до минимального уровня, а не до
критического: вернуться на критический значит завтра снова быть в тревоге.

**Плановый расход — величина компании.** Производственный заказ не называет
склад, с которого выдадут материалы: склада нет ни у заказа, ни у строки
`production_material`. Поэтому план применяется там, где он однозначен: в
компанийской строке — всегда, в складской — только когда весь остаток позиции
лежит на этом складе (`plannedApplied: true`). В остальных складских строках
план назван отдельным числом `plannedCompany`, а в расчёт не идёт: разложить
его по складам нечем, и «как-нибудь» значит подставить закупке выдуманную
цифру. Сколько таких строк — в `totals.plannedHidden`.

| Параметр | Что делает |
|---|---|
| `warehouse` | склад; сужает и компанийские строки — до компании этого склада |
| `state` | `critical` \| `below_min` |
| `all=true` | показать и позиции без нехватки; счётчики при этом не меняются |
| `limit` | 1..500, по умолчанию 200 |

Строка: `{key, scope, item, warehouse, minQty, criticalQty, onHand, promised,
available, plannedOut, plannedCompany, plannedApplied, projected, needQty,
state, needed}`. `scope` — `company` (склада нет, цифра про все склады сразу)
или `warehouse`. `state` — `critical | below_min | ok`. В отчёт попадает и
строка без тревоги, если доступное ушло в минус: обещано больше, чем лежит, и
уровень тут ни при чём.

Сумм по отчёту нет: труба считается в тоннах, скорлупа в погонных метрах —
складывать их нечем. `totals` считает строки: `{rows, critical, belowMin,
plannedHidden}`.

**Что изменилось у соседей.** Уровень теперь один и тот же везде на экране
склада:

- `GET /warehouse/summary` → `levels` считает те же `critical` и `belowMin`,
  что и отчёт: по доступному и с учётом складских уровней. Раньше считалось по
  наличию и только по карточке позиции, и карточка «Ниже критического» спорила
  бы с вкладкой потребности на том же экране.
- в строке `GET /warehouse/stock` появились `levelScope` (`company` |
  `warehouse`) и `levelAvailable` — с чем сравнивали и что сравнивали;
  `minQty` и `criticalQty` приходят уже действующие, а не всегда из карточки
  позиции. `isBelowCritical` и `isBelowMin` считаются по доступному.

Уведомления ответственным (ТЗ 5.10) в этот этап не вошли: они упираются в
общий тракт уведомлений — Telegram-боты и уведомления в системе, ТЗ 11. Отчёт
и счётчики от него не зависят и работают без него.

### 14.9. Склад: отчёты и выгрузка — `/warehouse/reports/*`

Пять отчётов из ТЗ 5.1, один расчёт на экран и на файл.

| `kind` | Отчёт | Период |
|---|---|---|
| `stock` | остатки | нет |
| `moves` | движение | да |
| `availability` | доступное и зарезервированное | нет |
| `turnover` | оборачиваемость | да |
| `inventory-diff` | расхождения инвентаризации | да |

Периода нет у остатков и доступности намеренно: они отвечают на вопрос «что
сейчас», и «остаток за март» — вопрос без ответа. Где период есть, по умолчанию
это последние 30 дней, границы — календарные дни `Asia/Tashkent`: их строит
Postgres через `AT TIME ZONE`, а не JavaScript по часовому поясу процесса.

`GET /warehouse/reports/{kind}` отдаёт таблицу:

```json
{ "data": { "kind": "stock", "title": "Остатки",
            "subtitle": "все склады, строк 74",
            "columns": [ { "title": "Склад" }, { "title": "Наличие", "numeric": true } ],
            "rows": [ ["Склад «Сергели»", 313.44042] ],
            "total": 74, "truncated": false } }
```

Числа в строках — числа, а не подписанные строки: формат («313,4 т») собирает
тот, кто показывает. `truncated` говорит, что строк больше, чем отдано:
показанная половина без предупреждения хуже, чем её отсутствие. Параметры:
`warehouse`, `from`, `to`, `limit` (до 20000, на экран обычно 500).

`GET /warehouse/reports/{kind}/file?format=csv|xlsx` — тот же отчёт файлом.
Ответ не в конверте: файл в JSON пришлось бы отдавать base64, а по нему браузер
ничего не сохранит. Имя — `sklad-{kind}-ГГГГ-ММ-ДД.{ext}` в `Content-Disposition`;
заголовок назван в `exposedHeaders`, иначе при работе с другого источника
браузер не отдаёт его странице и файл сохраняется как «report».

**Excel — настоящий `.xlsx`**, а не CSV с чужим расширением: в CSV число
становится текстом, и сумму по колонке бухгалтер не получает. Пишет его свой
модуль `src/common/xlsx.ts` (zip из пяти XML, без библиотек в поставке);
проверяется он независимым читателем `exceljs` — devDependency, только в
тестах, как `jsbarcode` у Code 128.

**CSV — для чужих программ** (1С, REGOS): разделитель `;`, BOM в начале и
десятичная запятая. Каждое из трёх — из-за русского Excel, и отмена любого
ломает файл: с запятой-разделителем всё встаёт в первую колонку, без BOM
кириллица превращается в мусор, с десятичной точкой числа становятся текстом.

Право на отчёты и выгрузку — `warehouse.view`: они только читают.

### 14.10. Вложения к операциям — `/attachments`

Фото, сканы и сертификат качества партии (ТЗ 5.4, 5.6, 6.3), фото из цеха
(ТЗ 4.1, 4.6) и сканы к документам (ТЗ 7.1). Один набор маршрутов на всех
владельцев: `owner` = `stock_move` | `batch` | `finance_operation` |
`production_order` | `document`, `uid` — uid самого владельца.

```
GET    /attachments?owner=stock_move&uid={uid}      -> [ Attachment ]
POST   /attachments?owner=&uid=&name=&kind=&comment= -> Attachment
GET    /attachments/{uid}/file                       -> сам файл
DELETE /attachments/{uid}                            -> { uid, removed }
```

`Attachment`: `uid`, `kind` (`photo|scan|certificate|other`), `fileName`,
`mimeType`, `sizeBytes`, `sha256`, `comment`, `createdAt`, `author`,
`disposition` (`inline` у картинок, `attachment` у остального).

**Загрузка — сырое тело, не multipart.** Байты идут телом `POST`, тип файла —
в `Content-Type`, описание — в строке запроса. Одно вложение за запрос: разбор
границ формы добавил бы зависимость и второй способ ошибиться с именем поля,
а `fetch(file)` пишется одной строкой.

**Принимаем** `image/jpeg`, `image/png`, `image/webp`, `image/heic`,
`application/pdf`, до 20 МиБ. Список, а не «всё, кроме опасного»: файл
отдаётся обратно в браузер, и каждый тип здесь — решение о том, что браузер
с ним сделает. HTML и SVG не принимаем вовсе — они исполняют скрипт в нашем
источнике. Предел веса продублирован ограничением базы: приложение обходится
скриптом, ограничение — нет.

**Право — по владельцу, отдельного права «вложения» нет.** Движение и партия:
`warehouse.view` на чтение, `warehouse.move` на загрузку и удаление.
Финансовая операция: `finance.view` и `finance.post`. Иначе кладовщик со своим
складским правом не приложил бы фото к собственному списанию.

По владельцам права такие: движение и партия — `warehouse.view` / `warehouse.move`;
финансовая операция — `finance.view` / `finance.post`; производственное задание —
`production.view` / `production.manage`; документ — `documents.view` /
`documents.edit`. Скан к документу прикладывает тот, кто документ ведёт, а не
тот, кто его согласует: согласование — решение, а не работа с файлом.

**Файл лежит на диске**, в базе — описание и ключ `компания/год/месяц/uid.ext`;
имя, которое дал человек, в ключ не входит. Корень задаётся `ATTACHMENTS_DIR`.
Байты в Postgres не кладём: один скан накладной весит как сотня тысяч строк
движений, и каждый дамп базы таскал бы их с собой. Замена диска на S3 или
MinIO — второй класс в `src/attachments/storage.ts` и ни одной правки в
бизнес-логике.

Выдача файла идёт с токеном, а не ссылкой: на маршруте стоит право, а к
`<a href>` заголовок `Authorization` не приложить. Имя файла уходит и как
`filename=`, и как `filename*=UTF-8''` — без звёздной формы браузер сохраняет
русское имя как «______».

### 14.10а. Валюты и курсы — `/refs/currencies/*`

Справочник валют и курс на дату (ТЗ 6.1-6.3). До 03.10.2026 курсы приходили
только с посевом: таблица была, а ввести курс в системе было нельзя — ни
руками, ни загрузкой, то есть требование 6.2 не выполнялось вовсе.

| Метод | Путь | Право | Что делает |
|---|---|---|---|
| `GET` | `/refs/currencies` | `finance.view` | валюты, последний курс, дата, источник, изменение к прошлой дате |
| `GET` | `/refs/currencies/{code}/rates?limit=` | `finance.view` | история курса по дням, новые сверху |
| `GET` | `/refs/currencies/available` | `refs.edit` | валюты ЦБ РУз, которых у нас ещё нет |
| `POST` | `/refs/currencies/sync` | `refs.edit` | загрузить курсы с ЦБ РУз (`force` — не глядя на кэш) |
| `POST` | `/refs/currencies/{code}/rates` | `refs.edit` | курс руками: `{ rateDate, rate }` |
| `POST` | `/refs/currencies` | `refs.edit` | завести валюту по коду из списка банка |
| `PATCH` | `/refs/currencies/{code}` | `refs.edit` | `{ autoload }` — загружать ли курс самостоятельно |

**Источник** — открытый архив ЦБ РУз `https://cbu.uz/ru/arkhiv-kursov-valyut/json/`,
без ключей и регистрации. Банк публикует официальный курс раз в рабочий день,
поэтому «в реальном времени» здесь значит «на сегодня, проверено тогда-то»:
другого официального курса для учёта в Узбекистане нет.

**Правила загрузки.**

- Курс, введённый человеком (`source = 'manual'`), загрузка не затирает.
- Номинал банка приводится к одной единице: тенге публикуется за 100.
- Банк не опрашивается, пока курс на сегодня уже лежит в базе; после неудачной
  попытки следующая — не раньше чем через 15 минут. Удачная загрузка эту паузу
  снимает.
- Недоступный банк не ломает экран: отдаётся последний известный курс и
  `sourceError` словами.
- Расписание в процессе API: первая попытка через 10 с после старта, дальше раз
  в час (`RATES_AUTOLOAD=off` выключает, в прогонах выключено само).
- Ручной ввод идёт в журнал действий (`currency_rate`, действие `rate`),
  автозагрузка — нет: это строка каждый день без человека за ней, а источник и
  время видны в самом справочнике.

### 14.11. Справочники на запись — `/refs/*`

Номенклатура с характеристиками металлопроката, места хранения, причины
списания и уровни запаса (ТЗ 5.2, 5.3, 5.7, 5.10). До этого этапа они
приходили из сида, и завести марку стали значило позвать разработчика.

```
GET    /refs/items?search=&all=&limit=   -> [ RefItem ]
POST   /refs/items                        -> { uid, code }
PATCH  /refs/items/{uid}                  -> { uid }
DELETE /refs/items/{uid}                  -> { uid }

GET    /refs/places?all=                  -> склад → зоны → ячейки деревом
POST   /refs/warehouses | PATCH /refs/warehouses/{uid}
POST   /refs/zones
POST   /refs/locations | PATCH /refs/locations/{uid} | DELETE /refs/locations/{uid}

GET    /refs/reasons?all=  | POST /refs/reasons | PATCH /refs/reasons/{uid} | DELETE …
GET    /refs/stock-levels  | POST /refs/stock-levels | DELETE /refs/stock-levels/{uid}
```

**Право.** Чтение — `warehouse.view`: справочник нужен каждому, кто работает со
складом, иначе форма операции останется без подбора. Запись — отдельное право
`refs.edit`: движение делает кладовщик у полки, а номенклатуру и склады заводит
тот, кто отвечает за то, как это всё названо и посчитано. В роли кладовщика
`refs.edit` нет; у администратора и директора есть.

**Общее правило: что уже участвовало в операциях — выключают, а не удаляют.**
`DELETE` разрешён только нетронутому и отвечает `409` с числом записей, если
объект где-то встречается: удаление увело бы из истории название, по которому
читается прошлое. Выключение — это `PATCH … { isActive: false }`, объект
исчезает из подбора и остаётся в отчётах.

**Что нельзя менять и почему** (ответ `422` с объяснением):

| Правка | Когда запрещена | Причина |
|---|---|---|
| `code` позиции | есть движения | код напечатан на этикетках и стоит в истории |
| `baseUnit` | есть движения | количества в истории пересчитались бы задним числом |
| `trackBatches: false` | есть партии | партии остались бы без хозяина |
| `trackSerials: false` | есть номера | то же самое для штучного учёта |
| `isActive: false` у склада | есть остаток | товар исчез бы из подбора, оставшись в отчёте |
| `isActive: false` у ячейки | лежит товар | сначала переложить остаток |
| `criticalQty > minQty` | всегда | позиция провалится в критические, не побывав ниже минимума |
| уровень с двумя нулями | всегда | строка ничего не говорит, но выключает уровень компании |

**Коэффициенты пересчёта** (`units`) задаются в карточке позиции: `т ↔ м ↔ шт`
считаются к базовой единице. Коэффициента базовой единицы нет — он равен
единице по определению, и запись «т = 0,98 т» означала бы, что количество
зависит от того, как его спросили. Ноль и отрицательное значение отклоняются
и проверкой, и ограничением базы `item_unit_factor_positive`.

Уровень на склад (`/refs/stock-levels`) **перекрывает** уровень компании по этой
позиции, а не складывается с ним (см. §14.8), поэтому запись идёт
`ON CONFLICT DO UPDATE`: пара «позиция + склад» может иметь только один уровень.

### 14.12. CRM: клиенты — `/crm/partners`

Первый этап модуля CRM (ТЗ 8.2). Раздел §8 объявлял пути, здесь — что они
реально отдают и по каким правилам пишут.

| Метод | Путь | Право |
|---|---|---|
| GET | `/crm/partners?search=&managerUid=&sourceUid=&role=&all=&limit=&offset=` | `crm.view` |
| GET | `/crm/partners/options` | `crm.view` |
| GET | `/crm/partners/{uid}` | `crm.view` |
| POST | `/crm/partners` | `crm.edit` |
| PATCH | `/crm/partners/{uid}` | `crm.edit` |
| DELETE | `/crm/partners/{uid}` | `crm.edit` |
| POST | `/crm/partners/{uid}/contacts` | `crm.edit` |
| PATCH/DELETE | `/crm/contacts/{uid}` | `crm.edit` |

`role` — `any` (умолчание), `client`, `supplier`. Клиент и поставщик это
признаки одной записи, а не два справочника: завод и покупает, и возит.
Заведённый дважды, он дал бы две задолженности по одному ИНН.

Поиск идёт по наименованию, ИНН, имени контактного лица и его телефону:
менеджер ищет по тому, что у него на экране входящего звонка.

Карточка несёт `usage` — где контрагент уже участвует (сделки, лиды, заказы,
движения склада, платежи, партии, документы, цены) и `permissions.canDelete`.
Экран строит кнопки по этому полю; сервер проверяет право повторно.

Правила записи:

- **ИНН уникален в компании.** Второй такой же — `409` с именем занявшего.
- **ИНН не меняется у контрагента с реквизитами на бумаге** (движения,
  платежи, документы) — `422`. Такая правка задним числом переписала бы,
  кому они ушли.
- **Версия карточки обязательна в `PATCH`** (§1.7). Без неё — `422`, при
  несовпадении — `409`, текущая версия в `error.details.version`.
- **Участвовавший в записях не удаляется, а выключается** — `DELETE` отвечает
  `409`, в `error.details` число ссылок по видам.
- **Главный контакт ровно один**: назначенный вторым снимает признак с первого.
- Контактное лицо удаляется совсем: это телефон уволившегося человека, и
  прошлые записи от его удаления смысла не теряют.

Теги приводятся к нижнему регистру, пустые и повторы отбрасываются.

Заодно исправлен общий конверт ошибки: `error.details` теперь несёт
подробности, которые положило бизнес-правило (версия записи, число ссылок), а
не только список замечаний валидатора. Раньше они терялись в фильтре ошибок.

Миграции этапа: `20260929150000_crm_partner_card` (`uid` у контактного лица,
`tags` у контрагента), `20260929151000_crm_ref_uids` (`uid` у источников лидов
и типов цен — наружу они уходят как выбор в форме карточки).

### 14.13. CRM: обращения — `/crm/leads`

Второй этап модуля (ТЗ 8.1, 8.3).

| Метод | Путь | Право |
|---|---|---|
| GET | `/crm/leads?search=&status=&sourceUid=&managerUid=&limit=&offset=` | `crm.view` |
| GET | `/crm/leads/{uid}` | `crm.view` |
| POST | `/crm/leads` | `crm.edit` |
| PATCH | `/crm/leads/{uid}` | `crm.edit` |
| POST | `/crm/leads/{uid}/convert` | `crm.edit` |

Список отдаёт `byStatus` — разбивку по статусам по тому же фильтру. Это не
украшение: «сегодня пришло семь» и «покажи эти семь» на экране один вопрос.

Правила:

- **`sourceUid` обязателен при создании.** Без источника отчёт по источникам
  пуст, а рекламу оплачивают по этому числу.
- **Статус `converted` руками не ставится** — `400`. В клиента обращение
  переводит только `convert`: он же заводит карточку.
- **Отказ требует `rejectReason`** — `422`. Причина отдельна от `comment`:
  в комментарии записано, что человек спрашивал, а не почему ушёл. Правило
  продублировано ограничением базы `lead_rejected_needs_reason`.
- **Превращённое обращение не правится** — `422`. Правят карточку клиента.

`POST /crm/leads/{uid}/convert` — тело: `partnerUid` (связать с уже заведённым)
**либо** `nameRu`/`inn`/`partnerType` (завести нового), плюс `withDeal`,
`dealTitle`, `dealAmount`.

Одной транзакцией: карточка клиента, контактное лицо из телефона и почты
обращения (главный), отметка на обращении, при `withDeal` — сделка первой
стадии воронки со своим номером `СД-NNNN` под блокировкой компании.

Ответ: `{ partnerUid, dealUid, alreadyConverted, lead }`. **Повторный вызов
возвращает того же клиента** с `alreadyConverted: true` — менеджер жмёт второй
раз, когда ответ пришёл не сразу, а второй карточки быть не должно. Отдельного
ключа идемпотентности здесь нет: состояние самого обращения и есть защита.

Отклонённое обращение не превращается, пока его не вернут в работу — `422`.
ИНН проверяется и здесь: вторым клиентом с тем же ИНН обращение не станет.

Миграция этапа: `20260929160000_crm_lead_reject_reason`.

### 14.14. CRM: воронка и сделки — `/crm/deals`

Третий этап модуля (ТЗ 8.3).

| Метод | Путь | Право |
|---|---|---|
| GET | `/crm/deal-stages` | `crm.view` |
| GET | `/crm/lost-reasons` | `crm.view` |
| GET | `/crm/deals/board?managerUid=&search=` | `crm.view` |
| GET | `/crm/deals?search=&status=&stageUid=&managerUid=&partnerUid=` | `crm.view` |
| GET | `/crm/deals/{uid}` | `crm.view` |
| POST | `/crm/deals` | `crm.edit` |
| PATCH | `/crm/deals/{uid}` | `crm.edit` |
| POST | `/crm/deals/{uid}/move` | `crm.edit` |
| POST | `/crm/deals/{uid}/win` \| `/lose` | `crm.edit` |

Маршруты со словами (`board`, `deal-stages`, `lost-reasons`) объявлены раньше
`deals/{uid}`: иначе `board` приняли бы за uid и ответили `400`.

**Стадии — из справочника компании**, наружу по `uid`. ТЗ: «стадии
настраиваются», поэтому доска рисует столько колонок, сколько их заведено,
в порядке `seq`.

`board` отдаёт по колонке на стадию: `{ ...стадия, count, amount, deals }`.
У конечных стадий `deals` пуст, а `count` и `amount` считают закрытые: за
полгода их сотни, и стопка карточек вытеснила бы с доски сегодняшнюю работу.

Правила:

- **`move` ходит только по открытым стадиям**, в обе стороны (сделка
  откатывается). Перенос в конечную — `422`: закрывают `win`/`lose`.
- **`lose` требует `reasonUid` из справочника компании** — свободной строки
  нет вовсе. Из неё отчёт по причинам отказов собрался бы из опечаток:
  «дорого», «Дорого», «дороже конкурента» стали бы тремя причинами.
  Правило продублировано ограничением базы `deal_lost_needs_reason`.
- **Закрытая сделка не двигается и не правится** — `422`. Иначе отчёт за
  прошлый месяц менялся бы от сегодняшних правок.
- **Версия сделки обязательна** в `move`/`win`/`lose`/`PATCH` (§1.7):
  двое тянут одну карточку по доске, и второй должен узнать о первом.

**Каждый переход пишет `deal_stage_event`**: кто, когда, откуда, куда.
Карточка отдаёт его как `history`. Текущая стадия говорит, где сделка сейчас,
но не сколько сделок через стадию прошло, — конверсия в Э6 считается по следу.
Сделка, созданная превращением обращения, след тоже оставляет.

Миграция этапа: `20260929170000_crm_funnel` — `uid` у стадий, `version` у
сделки, таблицы `deal_lost_reason` и `deal_stage_event` с RLS, перенос
`deal.lost_reason` из строки в ссылку на справочник.

### 14.15. CRM: задачи и активности — `/crm/tasks`, `/crm/activities`

Четвёртый этап модуля (ТЗ 8.4).

| Метод | Путь | Право |
|---|---|---|
| GET | `/crm/tasks?scope=&assigneeUid=&partnerUid=&dealUid=&type=` | `crm.view` |
| GET | `/crm/tasks/{uid}` | `crm.view` |
| POST | `/crm/tasks` | `crm.edit` |
| PATCH | `/crm/tasks/{uid}` | `crm.edit` |
| POST | `/crm/tasks/{uid}/complete` | `crm.edit` |
| POST | `/crm/tasks/{uid}/cancel` | `crm.edit` |
| GET | `/crm/activities?partnerUid=&dealUid=&type=` | `crm.view` |
| POST | `/crm/activities` | `crm.edit` |

**Задача и активность — разные времена.** Задача смотрит вперёд: срок,
ответственный, бывает просрочена. Активность смотрит назад: звонок состоялся,
письмо ушло. Одна таблица на оба смысла означала бы колонку «срок», пустую у
половины строк, и список просроченного, в который попадают состоявшиеся звонки.

Правила:

- **Связь с клиентом или сделкой обязательна** — `422`. Задача без обеих не
  покажется ни в одной карточке. Задача по сделке подставляет клиента сделки;
  клиент и сделка из разных карточек не сходятся — тоже `422`.
- **Закрытие требует результата** (`complete`), отмена — причины (`cancel`),
  иначе `422`. Галочка без слов не говорит, дозвонились ли, и через неделю
  работа делается заново. Правило продублировано ограничением базы
  `crm_task_closed_needs_result`.
- **Закрытая задача рождает активность** того же типа (`document` и `other` —
  заметкой), с результатом в `note` и ссылкой `task`. Одной транзакцией:
  оборвись это посередине, задача выглядела бы сделанной, а в ленте клиента
  звонка бы не было. Отмена активности не рождает — ничего не было.
- **Закрытую задачу не правят и не закрывают дважды** — `422`.
- **Версия задачи обязательна** в `PATCH`/`complete`/`cancel` (§1.7).
- **Активность не бывает в будущем** — `422`: на будущее заводят задачу со
  сроком. Направление и длительность есть только у звонка (и в базе тоже).

`scope` — вкладки списка: `overdue` (срок прошёл), `today`, `week` (срок ещё не
прошёл), `open`, `closed`, `all`. Границы дня считаются по Ташкенту. `counts`
приходит по всем вкладкам сразу и не зависит от выбранной: счётчик «Просрочено»
не должен пропадать, когда открыли «Закрытые».

Уведомления ответственному и руководителю о просрочке (ТЗ 8.4 `[С]`) в этап не
входят: рассылка идёт через общий тракт уведомлений. Просроченное видно
счётчиком и цветом срока.

Миграция этапа: `20260929180000_crm_tasks_activities` — таблицы `crm_task` и
`crm_activity` с RLS, перечисления типов, ограничения «есть владелец»,
«закрытая несёт результат», «направление и длительность только у звонка».

**Смежная правка, задевающая все даты API.** Драйвер Prisma разбирал
`timestamptz` наивно, а сервер базы настроен на `Asia/Tashkent`: приложение
сходилось само с собой, но с `now()` внутри SQL расходилось на пять часов.
Задача со сроком «сегодня к 17:00» ложилась в базу как 12:00 и становилась
просроченной раньше срока. Сессии приложения и посева переведены в UTC
(`-c timezone=UTC`), проверка — `backend/test/db-time.spec.ts`. Выражения
`AT TIME ZONE 'Asia/Tashkent'` в отчётах не затронуты: они называют пояс явно.

### 14.16. CRM: карточка клиента целиком — `/crm/partners/{uid}/*`

Пятый этап модуля (ТЗ 8.2).

| Метод | Путь | Право |
|---|---|---|
| GET | `/crm/partners/{uid}/deals` | `crm.view` |
| GET | `/crm/partners/{uid}/orders` | `crm.view` |
| GET | `/crm/partners/{uid}/documents` | `crm.view` |
| GET | `/crm/partners/{uid}/finance` | `crm.view` |
| GET | `/crm/partners/{uid}/history` | `crm.view` |

Задачи, активности и файлы у карточки берутся из готовых источников и второй
раз здесь не описываются: `/crm/tasks?partnerUid=`, `/crm/activities?partnerUid=`
и `/attachments?owner=partner&uid=` (§14.10 — к владельцам добавился `partner`,
право по нему `crm.view` / `crm.edit`).

**Карточка ничего не считает сама.** Заказы приходят из продаж, долг и платежи —
из финансов, причём выражениями из `backend/src/finance/receivables.ts`: те же,
что наполняют список дебиторов. Свой второй счёт тех же денег разошёлся бы с
финансовым, и на вопрос «сколько должен клиент» система начала бы отвечать
двумя числами — а спрашивают его перед отгрузкой. Равенство проверяется тестом
`crm-partner-card.e2e.spec.ts`, а не обещанием: отдельная проверка следит, что
отменённый заказ в долг не попадает ни там, ни там.

`finance` отдаёт `debt`, `overdue`, `debtLimit`, `overLimit`, `unpaidOrders`,
`maxOverdueDays`, `oldestDueDate` и до ста последних операций клиента.
`overLimit` — отдельный признак, а не «долг больше нуля»: отгружать дальше
нельзя именно по нему.

`documents` отдаёт `readOnly: true`. Таблица документов заведена и заполнена, а
модуля документов ещё нет: строки показываем, создавать и печатать нечем.
Прятать существующие документы до появления модуля значило бы врать, что их нет.

**Журнал изменений.** Таблица `audit_log` существовала с первой миграции и
закрыта триггером `audit_log_append_only` — строку нельзя ни исправить, ни
удалить, — но до этого этапа в неё никто не писал. Теперь правки клиента и его
контактных лиц пишутся туда той же транзакцией, что и само изменение:
отдельной транзакцией журнал расходился бы с данными. В `changes` попадает
только то, что действительно изменилось, парой «было — стало»; правка, ничего
не менявшая, записи не оставляет. Контактные лица пишутся в историю клиента
(`entity_type = 'partner'`), а не своей сущностью: в карточке ищут «когда
сменили телефон», а не «что было с контактом номер такой-то».

**Право на все вкладки одно — `crm.view`.** Заказы, долг и платежи клиента
названы в ТЗ 8.2 содержимым его карточки: менеджер смотрит их перед тем, как
обещать отгрузку. Разрезать карточку по правам финансов значило бы показывать
половину экрана с необъяснимо пустыми вкладками. Вопрос «кто именно видит

### 14.17. CRM: отчёты — `/crm/reports/{kind}`

Шестой этап модуля (ТЗ 8: «отчёты по менеджерам, источникам, конверсии и
причинам отказов»).

| Метод | Путь | Право |
|---|---|---|
| GET | `/crm/reports/{kind}?from=&to=&limit=` | `crm.view` |
| GET | `/crm/reports/{kind}/file?format=xlsx\|csv` | `crm.view` |

`kind`: `funnel`, `managers`, `sources`, `lost-reasons`. Форма ответа общая с
отчётами склада (§14.9): заголовок, подзаголовок, колонки, строки, признак
обрезки — плюс `totals` для плашек над таблицей. Форма описана в
`backend/src/common/report.ts` и используется обоими модулями: выгрузка берёт
ровно её, поэтому в Excel уходит то же, что на экране.

**Конверсия считается по следу переходов, а не по текущей стадии.** Текущая
стадия говорит, где сделка лежит сейчас: дошедшая до договора и проигранная из
«расчёта» уже ушла, и в числителе её не видно. Воронка берёт
`deal_stage_event` (пишется с Э3): «дошла до стадии» значит «есть событие
перехода в неё», даже если сделка стоит дальше или закрыта.

**Когорта — по дате заведения сделки.** Отчёт берёт сделки, заведённые в
периоде, и смотрит, куда они дошли к сегодняшнему дню. Считать по дате самого
перехода значило бы сравнивать разные сделки в числителе и знаменателе: в марте
до договора дошли те, кого завели в январе. Цена честности названа в
подзаголовке: у свежей когорты конверсия занижена — сделки ещё идут.

У конечных стадий колонка «от прошлой стадии» пуста: перед «проиграна» в списке
стоит «выиграна», и деление одной на другую давало бы 133%. Отвалившиеся сделки
уходят с разных стадий, одной «прошлой» у них нет.

У менеджеров конверсия — доля выигранных **среди закрытых**: незакрытые ещё
могут стать любыми, и включать их в знаменатель значит занижать показатель тем,
у кого много работы в ходу.

Источники считают две вещи: обращения — по источнику заявки, сделки — по
источнику карточки клиента. Источник попадает в карточку сам, превращением
обращения (§14.13).

Период по умолчанию — 90 дней, а не 30: цикл сделки по металлу длиннее месяца,
и на тридцати днях воронка показывала бы почти одни незакрытые сделки. Границы
суток считаются по Ташкенту.

### 14.18. CRM: справочники на запись — `/crm/refs/*`

| Метод | Путь | Право | Что делает |
|---|---|---|---|
| `GET` | `/crm/refs?all=` | `crm.view` | стадии, источники, причины отказа, типы задач одним ответом |
| `POST` | `/crm/refs/stages` | `refs.edit` | новая стадия воронки |
| `PATCH` | `/crm/refs/stages/{uid}` | `refs.edit` | название, вероятность, код, включение |
| `DELETE` | `/crm/refs/stages/{uid}` | `refs.edit` | удаление нетронутой стадии |
| `POST` | `/crm/refs/stages/order` | `refs.edit` | порядок стадий списком целиком |
| `POST`/`PATCH`/`DELETE` | `/crm/refs/sources[/{uid}]` | `refs.edit` | источники обращений |
| `POST`/`PATCH`/`DELETE` | `/crm/refs/lost-reasons[/{uid}]` | `refs.edit` | причины отказа |
| `POST`/`PATCH`/`DELETE` | `/crm/refs/task-types[/{uid}]` | `refs.edit` | типы задач |

Чтение — правом `crm.view`: из справочника подбирают в формах, и без него не
завести ни обращение, ни задачу. Запись — правом `refs.edit`, тем же, что у
складских справочников: это работа того, кто отвечает за названия, а не того,
кто ведёт клиента. Отдельного права для CRM не заводилось — иначе настройку
воронки и настройку номенклатуры пришлось бы выдавать по отдельности, о чём
никто не просил.

Ответ `GET /crm/refs` в каждой строке несёт `usage` — число записей, которые на
неё ссылаются: у стадии `deals`, `openDeals`, `events`, у источника `leads` и
`partners`, у причины и типа задачи — `deals`/`tasks`. По ним и решают, что
можно выключить.

**Три правила, общие со складскими справочниками (§14.9).**

1. **Использованное выключается, а не удаляется.** `DELETE` отвечает `409` и
   кладёт числа в `error.details`. Удалив источник «Реклама», мы стёрли бы его
   из отчёта за прошлый квартал, по которому оплачивали рекламу.
2. **Правка, меняющая смысл записанного, отклоняется.** Код стадии, по которой
   ходили сделки, закрыт: по нему читается след переходов. Канал источника, по
   которому уже пришли обращения, закрыт: смена переписала бы задним числом,
   откуда они пришли. Название и вероятность меняются всегда — это подпись, а
   не смысл.
3. **Справочник не может опуститься до нуля.** Обращение не принимается без
   источника, проигрыш — без причины, задача — без типа. Выключение последней
   действующей строки отвечает `422`.

**Конечные стадии системные.** `POST /crm/refs/stages` заводит только рабочую
стадию: конечных ровно две, `won` и `lost`, и попадают в них не переносом, а
действиями `/win` и `/lose`, которые ищут стадию по коду. Третья конечная стала
бы колонкой, в которую невозможно попасть. Выключить и удалить конечную нельзя
— закрыть сделку станет нечем.

**Порядок задаётся списком целиком** (`POST /crm/refs/stages/order`, `uids` —
все рабочие стадии компании по одному разу). Номер у одной строки оставил бы
воронку с двумя третьими стадиями. Конечные всегда получают номера после
рабочих, их в списке не передают.

**Выключенная строка не предлагается, но остаётся у тех, кто по ней записан.**
`GET /crm/deal-stages`, доска сделок и `GET /crm/partners/options` отдают только
действующие; перенос в выключенную стадию, обращение с выключенным источником и
задача с выключенным типом отвечают `422`. Отчёт по воронке при этом считает по
всем стадиям — иначе из истории пропал бы кусок пути.

**Тип задачи несёт вид активности** (`activityKind`: `call`, `meeting`,
`letter`, `note`). Закрытая задача ложится активностью в ленту клиента, и
решает это тип: заведя «выезд на объект» встречей, заказчик получит его в
ответе на «покажи все встречи». Поэтому поле обязательно при создании. Менять
его у использованного типа можно: уже записанные активности задним числом не
переписываются, меняется только то, чем ляжет следующая закрытая задача.


### 14.19. Админ: привязка Telegram — `/admin/users/{uid}/telegram`

| Метод | Путь | Право | Ответ |
|---|---|---|---|
| POST | `/admin/users/{uid}/telegram/code` | `admin.users` | `{code, expiresAt, ttlMinutes, login}` |
| DELETE | `/admin/users/{uid}/telegram` | `admin.users` | `{uid, linked: false}` |

`GET /admin/users` отдаёт у каждого человека
`telegram: { linked, userId, linkedAt, codeExpiresAt }`. `codeExpiresAt` — живой
код: выдан, но ещё не введён. Самого кода там нет и быть не может.

**Код виден один раз — в ответе на выдачу.** В базе лежит `sha256`, в журнале
действий только факт выдачи и срок. Поэтому выдача — `POST`, а не `GET`: её
нельзя ни повторить из истории браузера, ни закешировать.

**Восемь знаков, 15 минут, однозначный алфавит** (без `0`/`O` и `1`/`I`): код
диктуют голосом и набирают в чужом приложении. Выдача нового кода гасит прежние
неиспользованные — иначе «виден один раз» перестаёт что-либо значить.

**Обмена кода на привязку в API нет.** Код принимает служба
`TelegramLinkService.claim(code, telegramUserId)`, и её позовёт процесс бота,
который узнаёт номер аккаунта от самого Telegram. Открытый маршрут означал бы,
что подключиться может любой, кто угадал короткий код. Все отказы `claim`
говорят одно и то же («код не найден или уже не действует»): по сообщению нельзя
понять, существует ли код.

**Привязка одна на человека и одна на аккаунт Telegram** (уникальный индекс в
базе). Подключённому второй код не выдаётся — `409`: сначала отключите прежний
аккаунт. Отключение доступно администратору всегда: телефоны теряют, а доступ
уходит вместе с аккаунтом. Привязка ложится в журнал с источником `bot`, выдача
и отключение — `web`.

### 14.20. Журнал действий: склад, финансы, справочники (ТЗ 3.4)

Маршрута здесь нет — читается журнал тем же `GET /admin/audit-log`. Этап закрыл
дыру: писали в `audit_log` только CRM, документы и админка, а движения склада,
финансовые операции и правки справочников исчезали без следа.

Кто пишет теперь и под какими действиями:

| Сущность | Действия |
|---|---|
| `stock_move` | `create`, `reverse` |
| `stock_reservation` | `create` (с признаком `overSell`), `release` |
| `inventory_sheet` | `create`, `count`, `finish`, `approve`, `cancel` |
| `finance_operation` | `create`, `update`, `reverse`, `submit`, `approve`, `reject`, `post` |
| `budget` | `create`, `update`, `delete` |
| `item`, `warehouse`, `warehouse_zone`, `storage_location`, `stock_reason`, `item_stock_level`, `company_settings` | `create`, `update`, `delete`, `set` |

**Запись идёт той же транзакцией, что и само изменение.** Отдельной транзакцией
журнал расходился бы с данными: откат движения оставлял бы в истории отмену того,
чего не было. Поэтому `writeAudit` принимает `tx`, а не сервис Prisma.

**В `changes` только изменившееся, парой «было — стало».** Правка, ничего не
менявшая, записи не оставляет — иначе журнал заполняется открытыми и закрытыми
формами. Для пересчёта инвентаризации вместо всех строк пишется их число
(`diffLines`): в журнале ищут «кто утвердил расхождение», а сами строки лежат в
самой ведомости.

**Код действия без подписи — ошибка сборки, а не мелочь интерфейса.** Человек
читает журнал словами; голый `edit_new_version` в таблице ничего ему не говорит.
Поэтому `test/journal-labels.spec.ts` обходит `writeAudit` в коде и требует для
каждого действия русское и узбекское название в `ACTIONS`.

**Строка журнала называет предмет, а не его `uid`.** `GET /admin/audit`
отдаёт `entityTitle` — номер документа, код номенклатуры, имя клиента,
наименование склада. Названия берутся одним запросом на тип сущности и только
по показанной странице. Удалённый предмет названия не получает: строка
остаётся с идентификатором — выдумывать имя тому, чего уже нет, нельзя, а
прятать запись нельзя тем более. Поля и значения переводит экран: `status
approved → draft` человеку не говорит ничего, «Статус Утверждён → Черновик»
говорит.

### 14.21. Производство: жизненный цикл заказа — `/production/orders*` (ТЗ 4.1)

**Дата:** 04.10.2026. **Кто:** Разработчик 1. **Статус:** реализовано в
`dev/backend`, проверено `test/production-write.e2e.spec.ts` (18 проверок) и
прогоном экрана `qa/production-live`.

**Почему это отступление.** В §5 переходы заказа описаны отдельными
эндпоинтами-действиями (`/plan`, `/start`, `/pause`, `/resume`, `/finish`,
`/close`, `/cancel`) и сказано «а не `PATCH status`». Сделано одним маршрутом с
целевым статусом в теле — так же, как уже работают продажи
(`POST /sales/orders/{uid}/status`). Причина не в экономии: у перехода есть
таблица допустимых следующих состояний, и она одна. Семь маршрутов означали бы
семь мест, где эту таблицу надо не забыть, а восьмой переход завели бы ещё
одним файлом. Возражение из §5 («на сервере остаётся место для проверок
конкретного перехода») снято тем, что проверки стоят внутри по `target`:
выпуск смотрит этапы, отмена — выпуск и выданный материал.

| Метод | Путь | Право |
|---|---|---|
| GET | `/production/options` | `production.view` |
| POST | `/production/orders` | `production.manage` |
| PATCH | `/production/orders/{uid}` | `production.manage` |
| POST | `/production/orders/{uid}/status` | `production.manage` |

`GET /production/orders/{uid}` дополнен полями: `nextStatuses` — куда заказ
можно перевести, `canEdit` — можно ли его править, `comment` — зачем этот
заказ, `statusReason` и `statusReasonAt` — последняя названная причина перехода
(почему остановили или отменили).

**Причина остановки не пишется в примечание заказа.** Сначала было сделано
наоборот — и живой прогон выкатки это показал: причина паузы затёрла то, зачем
заказ завели. Теперь причина живёт в журнале действий, а в карточку приходит
отдельным полем одной строкой из `audit_log`. Своего столбца под неё нет
намеренно: два источника одной правды разойдутся. **Список переходов считает сервер, а не экран:**
своя копия таблицы на фронте однажды разойдётся с проверкой, и человек нажмёт
кнопку, на которую ему ответят 409. `responsibleUid` в ответе появился ради
формы правки — по имени ответственного её не заполнить.

Путь заказа:

```
draft ──→ planned ──→ in_progress ──→ produced ──→ closed
  │           │          │    ↑
  │           │          ↓    │
  │           │        paused ┘
  └───────────┴──────────┴──→ cancelled
```

Правила, которые делают переход действием, а не записью поля:

- **выпуск не ставится поверх незавершённого этапа** — 409 с номером и
  названием этапа. Иначе «выпущен» значит «кто-то нажал кнопку»;
- **отмена не стирает факты** — если есть выпуск (`qty_produced > 0` или строки
  `production_output`) или выданный в цех материал, отмена отбивается: отменяют
  выпуск и возвращают материал, а не заказ целиком;
- **пауза и отмена требуют причины** (от 5 знаков) — из причин паузы растёт
  журнал простоев, а отмена без причины теряет историю;
- **править можно только черновик** — запланированный заказ уже увидел цех,
  и молча изменить ему количество значит соврать мастеру. Исправляют отменой и
  новым заказом;
- **отметки времени ставит переход, и каждая один раз**: `started_at` при
  первом запуске (возврат с паузы его не переписывает), `finished_at` при
  выпуске, `closed_at` при закрытии. На экране возврат с паузы и называется
  «Продолжить», а не «Запустить»: статус один, а действие для человека разное;
- **в заказ встаёт только то, что завод производит** (`item_type` `finished`
  или `semi`), штучная продукция — целым количеством;
- номер `ПР-00001` в пределах компании, под `pg_advisory_xact_lock`: без него
  одновременные заведения получили бы один номер и упали на уникальном индексе.

Журнал действий: `production_order` с действиями `create`, `update`, `status`
(подписи уже были в `ACTIONS`), заголовок строки — номер заказа.

**Чего в Э1 нет и почему.** Проверки «нельзя запустить заказ без этапов» здесь
нет: этапы появятся в Э3, и до тех пор она запрещала бы запускать всё, что
завели. Обратная ей проверка — «нельзя выпустить с открытым этапом» — стоит и
защищает данные уже сегодня. Отметок по этапам (`start`/`pause`/`finish`),
материалов, выпуска и себестоимости в маршрутах по-прежнему нет: это Э3–Э6.

### 14.22. Производство: техкарты с версиями — `/production/tech-cards*` (ТЗ 4.1)

**Дата:** 04.10.2026. **Кто:** Разработчик 1. **Статус:** реализовано в
`dev/backend`, проверено `test/production-techcards.e2e.spec.ts` (18 проверок)
и прогоном экрана `qa/production-live`.

| Метод | Путь | Право |
|---|---|---|
| GET | `/production/tech-cards?status=&itemCode=&limit=` | `production.view` |
| GET | `/production/tech-cards/{uid}` | `production.view` |
| POST | `/production/tech-cards` | `production.manage` |
| PATCH | `/production/tech-cards/{uid}` | `production.manage` |
| POST | `/production/tech-cards/{uid}/new-version` | `production.manage` |
| POST | `/production/tech-cards/{uid}/activate` | `production.manage` |
| POST | `/production/tech-cards/{uid}/archive` | `production.manage` |

**Отступление от §5.** Там карты описаны как `/production/tech-cards/{uid}/versions`
— отдельный маршрут списка версий. Сделано иначе: версии приходят в самой
карте полем `versions[]` (uid, номер, состояние). Отдельный запрос ради трёх
строк, которые всё равно рисуются рядом с картой, — лишний круг.

**Жизнь карты:** `draft → active → archived`.

- **правка только в черновике.** PATCH действующей карты отбивается 409 с
  объяснением: по ней уже посчитаны заведённые заказы, и правка на месте
  сдвинула бы их норму задним числом;
- **`new-version`** делает копию действующей карты в черновике — со всеми
  этапами и материалами. Иначе «поднять версию» означало бы «заведите заново»,
  а это и есть способ потерять девять нормативов из десяти;
- **на номенклатуре действует ровно одна карта.** `activate` уводит прежнюю
  действующую в архив той же транзакцией. Две активные означали бы, что заказ
  выбирает норму сам и молча;
- **незаконченный черновик на номенклатуре может быть только один** — и при
  заведении, и при поднятии версии. Иначе в справочнике копится хвост
  полуготовых карт;
- **пустую карту в работу не вводят**: без этапов нормировать нечего;
- **удаления нет вовсе**, только архив: на карту ссылаются заказы.

**Этапы и материалы заменяются целиком**, одним PATCH, а не по строке. Правка
нормы — это правка целого: убрали этап, перенумеровали остальные, сдвинули
материал. Отдельные маршруты на строку заставили бы экран выстраивать порядок
вызовов, и половина правки доезжала бы при обрыве. Проверки: номера этапов идут
подряд с 1 без дыр; материал не может быть самой продукцией карты; материал
нельзя повесить на этап, которого в карте нет; рабочий центр — активный и свой;
норма времени 0…100 000 минут целым; процент отхода 0…100.

**Нормы задаются на одну единицу продукции**, и это написано прямо на экране.
`output_qty` в модели остаётся равным 1 и в этом заходе не редактируется: пока
заказчик не сказал, что нормирует партией («на 100 п.м.»), две трактовки одного
поля — это способ однажды посчитать расход в сто раз меньше. Вопрос записан в
`09-CLIENT-INPUTS.md`.

**Связь с заказом.** `POST /production/orders` теперь сам подставляет
действующую карту номенклатуры и **запоминает её версию** (`tech_card_version`).
Завтра карту поправят новой версией — заказ останется посчитанным по той норме,
по которой его завели; новый заказ возьмёт новую. Карты в архиве и в черновике
норму заказу не дают. Правка черновика заказа со сменой продукции
перепривязывает карту вместе с ней.

`GET /production/options` дополнен `workCenters[]` и `materials[]` — тем же
ответом наполняется и форма заказа, и редактор карты. Список материалов
ограничен тремя сотнями строк: на таком размере выпадающий список ещё читается,
дальше нужен поиск — и это станет видно по номенклатуре заказчика.

Журнал действий: `tech_card` с действиями `create`, `update`, `version`,
`activate`, `archive`; заголовок строки — «код номенклатуры · vN».

### 14.23. Производство: этапы заказа и фиксация факта — `/production/orders/{uid}/stages*` (ТЗ 4.1)

**Дата:** 04.10.2026. **Кто:** Разработчик 1. **Статус:** реализовано в
`dev/backend`, проверено `test/production-stages.e2e.spec.ts` (23 проверки)
и прогоном экрана `qa/production-live`.

| Метод | Путь | Право |
|---|---|---|
| GET | `/production/my-stages?limit=` | `production.view` |
| POST | `/production/orders/{uid}/stages/from-card` | `production.manage` |
| PUT | `/production/orders/{uid}/stages` | `production.manage` |
| POST | `/production/orders/{uid}/stages/{seq}/mark` | `production.work` |

**Новое право и новая роль.** `production.work` — «отметки по своим этапам».
Отдельно от `production.manage`, потому что у станка стоит не тот, кто
планирует: рабочий не заводит заказы и не меняет нормы. Роль
`production_worker` («Сотрудник производства») получает `dashboard.view`,
`production.view`, `production.work` — и больше ничего. Право и роль едут
миграцией `20261004170000_production_worker_role`, а не только сидом: на
стенде и в проде база живёт, пересевать её нельзя.

**Чей этап.** С `production.manage` отмечают любой этап заказа. С одним
`production.work` — только свой: тот, где человек назван ответственным за этап,
или (если у этапа ответственного нет) за весь заказ. Чужая отметка — это чужая
смена и чужая выработка.

**Откуда берутся этапы.** `from-card` разворачивает этапы из техкарты **той
версии, которую помнит заказ**: карту потом поправят новой версией, а у этого
заказа норма останется прежней. Норма карты задана на единицу продукции,
поэтому план этапа — норма на количество заказа, округлённая вверх. `PUT
stages` задаёт список руками целиком: номера подряд с 1, пустой список не
принимается, рабочий центр проверяется, ответственного можно назначить на
этап.

**Когда план работ ещё можно переписать.** Пока по этапам никто не отработал.
Правило не про статус заказа, а про труд: заказ запустили утром, мастер увидел,
что забыли этап, — пусть поправит. После первой отметки перезапись стёрла бы
отработанное время вместе с событиями, из которых оно посчитано. По выпущенному,
закрытому и отменённому заказу план не правят вовсе.

**Отметки:** `start → pause → resume → finish`. Что можно нажать в текущем
состоянии, решает сервер; экран лишнего не предлагает, но запрещает всё равно
сервер. Отмечают только по заказу «в работе» — запускает заказ начальник
производства. Этап на паузе сначала продолжают, а потом заканчивают: иначе
непонятно, когда кончился простой.

- **фактическое время не вводится руками.** Оно складывается из закрытых
  отрезков: от «начал» или «продолжил» до «пауза» или «закончил». Часы берутся
  у базы, а не у браузера: у телефона в цеху часы свои;
- **пауза без причины не ставится.** Причина — из справочника причин вида
  `downtime` своей компании. При возобновлении закрывается строка
  `deviation_log` вида `downtime` с длительностью простоя и той же причиной:
  журнал простоев (ТЗ 4.1) растёт из пауз, а не заполняется отдельно;
- **запуск заказа требует этапов.** Проверка, отложенная в Э1: заказ без этапов
  означает, что цеху не сказали, что делать.

`GET /production/options` дополнен `downtimeReasons[]` — ими экран наполняет
вопрос «почему останавливаем». Причины те же, что у складских списаний:
справочник один на компанию.

Журнал действий: entity `production_order`, действия `stage.plan`,
`stage.start`, `stage.pause`, `stage.resume`, `stage.finish` — с номером этапа и
названием в `changes`.

**Чего в Э3 сознательно нет:**

- **порядка этапов.** У этапа заказа нет признака параллельности — он есть
  только в техкарте (`tech_card_stage.is_parallel`). Строгий порядок запретил
  бы то, что цех делает параллельно, а это хуже отсутствия проверки. Появится в
  Э7 вместе с календарём, где у этапа будут свои сроки;
- **плановых дат этапа**: `planned_start` и `planned_end` остаются пустыми —
  разложить норму по датам нельзя без графика смен (Э7);
- **выпуска по закрытию последнего этапа**: работа сделана ≠ продукция принята
  на склад. Приход — Э5.

### 14.24. Производство: материалы заказа — `/production/orders/{uid}/materials*` (ТЗ 4.1)

**Дата:** 04.10.2026. **Кто:** Разработчик 1. **Статус:** реализовано в
`dev/backend`, проверено `test/production-materials.e2e.spec.ts` (21 проверка)
и прогоном экрана `qa/production-live`.

| Метод | Путь | Право |
|---|---|---|
| GET | `/production/orders/{uid}/materials/stock?itemCode=` | `production.view` |
| POST | `/production/orders/{uid}/materials/from-card` | `production.manage` |
| PUT | `/production/orders/{uid}/materials` | `production.manage` |
| POST | `/production/orders/{uid}/materials/issue` | `warehouse.move` |
| POST | `/production/orders/{uid}/materials/return` | `warehouse.move` |
| POST | `/production/orders/{uid}/materials/use` | `production.manage` |

**Три числа на строку материала, а не одно.** `qtyPlanned` — сколько нужно по
норме, `qtyIssued` — сколько кладовщик отдал в цех, `qtyUsed` — сколько цех
израсходовал. Выданное минус использованное минус возвращённое — то, что
сейчас «на руках у цеха»: по нему видно, что лежит у станка, и его придётся
вернуть перед закрытием заказа. Одним числом эти три вопроса не отвечаются.

**План считается с отходами.** `from-card` берёт норму расхода на единицу из
техкарты той версии, которую помнит заказ, умножает на количество заказа и
добавляет процент отхода этапа, к которому материал привязан: нарезка
гарантированно даёт обрезь, и прятать её в «перерасход» нечестно. План правится
`PUT materials` руками, пока по заказу **ничего не выдано**: после первой
выдачи перезапись плана разошлась бы с движениями на складе.

**Выдача и возврат — это склад, а не заказ.** Остаток меняет настоящее
складское движение: `issue_to_production` и `return_from_production` пишет
`WarehouseWriteService` внутри той же транзакции, в которой меняются числа
заказа. Поэтому:

- право спрашивается складское (`warehouse.move`), а не производственное.
  Кладовщик отдаёт, цех расходует — разные люди и разные кнопки. Чтобы
  кладовщик видел, подо что выдаёт, роль `warehouse_keeper` получила
  `production.view` (миграция `20261004180000_keeper_sees_production`);
- движение помечено источником `production_material` с номером строки заказа:
  прослеживаемость партий (ТЗ 3.4) находит его сама, отдельного учёта не
  понадобилось;
- выдачу не «отменяют» сторнированием: движение с документом-источником
  `reverse` не принимает. Отдали лишнее — возвращают возвратом, и на складе
  видно оба факта;
- `GET materials/stock` отвечает на вопрос «где взять»: склад, ячейка, партия и
  свободный остаток. Экран из этого строит один выбор места, а не три поля.

**Расход склада не касается.** `use` только записывает, сколько ушло в работу:
со склада материал уже уехал выдачей, второе списание было бы двойным.
Записывают по заказу «в работе» или «на паузе», и не больше, чем на руках у
цеха. Перерасход — то, что выше плана, — ложится строкой `deviation_log` вида
`overuse` на разницу: журнал отклонений (ТЗ 4.1) растёт из факта, а не
заполняется отдельно. Если расход потом уточнили вниз, прежний перерасход не
удваивается — в журнал идёт только приращение.

Журнал действий: entity `production_order`, действия `material.plan`,
`material.issue`, `material.return`, `material.use`.

**Чего в Э4 сознательно нет:**

- **привязки расхода к этапу.** Строка материала знает этап из техкарты, но
  `use` его не спрашивает: в цеху один материал режут на нескольких этапах, и
  требовать выбор — лишний вопрос на экране;
- **автосписания по норме при закрытии этапа.** Норма — это план; сколько ушло
  на самом деле, говорит человек. Иначе перерасход никогда не появится;
- **себестоимости.** Материал посчитан в количестве, не в деньгах: цена партии
  и распределение по выпуску — Э6.

### 14.25. Производство: выпуск заказа — `/production/orders/{uid}/output*` (ТЗ 4.1)

**Дата:** 04.10.2026. **Кто:** Разработчик 1. **Статус:** реализовано в
`dev/backend`, проверено `test/production-outputs.e2e.spec.ts` (22 проверки)
и прогоном экрана `qa/production-live`.

| Метод | Путь | Право |
|---|---|---|
| GET | `/production/orders/{uid}/outputs` | `production.view` |
| POST | `/production/orders/{uid}/output` | `production.manage` |
| POST | `/production/orders/{uid}/rework` | `production.manage` |

**Четыре вида выпуска, и у каждого своя судьба.** `good` — годная продукция,
`semi` — полуфабрикат другой номенклатуры, `defect` — брак, `waste` — отход
техпроцесса. Годное и полуфабрикат **уходят на склад тем же действием**:
движения делает `WarehouseWriteService` внутри той же транзакции, тип
`output`. Брак и отход на склад не приходуются вовсе — их там нет: брак либо
переделывают, либо списывает цех, а обрезь это не товар.

**Тип `output` со складского экрана не завести.** Он не входит в `MoveKind`
формы и не имеет строки в таблице прав: `WriteService.create` отвечает отказом
словами, а `createIn` принимает его только изнутри производства, с пометкой
основания `production_output`. Приход продукции без заказа — это остаток,
который некому объяснить.

**Партия выпуска принадлежит заказу.** Номер по умолчанию — номер заказа,
`batch.production_order_id` указывает на него, и прослеживаемость (ТЗ 3.4)
отвечает «из какого задания эта труба» уже написанным кодом. В чужую партию
выпуск не дописывают: номер партии — паспорт металла, и дописать туда
сегодняшнюю трубу значит соврать про её происхождение.

**У брака и отхода причина обязательна,** и списки разные. Для брака — причины
вида `defect`, для отхода — новый вид `waste` (миграции
`20261004190000_reason_kind_waste` и `20261004190100_waste_reasons`). Сложить
их в один список значило бы сделать вид, что обрезь при нарезке — испорченная
работа. Брак дополнительно ложится строкой `deviation_log` вида `defect` с той
же причиной и количеством: журнал отклонений растёт из факта.

**Счётчики заказа** `qty_produced`, `qty_defect`, `qty_waste` складываются из
выпусков. Полуфабрикат в них не идёт: это не та продукция, ради которой завели
заказ. Верхняя граница есть только одна — суммарно не больше двух планов
заказа: цех иногда делает больше, и запрещать это нельзя (план запущенного
заказа не правят), но «1000» вместо «10» уедет на склад движением, которое уже
не отменить.

**Переделка — дочерний заказ** (`parent_order_id`), а не правка исходного:
иначе себестоимость переделки растворится в основном заказе. Переделать можно
только то, что записано браком и ещё не отдано в переделку; дочерний заказ
рождается черновиком, с той же номенклатурой, той же версией техкарты и своим
номером из общего счётчика.

**Выпуск заказа (`status = produced`) теперь требует записанного годного** —
проверка, отложенная в Э1. Порядок отказов осмысленный: сначала спрашивают про
незакрытые этапы (пока работа идёт, разговор о выпуске преждевременный), и
только потом про то, что цех сдал.

`GET /production/options` дополнен `defectReasons[]`, `wasteReasons[]`, а у
`warehouses[]` появились `locations[]`: у новой продукции остатка ещё нет,
спросить «где она лежит» не у кого, а склад с ячейками приход без ячейки не
примет.

Журнал действий: `output.good`, `output.defect`, `output.waste`, `output.semi`,
`order.rework`.

**Чего в Э5 сознательно нет:**

- **отмены выпуска.** Движения склада append-only, и продукция уже лежит на
  складе: ошибку исправляет склад своим движением, а не производство задним
  числом;
- **приёмки выпуска кладовщиком.** Сейчас одно действие цеха и приходует, и
  записывает. Двухшаговая приёмка («цех сдал — склад принял») — это решение
  заказчика, а не наше: записано в `09-CLIENT-INPUTS.md`;
- **себестоимости выпуска.** Количество есть, денег нет: распределение
  материалов и переделки по годному — Э6.

### 14.26. Производство: себестоимость заказа — `/production/orders/{uid}/cost` (ТЗ 4.7)

| Метод | Путь | Право | Что делает |
|---|---|---|---|
| GET | `/production/orders/{uid}/cost` | `production.view` | текущий расчёт со строками, предупреждениями и историей снимков |
| POST | `/production/orders/{uid}/cost` | `production.manage` | считает заново и фиксирует снимок |

Ответ GET: `{ current: null | CostDetail, history: CostEntry[] }`. `CostEntry` —
`calculatedAt`, `materialCost`, `semiCost`, `directCost`, `reworkCost`,
`totalCost`, `qtyGood`, `unitCost`, `isCurrent`, `calculatedByName`.
`CostDetail` — это `CostEntry` плюс `lines[]` и `warnings[]`. Строка `lines[]`:
`itemCode`, `itemNameRu`, `itemNameUz`, `unit`, `qty`, `unitCost`, `total`,
`fromOrderNumber`.

**Снимок, а не формула на лету.** Расчёт пишется строкой
`production_order_cost`, прежняя остаётся с `is_current = false`: цифру, по
которой продают, нельзя менять задним числом молча. Поэтому на экране видно,
когда и кто считал, а прошлые расчёты лежат рядом.

**Из чего складывается:**

- **материалы** — по факту расхода (`qty_used`), по той цене, по которой их
  выдали со склада: сумма берётся из движений `issue_to_production` этого
  заказа (`cost_total`, со знаком возвратов), а не из текущей цены остатка.
  План в расчёт не идёт вовсе;
- **полуфабрикаты** — по расчёту заказа, который их выпустил: если партия
  материала пришла из производства, цена берётся из его текущего снимка;
- **прямые затраты цеха** — отработанные минуты этапов на ставку часа участка
  (`work_center.cost_per_hour`, новое поле, по умолчанию 0);
- **переделка** — отдельной строкой: берётся текущий снимок дочернего заказа, а
  если его ещё не считали, но заказ уже можно считать, он считается тут же.
  Итог родителя не должен зависеть от того, нажал ли кто-то кнопку на
  переделке.

**Себестоимость единицы — на годный выпуск** (`production_output` вида `good`),
а не на весь: брак не уменьшает цену годного, он её удорожает. Нет годного —
единица не считается (0) и расчёт говорит об этом словами.

**Когда считают.** Только по заказу, работа по которому кончилась (`produced`,
`closed`): пока цех режет, расход записан не весь. Закрытие заказа считает
себестоимость само — тем же кодом, что и кнопка, иначе два пути давали бы два
числа.

**Партия выпуска получает цену.** После расчёта `batch.unit_cost` и
`stock_balance.unit_cost` партий этого заказа переоцениваются по
`unitCost`: до Э6 новая продукция лежала на складе с нулевой ценой.

**Предупреждения важнее итога** (`warnings[]`): материал ещё на руках у цеха;
цена списания неизвестна (материал попал в заказ без складской выдачи); у
участка не задана ставка часа; переделка ещё в работе; годного выпуска нет.
Цифра в таких случаях меньше правды, и экран говорит об этом прямо.

Журнал действий: `cost.calculate`.

**Чего в Э6 сознательно нет:**

- **косвенных и общезаводских затрат.** ТЗ 4.7 просит прямую себестоимость
  заказа; разнесение накладных — отдельный разговор с заказчиком о базе
  распределения;
- **ставок часа по справочнику.** Поле есть, цифры заказчик назовёт: до этого
  прямые затраты считаются нулём и расчёт об этом предупреждает
  (`09-CLIENT-INPUTS.md`);
- **отмены снимка.** Ошибочный расчёт исправляется новым расчётом — история
  остаётся целиком.

### 14.27. Производство: календарь и контроль — `/production/calendar`, `/production/deviations` (ТЗ 4.1)

| Метод | Путь | Право | Что делает |
|---|---|---|---|
| GET | `/production/calendar?from=&to=` | `production.view` | рабочая неделя, смены и дни периода |
| POST | `/production/calendar/week` | `production.manage` | задать рабочую неделю (ISO-дни) |
| POST | `/production/calendar/days` | `production.manage` | исключение: праздник или рабочая суббота |
| POST | `/production/calendar/days/{day}/clear` | `production.manage` | вернуть день к обычной неделе |
| POST | `/production/calendar/shifts` | `production.manage` | завести смену |
| PATCH | `/production/calendar/shifts/{uid}` | `production.manage` | поправить или закрыть смену |
| POST | `/production/orders/{uid}/stages/schedule` | `production.manage` | разложить этапы заказа по сменам |
| GET | `/production/deviations?period=&kind=&limit=` | `production.view` | журнал отклонений и итоги по видам |
| POST | `/production/deviations/downtime` | `production.manage` | записать простой участка |

**Календарь — это рабочая неделя плюс исключения.** `company.work_days` (новое
поле, ISO-дни, по умолчанию пн–сб) задаёт обычные дни;
`production_calendar_day` хранит только то, что из неё выбивается: праздник
среди недели и рабочую субботу. Календарь на год руками не заводят, а
исключение без причины не принимается — её читает цех.

**Смена** (`production_shift`) — код, названия и время начала и конца. Ночная
смена проходит через полночь: длительность считается секундами с добавлением
суток, потому что в Postgres время заворачивается по кругу (`time '00:00' + 24
часа` снова ноль). Рабочий день завода — сумма активных смен.

**Раскладка этапов по сменам** укладывает `planned_duration_min` каждого этапа
подряд в рабочий день; не влезло — переносится на следующий рабочий день.
Ответ: плановые даты этапов, `finishesOn` (день, когда кончим по графику),
`dueDate` и `lateDays` — опоздание в рабочих днях. Раскладка ничего не
запрещает: цех начинает и заканчивает, когда начал и закончил.

**Сроки в карточке заказа** (`GET /production/orders/{uid}`) дополнены полями
`workDaysLeft`, `workDaysOverdue`, `dueOnWorkingDay`: «осталось два дня» и
«осталось два рабочих дня» — разные вещи, если между ними воскресенье.

**Загрузка участков** в `GET /production/summary` получила `calendar`
(`workingDays`, `dayMinutes`, `availableMin`) и у каждого участка —
`downtimeMin`, `availableMin`, `loadPercent`, `capacityPerShift`. Процент
считается от рабочих смен календаря, а не от суток подряд. Смен нет —
`availableMin` и `loadPercent` равны `null`, и экран говорит об этом словами.

**Журнал отклонений** отдаёт строки (вид, заказ, этап, участок, причина,
длительность, сумма, кто записал) и итоги по видам за период. Виды прежние:
`downtime`, `overuse`, `defect`, `delay`.

**Простой участка руками** — то, чего не хватало: пауза этапа отвечает на
вопрос «почему встал заказ», а участок простаивает и без заказа. Причина
обязательна и только вида `downtime`; длительность в минутах и не больше суток
(длиннее — это опечатка, а не простой). У отклонения появилось своё поле
`work_center_id`: простой без этапа всё равно знает свой участок.

Журнал действий: `calendar.week`, `calendar.day`, `calendar.day.clear`,
`shift.create`, `shift.update`, `stages.schedule`, `downtime.register`.

**Чего в Э7 сознательно нет:**

- **перерывов внутри смены и между сменами.** Рабочий день в раскладке —
  непрерывный блок смен: учёта перерывов в системе нет, и выдумывать его
  значило бы считать сроки по правилу, которого никто не задавал;
- **графика смен по людям.** Смена — это время работы завода, а не наряд на
  бригаду: табель и выходы людей живут в другом модуле;
- **своего календаря у каждого участка.** Доступные минуты одинаковы для всех
  участков компании. Если линия работает в одну смену, а стан в две, это
  отдельное поле и отдельный разговор с заводом;
- **автоматической пересборки плана.** Раскладка делается по кнопке: план,
  который сам сдвигается от каждой отметки цеха, перестаёт быть планом.


### 14.28. Производство: отчёты и участки — `/production/reports`, `/production/work-centers` (ТЗ 4.1)

| Метод | Путь | Право | Что делает |
|---|---|---|---|
| GET | `/production/reports/{kind}?from=&to=&limit=` | `production.view` | таблица отчёта |
| GET | `/production/reports/{kind}/file?format=&from=&to=` | `production.view` | тот же отчёт файлом |
| GET | `/production/work-centers` | `production.view` | справочник участков |
| POST | `/production/work-centers` | `production.manage` | завести участок |
| PATCH | `/production/work-centers/{code}` | `production.manage` | поправить или закрыть участок |

**Пять отчётов** (`kind`), по одному на вопрос, который задают в цеху:

| `kind` | Заголовок | О чём |
|---|---|---|
| `orders` | План и факт по заказам | заказы со сроком в периоде: план, годное, брак, отход, «Выполнено, %», просрочка в рабочих днях |
| `output` | Выпуск по номенклатуре | что приняли за период и какова доля брака |
| `materials` | Расход материалов | норма против выдачи: план, выдано, возврат, расход, отклонение, стоимость |
| `deviations` | Отклонения по причинам | простои, перерасход и брак, сведённые по виду, причине и участку |
| `load` | Загрузка участков | план, факт, простой, доступные минуты календаря и процент загрузки |

Форма ответа — общая `ReportTable` (`common/report.ts`): `title`, `subtitle`,
`columns`, `rows`, `total`, `truncated`. Выгрузка (`/file`) берёт ровно её, так
что в Excel уходит то же, что видно на экране; форматы `xlsx`, `csv`, `pdf`,
имя файла — `proizvodstvo-<kind>-<дата>`.

**Период** — календарные дни местного времени. Не указан — последние тридцать
дней, и `subtitle` говорит период словами («с 05.09.2026 по 04.10.2026»): пустые
поля дат иначе читаются как «за всё время». Дата «с» позже даты «по» — 422,
неизвестный `kind` — 400.

**Чего отчёт не придумывает.** `Выполнено, %` равно `null`, когда план нулевой;
доля брака — `null`, когда годного не принимали; `Доступно, мин` и `Загрузка, %`
в отчёте загрузки — `null`, когда смены не заведены, и подзаголовок говорит об
этом словами. Деление на ноль нигде не прячется за нулём в отчёте: ноль — это
результат, `null` — «считать не из чего».

**Участки стали справочником.** До Э8 они жили только в данных: их завели при
установке, а завод живой — линию переносят, добавляют, выводят в ремонт. Код
участка — его ключ: он виден в техкартах и этапах, поэтому в `PATCH` он не
меняется, а повторный код в `POST` — 409 («Участок с кодом X уже заведён»).

**Участок не удаляют, а закрывают.** На нём висят закрытые этапы прошлых
заказов, и удали его — пропадёт, где их делали. Пока на участке есть
незакрытые этапы, закрыть его нельзя: 409 с их числом. В строке списка для
этого есть `openStages`.

**Ставка часа участка** (`costPerHour`) — та самая цифра, из которой Э6 считает
работу в себестоимости. Теперь её вводят на экране, а не миграцией. Нулевая
ставка не ошибка, а незаполненный справочник: экран говорит, что в
себестоимости посчитаются только материалы.

**Список заказов стал страницей.** `GET /production/orders` отдаёт
`{rows, total, limit, offset}` вместо массива: прежняя сотня последних строк
отвечала на вопрос «что недавно», а в цеху спрашивают «где мой заказ». Экран
листает по 25 строк и пишет, где человек находится: «Заказы 1–25 из 34».

Журнал действий: `work_center.create`, `work_center.update`.

**Чего в Э8 сознательно нет:**

- **конструктора отчётов.** Пять отчётов отвечают на пять названных вопросов;
  произвольные срезы по выбору колонок — это другая работа и другой разговор
  с заказчиком, а выгрузка в Excel уже позволяет считать в нём что угодно;
- **графиков и диаграмм.** Отчёт — это таблица, которую печатают и
  подкладывают к делу; картинку по ней собирают в Excel;
- **своего календаря у участка.** Доступные минуты в загрузке общие для
  компании: собственный график у линии никто не задавал.

### 14.29. Язык ответа — `Accept-Language`, `POST /auth/me/locale` (ТЗ 13.4)

Интерфейс двуязычный, и часть его приходит с сервера: шапки отчётов, тексты
отказов, названия справочников. До этого раздела всё это было русским всегда —
на узбекском экране половина надписей говорила не на том языке, а в выгрузке
Excel язык вообще нельзя было выбрать на стороне экрана.

**Язык запроса.** Заголовок `Accept-Language: uz` (иначе русский). Он уже
разбирался в `ContextMiddleware`; теперь по нему отвечают три слоя:

| Слой | Как устроено |
|---|---|
| Тексты сервера | `say(ru, uz)` из `common/say.ts` — русский первым, это язык кода и журналов |
| Повторяющиеся отказы | `MSG.*` из `common/messages.ts`: «Компания не выбрана» стояла в 19 местах |
| Названия справочников | SQL-функция `app_loc(name_ru, name_uz)` по настройке `app.locale` |

`app.locale` выставляется в той же транзакции, где `app.company_ids` для RLS
(`PrismaService.withContext`). Имя колонки нельзя передать параметром, а
половина запросов собрана строками — выбор языка в SQL оказался единственным
способом, работающим во всех запросах сразу. Вне запроса (миграция, посев,
воркер) настройки нет, и `app_loc` отдаёт русское: это не ошибка, а работа без
человека.

**Названия в ответах — одно правило.** Объект, у которого название правят
(справочники), отдаёт пару `nameRu`/`nameUz`, и язык выбирает экран
(`refName` в `lib/formatters.ts`). Готовая строка для показа (`companyName`,
`partner`, `reason`, шапка отчёта) приходит уже на языке запроса.

**Выбор языка за человеком.** `POST /auth/me/locale` с телом
`{"locale":"ru"|"uz"}` — прав не требует, идентификатор берётся из токена.
Язык пишется в `user_account.locale`, то есть один на веб и бота: раньше в боте
он запоминался, а веб забывал выбор при каждой перезагрузке. `GET /auth/me`
и ответ входа его возвращают; экран читает язык профиля при входе, а
сознательный выбор в этом браузере сильнее профиля.

Чужой язык отбивается: `locale` принимает только `ru` и `uz`.

**Чем проверено:**

- `test/locale.e2e.spec.ts` — язык человека, шапки трёх отчётов, названия
  через `app_loc`, пара в справочнике мест, текст отказа;
- `test/messages-locale.spec.ts` — разбор исходников: русский текст в
  исключении обязан идти через `say()`. Каталог `bot/` не считается, у бота
  свой двуязычный слой;
- `qa/web-uz/run.mjs` — обход всех модулей и вкладок под узбекским с чтением
  отрисованных надписей. Данные заказчика отсеиваются словарём из базы:
  русское название, у которого в базе есть узбекское, — находка, а название
  без узбекского — данные, и переводить их за заказчика нельзя.

### 14.30. Мобильное приложение: сессии, устройства, push, ключ повтора (ТЗ 10, 02-ARCHITECTURE 7.1)

Клиент называет себя заголовком **`X-Client: mobile`**. По нему сервер:

- выдаёт при входе короткий токен доступа (15 минут) и refresh-токен (30 дней);
- требует `Idempotency-Key` на каждой записи (POST/PUT/PATCH/DELETE), кроме
  `/auth/*` и `/devices/register`;
- пишет действия в `audit_log` с источником `mobile`.

Браузер (без заголовка) работает как раньше: токен на 12 часов, ключ повтора
не обязателен. Но и у браузера каждый вход — сессия, которую можно отозвать.

**Вход телефона** — `POST /auth/login` с полем `device`:

```json
{ "login": "a.saidov", "password": "…",
  "device": { "installationId": "android-…", "platform": "android",
              "model": "Samsung SM-A546", "osVersion": "34", "appVersion": "0.7.0",
              "pushToken": "ExponentPushToken[…]", "pushProvider": "expo" } }
```

Ответ дополнительно к прежним полям: `accessToken` (то же, что `token`),
`expiresIn` (секунды), `refreshToken` (только телефону), `sessionUid`,
`device: { uid }`. Отозванное устройство — `403 DEVICE_REVOKED`.

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/auth/refresh` | `{refreshToken}` → `{token, accessToken, refreshToken, expiresIn}`. Ключ одноразовый: старый после обновления даёт `401 SESSION_EXPIRED` |
| POST | `/auth/logout` | закрывает текущую сессию; её токены сразу перестают приниматься |
| GET | `/auth/sessions` | свои живые сессии, текущая — `current: true` |
| DELETE | `/auth/sessions/{uid}` | закрыть свою сессию; чужая — 404 |
| POST | `/devices/register` | телефон и его push-адрес (`DeviceDto`); привязывает текущую сессию к устройству |
| GET | `/mobile/config` | открыто: `minVersion`, `latestVersion`, `updateUrl`, `messageRu/Uz` |
| GET | `/admin/devices?userUid=` | `admin.users`: устройства, число живых сессий, кто отозвал |
| POST | `/admin/devices/{uid}/revoke` | `admin.users`: отозвать телефон и все его сессии (`{reason?}`) |
| POST | `/admin/devices/{uid}/restore` | `admin.users`: вернуть телефон |
| GET | `/admin/sessions?userUid=` | `admin.users`: живые сессии людей |
| DELETE | `/admin/sessions/{uid}` | `admin.users`: закрыть чужую сессию |
| GET / PUT | `/admin/mobile-config` | `settings.edit`: настройки приложения; минимальная версия не выше актуальной |

Отказ по токену с отозванной или истёкшей сессией — `401` с кодом
`SESSION_EXPIRED`: телефон по нему идёт на экран входа без сообщения об
ошибке. Старые токены без `sid` принимаются до своего срока.

**Ключ повтора с телефона.** Первый запрос выполняется, ответ хранится сутки
(`idempotency_key`); повтор с тем же ключом и телом получает тот же ответ без
повторного выполнения; тот же ключ с другим телом — `409 IDEMPOTENCY_KEY_REUSED`;
нет ключа — `400 IDEMPOTENCY_KEY_REQUIRED`.

**Push.** Те же строки `notification_outbox`, что уходят в Telegram (те же права
и личные выключатели), со своей отметкой `push_sent_at`. Доставка — служба Expo
(`exp.host`), раз в минуту из процесса API (`PUSH_SCHEDULER=off` выключает).
Шлётся только собранное после регистрации телефона; адрес, который служба
назвала мёртвым (`DeviceNotRegistered`), стирается. Ключи FCM и APNs заводятся в
аккаунте Expo проекта, не на сервере.
