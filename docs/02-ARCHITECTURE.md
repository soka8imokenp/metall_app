# Архитектура системы METALL ASIA

Документ описывает, как устроена система и почему именно так. Решения приняты
исходя из того, что это учётная система с деньгами и остатками: цена ошибки —
не битый пиксель, а расхождение склада с реальностью и спор с клиентом о сумме.

---

## 1. Главные архитектурные решения

| # | Решение | Причина |
|---|---|---|
| 1 | Один монолит с чёткими модулями, а не микросервисы | Весь смысл системы — сквозные транзакции «резерв → списание → себестоимость → платёж». В микросервисах это распределённая транзакция и вечные расхождения. Срок 4 недели дополнительно закрывает вопрос |
| 2 | Склад — неизменяемый журнал движений, остаток вычисляется | Остаток-поле рано или поздно расходится с историей и починить нельзя. Журнал всегда можно пересчитать |
| 3 | Деньги — двойная запись по счетам | Сходимость проверяется арифметически, а не на глаз. Любой отчёт выводится из одного источника |
| 4 | Мультитенантность через `company_id` + RLS в PostgreSQL | Требование Спецификации 3.2: сотрудник одной компании не должен видеть данные другой. Забытое `WHERE company_id` в одном запросе — утечка; RLS закрывает это на уровне БД |
| 5 | Права — данные, а не код | Спецификация: «изменять роли и права доступа через административную панель без доработки системы» |
| 6 | Денежные и количественные величины — `numeric`, никогда float | `0.1 + 0.2` в float даёт расхождение, которое в учёте недопустимо |
| 7 | Все изменяющие операции идемпотентны по ключу | Мобильное приложение работает в цеху с плохой связью и будет повторять запросы |
| 8 | Транзакционный outbox для уведомлений и интеграций | Уведомление не должно уходить, если транзакция откатилась, и не должно теряться, если Telegram недоступен |
| 9 | Расчёт себестоимости — снимок, а не вычисление на лету | Иначе вчерашняя отгрузка меняет маржу задним числом при каждом новом приходе |
| 10 | Контракт API фиксируется до кода, фронт и бэкенд собираются по нему | Фронт делает сторонний исполнитель, бэкенд — позже. Контракт — единственный шов |

## 3. Слои и границы

### 3.1. Слои внутри бэкенда

```
HTTP-контроллер     принимает запрос, валидирует форму, не знает бизнес-правил
       ↓
Сценарий (use case) одна бизнес-операция целиком, владеет транзакцией
       ↓
Доменный сервис     правила предметной области, инварианты
       ↓
Репозиторий         доступ к данным, ничего не решает
```

Правило, которое держит систему в порядке: **бизнес-правило живёт ровно в одном
месте**. «Нельзя отгрузить больше, чем доступно» проверяется в доменном сервисе
склада, а не в контроллере, не на фронте и не в трёх местах сразу. Фронт дублирует
проверку только ради подсказки пользователю; решение всегда за сервером.

### 3.2. Границы модулей

Модули обращаются друг к другу только через публичные сервисы, не через чужие
таблицы. Связи между модулями:

| Кто | К кому | Зачем |
|---|---|---|
| Продажи | Склад | проверка доступного, резерв, отгрузка |
| Продажи | Производство | создание производственного заказа под нестандарт |
| Продажи | Финансы | ожидаемая оплата, дебиторка, маржа |
| Производство | Склад | выдача материалов, возврат, оприходование выпуска |
| Производство | Финансы | себестоимость заказа |
| Документы | все | данные для подстановки в шаблон |
| CRM | Продажи | сделка → заказ |
| Все | Доступ | проверка прав и области видимости |
| Все | Уведомления | события через outbox |

## 4. Мультитенантность двух компаний

### 4.1. Модель

Одна база, одна схема, разделение по `company_id`. Два уровня защиты:

1. **Прикладной** — каждый запрос выполняется в контексте пользователя, где
   известен список доступных ему компаний; репозитории подставляют фильтр.
2. **PostgreSQL RLS** — политика на таблицах не отдаёт строки чужой компании
   даже при ошибке в коде. Контекст ставится в начале транзакции:

```sql
SET LOCAL app.company_ids = '{1}';
SET LOCAL app.user_id = '42';
```

```sql
CREATE POLICY company_isolation ON sales_order
  USING (company_id = ANY (current_setting('app.company_ids')::bigint[]));
```

Второй уровень не «на всякий случай». Требование 3.2 Спецификации — про
конкуренцию двух юрлиц внутри одной группы; утечка коммерческих данных между
ними это спор с заказчиком, а не баг.

### 4.2. Сводный доступ

Уполномоченный руководитель получает несколько компаний в контексте.
Все сводные отчёты обязаны показывать разбивку по компаниям и корректно
исключать внутренние обороты между ними (продажа завода торговой компании —
не выручка группы).

### 4.3. Общие и раздельные данные

| Раздельно по компаниям | Общее |
|---|---|
| заказы, склады, движения, платежи, документы, сделки, клиенты | справочник единиц измерения, валюты и курсы, права, типы документов, шаблоны (с признаком компании), пользователи |

Пользователь — общая сущность, его роли — в разрезе компании.

### 4.4. Роли в базе: у работающего сервиса нет обхода политик

Ролей две, обе `NOSUPERUSER` — суперпользователь обходит RLS молча.

| Роль | Кто ею ходит | BYPASSRLS |
|---|---|---|
| `metall_owner` | миграции и сид, то есть отдельные запуски вне сервиса | да |
| `metall_app` | сам сервис, все запросы без исключений | нет |

Плюс `FORCE ROW LEVEL SECURITY`: владелец таблицы иначе не подчиняется
собственным политикам.

Вход в систему — место, где обход напрашивается: логин и пароль надо проверить
раньше, чем известны компании пользователя, а без контекста компаний политики
не отдают ничего. Соблазн — открыть второе подключение ролью владельца. Цена
ему: ради четырёх таблиц в процессе всё время открыт обход политик для всех
остальных, и любой случайный запрос через этот пул вернёт данные обеих
компаний.

Поэтому круг разорван в самой базе, а не в приложении:

- `user_account`, `login_log`, `permission`, `role_permission` политик не несут —
  это не данные арендатора, читать их без контекста можно;
- `user_role_assignment` получил вторую политику `own_assignments`:
  `USING (user_id = app.current_user_id())`. Политики PERMISSIVE складываются
  по ИЛИ, поэтому изоляция по компаниям работает как работала, а к ней
  добавляются собственные строки входящего пользователя.

Дальше профиль собран, контекст компаний выставлен, и запрос идёт обычным
путём. Подключение с BYPASSRLS в сервисе отсутствует.

Проверяется это тестом `test/runtime-privileges.spec.ts`, а не обещанием:
рабочая роль не должна иметь ни `rolsuper`, ни `rolbypassrls`; в `src/` не
должно быть ни `DATABASE_URL`, ни обращений к обходному пулу; из контекста
входа не должны читаться ни заказы, ни остатки, ни компании.

## 5. Складской контур

### 5.1. Журнал движений

Центральная таблица `stock_move` — только добавление. Ни одна строка не
редактируется и не удаляется. Ошибка исправляется сторнирующим движением со
ссылкой на исходное.

Каждое движение: дата, компания, тип операции, номенклатура, характеристика,
партия, серийный номер, склад-источник, склад-приёмник, место, количество
(в базовой единице), стоимость, документ-основание, автор.

Приход — движение «извне → склад», отгрузка — «склад → вовне», перемещение —
«склад → склад». Единая форма упрощает всё: остаток на любую дату — сумма
движений до этой даты.

### 5.2. Остатки

Остаток считается из журнала, но считать его каждый раз по миллиону строк
нельзя. Решение — агрегат `stock_balance`, обновляемый в той же транзакции,
что и движение:

- `qty_on_hand` — физический остаток;
- `qty_reserved` — в резерве;
- `qty_available` — вычисляемое, `on_hand − reserved`.

Ключ агрегата: компания, склад, место, номенклатура, характеристика, партия,
серийный номер. Обновление — `INSERT ... ON CONFLICT DO UPDATE` с блокировкой
строки: две параллельные отгрузки одной позиции выстраиваются в очередь, а не
портят цифру.

Ночная задача сверяет агрегат с суммой журнала и сообщает о расхождении.
Это дешёвая страховка, которая ловит ошибку в день её появления.

### 5.3. Резервы

Резерв — отдельная таблица со ссылкой на заказ и сроком. Резерв не двигает
товар, но уменьшает доступное. Снятие — при отгрузке, отмене заказа или
истечении срока (фоновая задача с уведомлением менеджеру).

### 5.4. Партии и FIFO

Списание подбирает партии по дате прихода. Стоимость движения = сумма
`количество × стоимость единицы партии` по подобранным партиям. Подбор и
списание — в одной транзакции с блокировкой партий, иначе два параллельных
списания заберут одну и ту же партию дважды.

Метод списания вынесен в настройку компании (FIFO или средневзвешенная) —
см. открытый вопрос в `01-TZ.md` §5.7.

### 5.5. Прослеживаемость

Строится обходом графа движений: от партии вверх (откуда пришла) и вниз
(куда ушла, в какой производственный заказ, в какой выпуск, кому отгружена).
Рекурсивный запрос по `stock_move` + связи производственных заказов.
Глубина ограничена, результат кэшируется на время просмотра.

## 6. Финансовый контур

### 6.1. Двойная запись

Каждая денежная операция порождает минимум две проводки: дебет одного счёта,
кредит другого. Сумма проводок операции равна нулю — это проверяется
ограничением в БД, а не надеждой на код.

Счета: кассы, банковские счета, расчёты с покупателями, расчёты с поставщиками,
доходы, расходы, НДС, внутренние перемещения.

Что это даёт: дебиторка, ДДС, прибыль и остатки по кассам выводятся из одной
таблицы проводок. Нет ситуации, когда отчёт о долге и отчёт о деньгах спорят
между собой, потому что их считали разными способами.

### 6.2. Валюты

Проводка хранит сумму в валюте операции и в базовой валюте компании, плюс
применённый курс и его дату. Курс фиксируется при проведении. Переоценка
валютных остатков — отдельная операция, а не пересчёт истории.

Сам курс живёт в справочнике `currency_rate` и попадает туда двумя путями
(ТЗ 6.2): загрузкой с открытого архива ЦБ РУз и руками. Ручной ввод старше:
загрузка строку с источником `manual` не трогает. Банк публикует официальный
курс раз в рабочий день — минутного опроса здесь нет и быть не может, проверка
идёт раз в час и только пока курса на сегодня нет. Подробности и правила —
`04-API-CONTRACT.md`, раздел 14.10а.

### 6.3. Неизменяемость

Проведённая операция не редактируется. Исправление — сторно (обратные проводки
со ссылкой на исходную операцию) плюс новая правильная операция. История
полностью восстановима, что и требуется от финансового контура.

### 6.4. Себестоимость и маржа

- Себестоимость отгрузки фиксируется в момент отгрузки из подобранных партий.
- Себестоимость производственного заказа рассчитывается при закрытии и
  сохраняется снимком (`production_order_cost`).
- Маржа заказа продажи = зафиксированная выручка − зафиксированная себестоимость.

Снимок — принципиально. Без него завтрашний приход по другой цене меняет
вчерашнюю маржу, и отчёт за закрытый месяц перестаёт быть воспроизводимым.

## 7. Доступ и права

### 7.1. Аутентификация

- Вход по логину и паролю, пароли — Argon2id.
- Короткоживущий access-токен (JWT, 15 минут) + refresh-токен в httpOnly cookie
  для веба и в защищённом хранилище для мобильного.
- Отзыв сессии администратором, список активных сессий пользователя.
- Журнал входов, в том числе неудачных; блокировка после серии неудач.

Telegram: привязка аккаунта одноразовым кодом из веб-интерфейса. Номер телефона
как идентификатор не используется — его подделать проще.

### 7.2. Авторизация

Два уровня, оба обязательны:

1. **Право на действие** — `module.entity.action`.
2. **Область видимости записи** — компания, подразделение, склад, «только свои».

Проверка области — не фильтр в UI, а условие в запросе и политика RLS.
Попытка открыть чужую запись по прямой ссылке даёт 404, а не 403: существование
чужой записи тоже информация.

### 7.3. Журнал действий

`audit_log` — только добавление. Пишутся: вход, изменение прав, создание и
изменение документов, проведение и сторно финансовых операций, складские
операции, изменение настроек, экспорт данных. Состав записи: кто, когда,
компания, сущность, действие, что было, что стало, источник (веб, мобильное,
бот, интеграция), IP.

## 8. Фоновые задачи и события

### 8.1. Outbox

Событие («заказ отгружен», «остаток ниже критического») пишется в таблицу
`outbox` в той же транзакции, что и само изменение. Отдельный обработчик
читает outbox и доставляет: уведомление в Telegram, push, вебхук во внешнюю
систему, пересчёт отчёта.

Так уведомление не уйдёт при откате транзакции и не потеряется при недоступном
Telegram — повтор с экспоненциальной задержкой, после N неудач — в «мёртвую»
очередь с сигналом администратору.

### 8.2. Расписание

| Задача | Период | Что делает |
|---|---|---|
| Контроль остатков | каждый час | сравнивает доступное с минимальным и критическим уровнем, формирует потребность в закупке |
| Просроченные этапы | каждый час | производственные этапы с истёкшим плановым сроком |
| Просроченные платежи | ежедневно утром | дебиторка с нарушенным сроком |
| Просроченные задачи CRM | ежедневно утром | задачи и сделки |
| Истечение резервов | ежедневно | снимает просроченные резервы |
| Сверка агрегата остатков | ночью | журнал против `stock_balance` |
| Курс валют | ежедневно | загрузка курсов, если источник доступен |
| Обмен с 1С/REGOS | по расписанию | при наличии доступа |
| Бэкап + проверка восстановления | ежедневно / еженедельно | п.3.3 Спецификации |

## 9. Документы

Генерация DOCX — подстановка в шаблон (docxtemplater): скалярные поля,
табличные части, условные блоки. PDF — печать готового HTML через headless
Chrome (на сервере разработки проверено, что кириллица и узбекская латиница
выходят корректно).

Файлы складываются в S3-совместимое хранилище, ссылка и метаданные — в БД.
Версия документа держит свои файлы: перевыпуск не затирает предыдущий.

Номер документа выдаётся атомарно через последовательность в БД в разрезе
компании, типа и периода.

## 10. Интеграционный слой

Единая точка вместо россыпи коннекторов:

- **Входящие вебхуки** — подписанный запрос, проверка подписи, постановка в
  очередь, обработка идемпотентна по внешнему id.
- **Исходящие вебхуки** — настраиваемые подписки на события системы.
- **Импорт/экспорт файлов** — CSV/XLSX для 1С и REGOS, если прямого API нет.
- **Журнал обменов** — каждое сообщение с телом, статусом и возможностью
  повторить вручную. Без него разбор «почему не пришла выписка» превращается
  в гадание.
- **Сопоставление справочников** — таблица соответствия внешних и внутренних
  идентификаторов. Обязательна: коды номенклатуры в 1С и в системе не совпадут.

Ни одна интеграция не находится на критическом пути пользовательской операции.
1С недоступна — заказ всё равно создаётся, обмен ждёт в очереди.

## 11. Наблюдаемость и эксплуатация

- Структурные логи (pino) с `request_id`, `user_id`, `company_id` в каждой записи.
- Трассировка (OpenTelemetry) на запросах API и фоновых задачах.
- Метрики (Prometheus): время ответа по эндпоинтам, длина очередей, ошибки
  интеграций, расхождения сверки остатков.
- Health-check: БД, Redis, хранилище файлов, Telegram API.
- Развёртывание: Docker Compose на сервере заказчика (сервер в Республике
  Узбекистан — п.5.7 Договора). Миграции БД — версионируемые, накатываются
  при старте, откат предусмотрен.

## 13. Тестирование

| Уровень | Что покрывает |
|---|---|
| Модульные | расчёты: себестоимость, FIFO, маржа, НДС, пересчёт единиц, KPI |
| Интеграционные | сценарии целиком на реальной БД: заказ → резерв → производство → выпуск → отгрузка → оплата |
| Контрактные | ответы API против схемы из `04-API-CONTRACT.md` |
| Параллельность | одновременные отгрузки одной позиции, двойное проведение платежа, гонка за номером документа |
| Права | каждая роль против каждого эндпоинта, включая попытки доступа к чужой компании |
| Приёмочные | контрольные примеры заказчика (п.8 Спецификации) — ОТКРЫТО: ждём примеры |

Тесты на расчёты пишутся до реализации: красный → зелёный → обратная проверка.

## 14. Риски

| Риск | Чем грозит | Что делаем |
|---|---|---|
| Срок 4 недели при объёме Спецификации | несдача в срок | п.6.6 Договора: срок продлевается на время задержек заказчика. Фиксируем каждую задержку письменно в рабочем чате в день её возникновения |
| Нет образцов документов | конструктор документов не закрыть | запросили; до получения делаем движок и типовые формы |
| Нет контрольных примеров | спор на приёмке | запросили; расчёты покрываем тестами на согласованных примерах |
| Нет доступа к 1С/REGOS/банку/телефонии | интеграции не сделать | обменный слой готов, коннектор — по факту доступа; отсутствие не блокирует остальное |
| Сервер не выдан вовремя | нет приёмочной среды | поднимаем stage у себя для демонстрации, прод — по готовности заказчика |
| Фронт делает другой исполнитель | расхождение с бэкендом | контракт API зафиксирован заранее, моки повторяют контракт, приёмка фронта — против контракта |
| Два юрлица | утечка данных между компаниями | RLS на уровне БД + тесты прав |
