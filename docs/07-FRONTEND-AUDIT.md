## 2. Что на самом деле сделано

Заявлено «дашборд и продажи». Фактически открываются все восемь разделов, но
готовность у них разная.

| Раздел | Состояние | Чем измерено |
|---|---|---|
| Дашборд | рабочий экран | 4 KPI, график с переключением тонны/сумма и 3 мес/30 дн/7 дн, таблица заказов с 4 вкладками, настройка колонок, drag-handle |
| Продажи | рабочий экран | 3 подраздела (заказы, журнал ТТН, договоры), боковая панель спецификации, форма нового заказа, форма выписки ТТН, печать ТТН, два графика |
| Склад | демо-экран | одна таблица остатков, поиск, фильтр по марке стали, «только дефицит», вход в модалку прослеживаемости и сканер |
| Производство | демо-экран | одна карточка заказа, 3 вкладки (этапы, материалы, себестоимость), кнопки этапов |
| Финансы | демо-экран | 2 вкладки: журнал операций (1 строка) и дебиторка по срокам |
| Документы | демо-экран | реестр из 2 строк, кнопки PDF без обработчика |
| CRM | демо-экран | канбан на 4 стадии, переключатель «канбан/таблица» |
| Администрирование | демо-экран | роли и права, журнал действий; в меню не вынесен, вход через «Настройки» |

«Демо-экран» здесь значит: верстка есть, данных 1–3 записи, ни создания, ни
редактирования, ни фильтров сверх примитивных, ни пагинации, интерфейс только
на русском.

Стек фактический: **Vite 8.3 + React 19.3 + Tailwind 4.3 + Recharts 3.10 + lucide-react**,
TypeScript 7.0.2. Версии взяты из `bun.lock`, а не из `package.json`.

## 3. Главная проблема: слой данных собран неправильно

В `05-FRONTEND.md` п.7 было условие: замена моков на реальный бэкенд не должна
требовать правок в компонентах. Сейчас требует.

`src/lib/api-client.ts` написан по контракту грамотно: конверт ответа, заголовки
`X-Company-Id`, `Accept-Language`, `Authorization`, `Idempotency-Key` на запись,
разбор ошибки. **Но им пользуются два компонента из шестнадцати** — `ScanBarcodeModal`
и `TraceabilityModal`.

Остальные берут данные одним из трёх способов мимо клиента:

1. Импорт фикстур напрямую — `WarehouseView`, `ProductionView`, `FinanceView`,
   `DocumentsView`, `CrmView`, `SalesView` (`import { MOCK_… } from '../../mocks/fixtures'`).
2. Массив, зашитый внутри компонента — `DataTableSection` (`INITIAL_DOCUMENTS`, 1433 строки
   файла, из них большая часть — данные), `SalesView` (`INITIAL_SHIPMENTS`, `INITIAL_CONTRACTS`,
   и сами заказы в `useState` на строке 183).
3. Значения прямо в разметке — `KpiCards`: `value: '26.2 млрд'`, `'10 360 т'`, `badge: '+18.5%'`
   строками в `useMemo`. Никакого `GET /dashboard/summary` дашборд не делает.

Следствие: на каждый экран при подключении бэкенда придётся переписывать компонент,
а не менять одну переменную окружения. Плюс `USE_MOCKS` в `api-client.ts:47` — это
`const USE_MOCKS = true`, хотя комментарий на 10 строк выше обещает переключение через
`VITE_USE_MOCKS`. Обещание в комментарии кодом не подкреплено.

Отдельно: тип `DocumentItem` объявлен дважды и по-разному — в `types/api.ts` (по контракту)
и в `DataTableSection.tsx` (поля `target`, `limit`, `reviewer`, `category: 'outline' | 'past_perf' | …`).
Второй — остаток шаблона дашборда shadcn, на который натянули металлургическую лексику.

## 4. Дефекты, видимые глазами

### 4.1. 360 px не сделан вообще

Замер переполнения `<main>` по горизонтали, значения в пикселях:

| Раздел | 1440 | 360 |
|---|---|---|
| Дашборд | 0 | **167** |
| Продажи | 0 | **284** |
| Склад | 0 | **142** |
| Производство | 0 | **242** |
| Финансы | 0 | **147** |
| Документы | 0 | **21** |
| CRM | 0 | **89** |
| Администрирование | 0 | **89** |

Тема на результат не влияет — в тёмной те же цифры.

Причина видна на снимке `360-light-dashboard.png`: сайдбар на 360 остаётся развёрнутым
и занимает две трети экрана, содержимое ужато в остаток. Заголовок KPI переносится
по слогам, значение «10 360 т» ломается на три строки. Таблицы на карточки не
превращаются, нижней панели действий нет. То есть средний брейкпоинт (768–1439)
и мобильный из п. 2.3 спецификации не реализованы — сделана только ширина ≥1440.

### 4.2. Числа выводятся сырыми строками

На экране склада: `42.500000 т`, на производстве: `1120.000000 / 1800.000000 м`.
Это значение из контракта, отданное в разметку как есть. Форматирования количеств
нет; для денег местами есть `Number(...).toLocaleString('ru-RU')`, местами нет.

### 4.3. Точность денег теряется

`parseFloat` и `Number()` по исходникам — 46 вхождений, часть на суммах:
`SalesView.tsx:402-403` (цена и количество при создании заказа),
`CrmView.tsx:66` (сумма стадии воронки). Ровно то, что в `05-FRONTEND.md` п. 6.3
названо невыполненной работой: строковая точность приведена к JS-number по дороге.

### 4.4. Состояния экранов отсутствуют

Загрузка, пусто, ошибка, нет прав — ни одного из четырёх, кроме `loading` в
`TraceabilityModal`. Везде данные считаются присутствующими всегда.

### 4.5. Права не учитываются

Поле `permissions` описано в типах на каждой сущности, но в разметке не используется
нигде: единственное совпадение `permissions.` в компонентах — это локальный массив
в `AdminView`. Все кнопки нарисованы всем.

### 4.6. Состояние не живёт в URL

Роутера нет совсем. Раздел, фильтры, выбранный заказ — всё в `useState`.
Ссылку на заказ не отправить, «назад» в браузере уводит с приложения.
В п. 6.3 спецификации это тоже в списке невыполненной работы.

### 4.7. Две системы локализации, обе неполные

Словарь `t()` в `AppContext` используется только в `Sidebar` (18 вызовов) и `TopBar` (10).
`DataTableSection`, `KpiCards`, `MonochromeAreaChart`, `SalesView` переводят инлайновым
тернарником `isUz ? '…' : '…'` — 263 вхождения. `WarehouseView`, `ProductionView`,
`FinanceView`, `DocumentsView`, `CrmView`, `AdminView` не переведены вовсе: только русский.
Узбекская локаль в договоре обязательна.

Мелочь оттуда же: `'brand.name': 'Acme Inc.'` в обоих словарях.

### 4.8. Остатки чужого шаблона и чужого хостинга

- `package.json` → `"name": "react-example"`.
- Зависимость `@google/genai` 2.24.0 тянет `google-auth-library`, `protobufjs`, `ws` —
  в коде не используется ни разу.
- `express`, `dotenv`, `tsx` в зависимостях клиентского приложения — не используются.
- `.env.example` состоит из `GEMINI_API_KEY` и `APP_URL` для AI Studio; ни `VITE_API_URL`,
  ни `VITE_USE_MOCKS` в нём нет.
- `vite.config.ts` завязан на `DISABLE_HMR` от AI Studio.
- Словари `nav.lifecycle`, `nav.analytics`, `nav.projects`, `nav.team`, `nav.data_library`,
  `nav.word_assistant` — пункты меню шаблона, в приложении их нет.

### 4.9. Выдуманные утверждения в интерфейсе

Внизу экрана продаж подпись «Синхронизация с 1С и КПП активна». Интеграции с 1С нет
и доступа к ней клиент пока не дал. На демонстрации заказчику такая строка — обещание,
за которое придётся отвечать. Убрать.

## 6. Что сделано хорошо

Признать честно, иначе решение о судьбе кода будет неверным.

- Визуальный язык выдержан и выглядит как продукт, а не как макет: монохром,
  волосяные границы, табличные цифры, тёмная тема работает.
- `src/types/api.ts` (424 строки) написан строго по `03-DATA-MODEL.md` и `04-API-CONTRACT.md`:
  суммы и количества строками, `version` для оптимистической блокировки, `permissions`,
  конверт ответа и ошибки. Это переиспользуется дальше без переделки.
- Отраслевая часть не выдумана поверхностно: ГОСТ 10704-91, 10705-80, 30732-2020,
  марки Ст3сп / Ст20 / 09Г2С, ТЭСА, ППУ-ПЭ, штрипс, СОДК, паспорт ОТК, ТТН —
  всё на своих местах. Контрагенты и склады правдоподобны.
- `position: absolute` применён только по делу — выпадающие меню, иконка в поле ввода,
  подпись на графике. Подогнанных пикселей вместо flex/grid нет. Это требование
  спецификации выполнено.
- Дашборд и продажи на 1440 — рабочие экраны, их не стыдно показать заказчику
  после чистки п. 4.9.

Вывод: переписывать с нуля не нужно. Нужно достроить слой данных, адаптив и
локализацию, а экраны оставить.

## 7. Решения, которые нужно принять до кода

### 7.1. Next.js или остаться на Vite

В `05-FRONTEND.md` был записан Next.js 16.3 App Router. Пришёл Vite SPA.

Моя рекомендация — **остаться на Vite**. Обоснование: система закрыта авторизацией,
поэтому SSR, серверные компоненты и SEO не дают ничего; порт на App Router — это
переписывание всех шестнадцати компонентов и потеря нескольких дней из четырёх недель.
Стек фронтенда п. 2.5 договора относит к решению исполнителя, то есть к нам, и смена
не требует согласования с заказчиком.

Что при этом добавляется обязательно: React Router (состояние в URL), TanStack Query
(кэш и инвалидация), React Hook Form + Zod (формы и валидация).

Решение за Тагиром и Артёмом.

### 7.2. Кто доделывает недостающие шесть модулей

Либо тот же сторонний исполнитель по тем же документам, либо я. Вариант «я» безопаснее
по качеству, но занимает то же время, что и бэкенд, а срок по договору — 4 недели с
первого платежа.

### 7.3. Порядок этапов

Изначально: фронт целиком → потом бэкенд. Предлагаю иначе — **вертикально по модулям**:
«продажи» сначала доводятся до конца вместе с бэкендом и показываются заказчику,
потом склад, потом производство. Так первый рабочий результат виден на второй неделе,
а не на четвёртой, и расхождения контракта вскрываются на одном модуле, а не на шести.
