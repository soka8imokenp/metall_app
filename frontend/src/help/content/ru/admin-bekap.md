Эта статья — для тех, у кого открыт раздел **Настройки**.

Копию базы система делает сама, каждую ночь. Смотреть копии и запускать их вручную
— **Настройки → Копии базы**.

Ночное расписание включено по умолчанию: на новом сервере ничего настраивать не
нужно, копии начнутся сами. Выключается оно переменной `BACKUP_SCHEDULER` — тогда
экран прямо говорит «Расписание: Выключено», и копия делается только кнопкой. На
демонстрационном стенде расписание выключено нарочно: там копии не хранят.

## Что происходит без вас

1. Ночью, по умолчанию в **03:20** по времени сервера, система запускает `pg_dump`
   и пишет копию базы в каталог на том же сервере.
2. Копия сжимается и ложится файлом вида `metall-asia-20261007-032000-412.dump`.
   Хвост имени — номер записи в журнале копий: по нему файл и строка журнала
   находят друг друга.
3. В журнал записывается время начала, сколько шло, вес файла, его `sha256` и чем
   кончилось.
4. Лишние файлы удаляются: на диске держится столько последних копий, сколько
   задано в `BACKUP_KEEP` — по умолчанию **30**. Сколько именно, написано на
   экране в строке «Храним». Записи журнала при этом остаются все — по ним
   видно, что копия в тот день была.
5. Если копия не сделалась, администратору приходит сообщение в Telegram с
   причиной. Это обычное уведомление бота — как остальные
   [уведомления](help:telegram), его можно выключить, но не выключайте.

## Экран «Копии базы»

| Что показывает | Зачем |
| --- | --- |
| строка состояния сверху | когда была последняя удачная копия; больше 30 часов назад — предупреждение. При выключенном расписании предупреждения нет: ждать ночную копию не от кого |
| список копий | когда, сколько шло, вес, чем кончилось, кто запустил |
| кнопка «Сделать копию сейчас» | копия вне расписания: перед обновлением, перед большой правкой данных |
| «Скачать» у строки | забрать файл копии себе; у вытесненных копий кнопки нет — файла уже нет |

Копия идёт десятки секунд и мешает работе людей не больше, чем обычный отчёт.
Нажимать «Сделать копию сейчас» можно в рабочее время.

## Где лежат копии

На сервере стенда это каталог `dev/backend/var/backups-stand`. Диск рядом с базой,
и в этом его слабость: пожар, кража или отказ диска уносят базу вместе с копиями.
Поэтому раз в неделю скачивайте последнюю копию кнопкой «Скачать» и держите её на
другой машине. При переезде на свой сервер отведите под копии отдельный диск.

## Настройки на сервере

Задаются в файле окружения службы; что получилось, система показывает на экране.

| Переменная | Что значит | По умолчанию |
| --- | --- | --- |
| `BACKUP_DATABASE_URL` | адрес базы для `pg_dump`, ролью-владельцем схемы | обязательна, без неё копия не делается |
| `BACKUP_DIR` | каталог, куда писать копии | `./var/backups` |
| `BACKUP_AT` | время ночного запуска, `ЧЧ:ММ` | `03:20` |
| `BACKUP_KEEP` | сколько копий держать на диске | `30` |
| `BACKUP_PG_DUMP` | чем звать `pg_dump` | `pg_dump` |
| `BACKUP_SCHEDULER` | `off` выключает расписание | включено |

`BACKUP_DATABASE_URL` обязана указывать на роль-владельца схемы. Прикладной ролью
`pg_dump` вывезет защищённые таблицы **пустыми** и не скажет об этом: код выхода
нулевой, файл на месте, вес правдоподобный. Поэтому адрес задаётся отдельно от
рабочего, и без него система копию не делает вовсе.

## Как восстановить базу из копии

Кнопки «Восстановить» в системе нет, и это решение, а не недоделка: такая кнопка в
браузере — это «стереть все данные» в руках любого, кто получил сессию
администратора. Восстановление делается на сервере руками, по этому порядку.

1. Остановите службу системы, чтобы в базу никто не писал:
   `systemctl --user stop metall-asia-stand-api`.
2. Разверните копию **в новую базу**, а не в рабочую:

```
createdb -U postgres -O metall_owner metall_asia_restore
pg_restore -U postgres -d metall_asia_restore \
  --no-owner --no-privileges --exit-on-error \
  metall-asia-20261007-032000-412.dump
```

3. Сверьте число записей в новой базе с тем, что ожидаете, хотя бы по складу,
   заказам и финансам:

```
psql -U postgres -d metall_asia_restore -c \
  "select count(*) from stock_move; select count(*) from sales_order;"
```

4. Только теперь переключайте систему на восстановленную базу: поменяйте имя базы
   в адресе `APP_DATABASE_URL` в файле окружения службы и запустите её.
5. Старую базу не удаляйте неделю: если в восстановленной чего-то не хватит,
   сравнивать будет с чем.

База в контейнере — те же команды идут через него, а файл копии передаётся потоком:
`docker exec -i -e PGPASSWORD metall-asia-postgres pg_restore … < файл.dump`.

> **Не разворачивайте копию поверх рабочей базы.** Пересев базы сбрасывает пароли
> всех учётных записей, и система станет недоступна всем, кто в ней работал. Ровно
> поэтому шаги 2 и 4 разделены: сначала новая база, потом переключение.

## Раз в месяц проверьте, что копия живая

Копия, которую никто не разворачивал, — это файл, а не копия. Проверка — те же
шаги, но без остановки службы: развернуть последнюю копию в отдельную базу, сверить
число записей с рабочей, удалить временную базу. В проекте для этого есть готовый
скрипт — попросите его у тех, кто ведёт сервер.

## Что копия не покрывает

| Что | Где живёт | В копии базы |
| --- | --- | --- |
| данные системы | база PostgreSQL | да, это она и есть |
| загруженные файлы и вложения | каталог файлов на сервере | нет, копируются отдельно |
| код и сборка | git-репозиторий | не нужны, восстанавливаются [выкаткой](help:admin-vykatka) |
| файл окружения службы | сервер | нет, храните его копию отдельно и закрыто |

Вложения в дамп базы не попадают: это файлы на диске. Их каталог указан в
настройках службы, копируйте его тем же порядком, что и базу.
